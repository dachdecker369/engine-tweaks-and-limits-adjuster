# Notes

What each part does and the checks it makes, the measurements, the open issues and the bugs found in the projects the parts derive from. The design - every module, every format, every line of the log - is in [SPECIFICATIONS.md](SPECIFICATIONS.md), the game facts are in [PATTERNS.md](PATTERNS.md), the player's guide is [README.md](README.md), the credits and derivations in [CREDITS.md](CREDITS.md). Every part is TweaksV's own code since 2.0.0; the parts that follow another project's idea use none of its code.

- **Rules every part follows:** everything is found and checked before anything is written; a job's writes are all or nothing; what another mod has already changed is left alone; every job not done is a problem in the start-up summary, with the reason in the log; every value read from the game or the INI is bounded; nothing throws into the game; `DRY_RUN` and `DIAGNOSTIC_MODE` work the same for every part, with two exceptions: with `DIAGNOSTIC_MODE=1` the box streamer refuses its whole job when a tree-search call cannot be redirected, because the measurement is the reason the switch is on; and with `DRY_RUN=1` the Blips part checks its hook's sites but never sees `blip_controller`, which reaches it only through the hook a dry run does not make. A measurement whose thread cannot start is logged, not reported: it is a diagnostic aid, and the parts share one loop for it (`TweaksVMeasure`). The parts measured first (below) are aids as a whole: without `DIAGNOSTIC_MODE=1` they look for nothing, and `DRY_RUN` changes nothing in them but the siren count's measurement, which then redirects nothing.

- **`TweaksV.ini`:** created on the first start with its default settings. Missing keys are added back; existing values are never changed.
  - Every setting is defined once, in the table in `TweaksVSettings.h`: its section, key, default and limits, and the short comment the default file carries after its value (README.md explains every key in full). The default file, the keys added back - without a comment, since TweaksV adds none to an existing file - the log header and every reader come from it, and each setting is read once at start-up. A comment after a value, from `//` or `;`, is not part of it.
  - A value TweaksV cannot use - not a number, not on or off, outside its limits - is shown in the start-up summary as well as the log, with the value used instead.
  - `VERSION` under `[TWEAKSV]` says which layout the file has (3). A file of an older layout, from 2 on, is carried forward: it gets the keys it lacks, then the current `VERSION` written back in its line, a comment after it kept, and the log says so; a `VERSION` that cannot be written back is logged when the file is read-only and reported otherwise. A file without it has the layout of TweaksV 1.x, whatever else it holds: it is renamed to `TweaksV.old.ini` (an older `TweaksV.old.ini` that passes the own-file checks is replaced), the default file is written in its place and the start-up summary says so - nothing of the old file is read; a 1.x file that cannot be renamed is reported every start and not read either. A file from a newer TweaksV is reported.
- **`TweaksV.log`:** one log with a header (versions, paths, switches).
  - Paths in the Windows user's profile folder are written as `%USERPROFILE%\...`, also where the folder has its short form (`C:\Users\NAME~1`, as `%TEMP%` often has): logs get posted in public, and that folder is usually named after the user.
  - It grows to 64 MB at most, room for hours of the logs for testing; a last line says when it stops. Every kind of line that comes per event stops after 20,000 lines; the events are then only counted, with a summary every minute where the part has one.
- **Read-only game folders:** both files go to `%LOCALAPPDATA%\TweaksV` when the game folder cannot be written to.
  - A `TweaksV.ini` in the game folder always wins.
  - A read-only folder is normal, so it is only logged; it shows no message box. Any other reason, such as a `TweaksV.log` that another program holds open, is a problem in the start-up summary.
- **Links:** TweaksV writes only to its own files, never through a link to another file - which matters when the game runs as administrator:
  - A `TweaksV.log` in the game folder that is a link (a symbolic or a hard link) is left alone, and the log goes to `%LOCALAPPDATA%\TweaksV`;
  - A `TweaksV.ini` that is a link is neither read nor written: every setting keeps its built-in default;
  - `%LOCALAPPDATA%\TweaksV` must not be a link (a junction) itself; the game folder may be one, for an install moved to another drive;
  - Each of these is a problem in the start-up summary;
  - While TweaksV reads `TweaksV.ini` at start-up, the file cannot be renamed, deleted or replaced;
  - A file Windows keeps compressed (`compact`, CompactGUI) is not a link and is used as usual.

- **Conflicts:** two kinds of stand-alone plugin that do the job of one of TweaksV's parts are detected, in the game folder and its `scripts` and `plugins` folders. An old plugin TweaksV replaces (HeapAdjuster.asi, OpenRPF.asi, ...) switches its part off for the session and is listed in the start-up summary, which says to delete it. A plugin that stays installed, because another mod needs it, switches its part off for the session too, while the part is on in `TweaksV.ini`, and the summary names the `ENABLED=0` that stops the message, at every start until then; a part already off there gets no item, only a line in the log.
  - The one such plugin is NaturalVision Enhanced's loader, `onigiri.asi` 1.0.1.0 (PE timestamp 0x68543a76), for RageOpenV and StraightToStoryMode: a mods loader that serves loose files and archives from its `onigiri` folder and skips the splash and legal screens by its `onigiri.ini` (`SkipSplash` and `SkipLegal` on, `SkipIntro` off). It loads before TweaksV and patches nothing in its DllMain - at TweaksV's start every site held the game's own bytes - but patches at the game's first request for the time, after TweaksV's changes, and uses what it finds there unchecked: it faults with an access violation at its offset 0x1ea45 when RageOpenV has changed the cache check, the five RPF encryption calls or the console call, and at 0x1f2be when StraightToStoryMode has changed the splash and legal `jz` or the landing-page function; Windows' application log names `onigiri.asi` as the faulting module in every such crash, which the game's own handler does not dump. That is what a report to NVE's author needs; TweaksV cannot make another mod check its results, it can only leave those sites alone while that mod is there, and nothing of onigiri's code was read.

- **Problems on screen:** every problem at start-up is listed in one message box, the start-up summary (`ERROR_POPUP=1`, the default). A problem that comes later, such as a file in the mods folder that cannot be opened, gets a message box of its own, at most three per session; more than 40 problems at once are counted as "... and N more".

- **Scanner:** TweaksV's own search for its patterns in the running game's code (`TweaksVScanner`); the pattern parser is an altered version of ScriptHookVDotNet's (THIRD_PARTY_NOTICES.md):
  - A pattern miss is logged and returns null instead of exiting the game; so does a pattern whose site must be unique and that matches twice, because what would be written over cannot be known;
  - A malformed pattern is refused instead of throwing;
  - DIAGNOSTIC_MODE logs the address, match count and original bytes, and for a pattern that matches more than once, the bytes around each match;
  - Only the game's executable sections are searched, and only memory that can be read, so a page the game protects is skipped instead of crashing it. The search compares a pattern's two rarest bytes at 16 positions at a time and checks the whole pattern only where both match - about ten times faster than a search through the whole image byte by byte;
  - A second search, built the same way, finds every `lea` that loads one address - for a static array the game loads in places no pattern can tell apart (the box streamer's list, the decal definitions array) - and, with the `mov` stores to it, every reference to one, for an array whose patterns name its references (the modkit and packfile arrays);
  - A pattern can be asked for every match instead of the first, for a site the game repeats - the check seven decal-placing functions share (the decals part).

- **One patch module:** every patch to the game's code goes through `TweaksVPatch`, one writer for bytes, one for redirected calls and one for hooks on a function's start (MinHook, see T-HARDEN):
  - A group of writes is all or nothing: every page is made writable first, so a page that cannot be changed leaves the game as it was;
  - Every page gets its own protection back - on an exception too, and nothing that can throw runs while a page is writable - and the processor sees the new code;
  - A redirected call goes through a 16-byte jump near the game, which is written once and then only read and executed - never writable and executable at once;
  - A group of hooks is switched on together, the threads frozen once, and removed again when one of them cannot be made.

- **One pattern table:** every byte pattern TweaksV looks for is defined once, in `TweaksVPatterns.h`, under the label `PATTERNS.md` gives it:
  - A label the table does not have, or a malformed pattern, stops the build;
  - The tests check that `PATTERNS.md` lists exactly the table's patterns, and that the code uses each one once;
  - `TweaksV.log` names each pattern by its label, and `TEST_BREAK_PATTERN` (test builds only) takes a label.
  - `GTA5_Enhanced.exe` is encrypted on disk, so patterns are looked for in the running game: test builds save a copy of its code with `TEST_DUMP_CODE` - its code, constants and function table, never its data.
  - The game's archives store its scripts encrypted, so a script's code is read in the running game too: test builds save a script program as the game places it in memory with `TEST_DUMP_SCRIPT`, through the hook that the shared module `TweaksVScripts` keeps for every part that works on a script program - its three patterns, `Y-E-H1`, `Y-E-N1` and `Y-E-I1`, are looked for on every boot the Blips part is on, and by a test build with `TEST_DUMP_SCRIPT`.

- **One feature table:** `TweaksVFeatures.cpp` lists each feature once: its section of `TweaksV.ini`, the stand-alone plugins that do its job - the old ones TweaksV replaces and the ones that stay installed - and the function that starts it. DllMain starts the features from it and the conflict check takes their plugins from it, so a new feature is one entry there, plus its settings, and a new plugin one name in the entry of each part it does the job of.

- **One relocation core:** the four parts that move one of the game's static arrays - the modkit array, the packfile array, the box streamer's traversal list, the decal definitions array - describe it in a table (`TweaksVRelocation.h`: each pattern, where its match holds a reference to the array or a limit, and how the limit encodes the size) and share one implementation:
  - Every site is found and checked before anything is written: every reference must point at one array inside the game, every limit must be the expected instruction and decode to the same plausible size, and where the array's loads are found by its address (the box streamer's list, the decal definitions array) exactly as many must be found as the game has; where the patterns name the references (the modkit and packfile arrays), a scan for every `lea` and `mov` that reaches the array must find exactly those, so that a reference a game update adds cannot stay on the old, smaller array while the limits rise;
  - The new array always has its full size, as read/write data near the game, the game's own entries copied into it and the rest zero; the setting is clamped to the game's own size..that size, and a value below the game's own is reported, so that the start-up summary names the size really used;
  - Every reference and every limit, with what the part adds (a redirected call, a loop end), is written in one go, all or nothing - a part either does its whole job or leaves the game as it was;
  - DRY_RUN logs one line with what would change; DIAGNOSTIC_MODE logs every site, the value it holds and every write, in one wording for all four parts.

- **HeapAdjuster:** `[HEAP_ADJUSTER] HEAP_SIZE` (default 2000 MB) sets the game's memory heap, one immediate in its start-up code (`H-E1`):
  - The instruction is checked before the write, and the size it holds must be a whole number of MB;
  - `HEAP_SIZE` is clamped to the size found..2047 MB, with 64-bit arithmetic, and a value below the size found is reported, so that the start-up summary names the size really used; a heap that has the size asked for already is left as it is;
  - A heap of 1024 MB or more - up to 4095 MB, all the zero-extended imm32 holds, past `HEAP_SIZE`'s range too - is not the game's own (646 MB on 1.0.1158.16): another heap adjuster set it, so it is left as it is and the log says so - with NaturalVision Enhanced its heap size wins (README's "Other mods").

- **StraightToStoryMode:** one switch per screen in `[STRAIGHTTOSTORYMODE]` (`SKIP_SPLASH_SCREEN`, `SKIP_LEGAL_SCREEN`, `SKIP_LANDING_PAGE`):
  - The splash screen's `jz` (0x0D before `S-E1`) becomes a `jmp` to the same target, computed from the game's own instruction; the legal screen's 6-byte `jz` (0x0F before `S-E2`) becomes NOPs; the function the landing page's call (`S-E3`) leads to returns 0 at once;
  - The bytes are checked before writing (the splash and legal sites must hold the game's `jz`, the landing page's call must lead into the game), and with `DIAGNOSTIC_MODE` each site is logged with the bytes it holds; an already-patched screen is skipped quietly; a landing-page function hooked by another mod is left alone and reported;
  - A missing pattern skips only that screen.

- **ModkitLimit:** `[MODKIT_LIMIT] MODKITARRAY_SIZE` (default 65536) enlarges the game's array of vehicle modkit IDs - 1024 entries of 2 bytes, loaded by six `lea` (`M-E-R1..R6`) and sized by eight immediates that hold N-1, N+3 or 2N (`M-E-L1..L8`) - on the relocation core:
  - All six references must point at one array inside the game, so an array another mod has moved is left alone, and they must be every reference the game's code has to it (a scan finds no seventh); all eight limits must be the expected instruction and decode to the same plausible size;
  - The new array always has the full 65536 entries, as read/write data; the limits are clamped to the game's own size..65536, a value below the game's own reported;
  - The six references and the eight limits are written together, all or nothing.

- **PackfileLimit:** `[PACKFILE_LIMIT] PACKFILEARRAY_SIZE` (default 13000) enlarges the game's array of RPF archives - 7260 entries of 8 bytes on the current build, referenced by 33 instructions (`P-E-R01..R30`, `R32`, `R33` and, by game build, `R31a` or `R31b`) and sized by an immediate (`P-E-D3`, `D2` or `D1` by game build) and a variable the game compares an archive index against, which holds four less than the array's size (`P-E-I1`; the margin is kept) - on the relocation core, and replaces the archive count of the game's configuration:
  - All references must point at one array inside the game and be every reference the game's code has to it (a scan finds no 34th; `P-E-R32`, the live load in the function that hashes a collection's entries, and `P-E-R33`, behind a trap that is never run, came from my code dump), the limits must agree on a plausible size, and the streaming configuration call (`P-E-H1`) must lead into the game - one another mod has already redirected is left alone;
  - The call goes through a read+execute call stub to TweaksV's function, which replaces the archive count read from `gameconfig.xml` with the new size and calls the game's own function; the log says what it replaced. The count is replaced exactly, also a higher one: the game's own configuration holds 8512 on 1.0.1158.16, more than its array's 7260, so a `PACKFILEARRAY_SIZE` below 8512 lowers it;
  - The new array always has the full 65535 entries, as read/write data; the limits are clamped to the game's own size..65535, a value below the game's own reported;
  - The 33 references, the two limits and the redirected call are written together, all or nothing;
  - The game's file version chooses the patterns of its build; without one nothing is done, and the start-up summary says so.

- **BoxStreamer:** `[BOXSTREAMER] TRAVERSAL_LIST_SIZE` (default 10000). The game's box streamer keeps the map boxes one search returns in a static list of 1000 entries; with heavy map mods it fills up, and the boxes it has no room for are never streamed, so their LODs are missing. TweaksV moves the list to a larger one and raises the capacity the game hands its tree searches, on the relocation core:
  - The four capacity sites are found by pattern and must agree on the game's own size. The list's address comes from the `lea` after three of them, and the game's code is scanned for every `lea` that loads it: exactly 8 must be found (two of the game's four query functions are near-identical copies, which no pattern tells apart), so a list another mod has moved, or a game that has changed, is left alone;
  - The new list always has the full 100000 entries, as read/write data; the capacity is clamped to the game's own size..100000;
  - The 8 references and the 4 capacities are written together, all or nothing;
  - With `DIAGNOSTIC_MODE=1` the four calls to the game's tree searches go through TweaksV's call stubs to a wrapper that only counts (atomics, nothing else on the streaming thread) and logs, 10 seconds in and then every minute while the numbers change, how many searches ran, the most entries one returned and how many returned more than the game's own list could hold - the number that says whether a map load needs the larger list. A search stops 16 entries short of the capacity it is handed, so with `TRAVERSAL_LIST_SIZE` at the game's own size no search can return more than the game's own list could hold, and the summary says so. A call another mod has hooked, or a pair of calls that does not lead to the same tree search, skips the part - the one place where `DIAGNOSTIC_MODE` changes what a part does, because the measurement is why it is on; the calls are redirected in the same all-or-nothing write as the references and capacities;
  - Measured on 1.0.1158.16 with Forests of San Andreas: Revised and GTA V Remastered: Enhanced loaded, the measurement on: 180353 searches in three minutes, the largest returned 1123 entries, and 7209 returned more than the game's own list of 1000 could hold - each of those would have been cut off without the larger list. Ten minutes of driving through those forests and the city on 2.1.0, with the same mods: 946209 searches, the largest returned 1203 entries, and 24244 returned more than the game's own list could hold.

- **Decals:** `[DECALS] DECALDEFS_SIZE` (default 2048). The game keeps its decal definitions - the kinds of decal it reads from the `decals.dat` files - in a static array of 260 entries, with the number registered so far in a dword 16 bytes before it; once 260 are registered the parser drops every further definition silently, and add-on content, which comes last, loses its decals. TweaksV moves the array to a larger one and raises the limit at every site that carries it, on the relocation core:
  - The parser's "full" check gives the count's address and N (260), its `lea` the array's address, which must lie 16 bytes after the count, both inside the game. Every other site that carries the limit - 21 instructions, one pattern matching the 7 identical checks of the decal-placing functions - is found by pattern, must be the expected instruction and must hold N-1 or N; the decal manager's start-up loop must clear a whole number of entries per pass and end at its start offset + N x 80. The game's code is then scanned for every `lea` that loads the array: exactly 31 must be found, each with a 48 or 4C prefix, so an array another mod has moved, or a game that has changed, is left alone;
  - The new array always has the full 16384 entries (1.3 MB), as read/write data, the game's own entries copied in (zero at that point: the array's initial state) and the rest zero; the limit is clamped to the game's own size..16384 (a definition's index is a uint16 in the game's decal instances);
  - The 31 references and the 23 constants are written together, all or nothing; the loop end becomes a whole number of passes below the new size (the entries it leaves are zero anyway); the count stays where it is, since nothing reaches it through the array or the array through it;
  - With `DIAGNOSTIC_MODE=1` the part reads the count 10 seconds in and then every minute while it changes, and logs it against the limit and the game's own 260, with how many the game's own array would have dropped - nothing is hooked; with `DRY_RUN=1` it measures the unpatched game (without the mods folder, which RageOpenV does not serve in a dry run);
  - Measured on 1.0.1158.16 with the measurement on: vanilla registers 259 definitions - one short of the game's own 260, so a mod that adds two is already one too many. With a test `decals.dat` of 659 definitions (400 copies of a definition only a heist scene places, put first, then vanilla's 259) the part held all 659 and every decal type appeared; with the part switched off and the same file, the game's own array filled with the copies and not one bullet hole, blood splatter or tyre mark appeared - the failure the part cures, seen directly;
  - `DecalPatch.asi` counts as an old plugin for this part and the box streamer part: with it installed, both are switched off.

- **RageOpenV:** the mods folder, unencrypted (OPEN) RPF archives and the RPF cache check skip each have a switch in `[RAGEOPENV]`. The part does its work when the game first asks for the time - a hook on `GetSystemTimeAsFileTime` that runs once, shows the start-up summary and switches itself off - because the game's file system is not up in DllMain; if the game has not asked 30 seconds in, a thread reports that the start-up never ran, shows the start-up summary and switches the hook off:
  - The mods folder, in the game's current directory, normally the game folder - a game that runs in another folder while the game folder has a mods folder is reported, the two compared by their final paths, so that a short name or a junction of the game folder is the game folder: the eight file functions of the game's two file devices (`R-E-F1..F8`; two per device found at their start, two by a pattern inside them, every computed start checked with the game's unwind data) are hooked together or not at all, so that a path that exists under `mods\` is served from there. The folder is read once at start-up into a list of at most 200,000 files and folders, 32 levels deep: a folder deeper than that, and one that cannot be read, is skipped, counted and reported in the start-up summary while the rest is read, and a mods folder that cannot be read at all is reported, not called empty; its names are spelled in UTF-8, as the game's file functions take their paths on every Windows, whatever its ANSI code page (PATTERNS.md, item 5); a name that is not valid Unicode (an unpaired surrogate, which UTF-8 cannot spell), or whose path is longer than 254 bytes - the hooks hand the game `mods/` and the path, and its file functions read 259 bytes of that - is left out and counted in the log, and a folder whose list is empty hooks nothing; every call looks its path up in that list: no file system call, memory allocation or lock per call; both spellings of a path match, its letters compared as Windows compares file names, by their upper case, outside ASCII too; a path whose bytes are not UTF-8, one longer than 254 bytes, one with `..`, and one that is not relative (a leading separator, a drive), is never redirected; a file the folder does not have reaches the game's own function untouched. None of the four functions falls back to the game's own file: when a mods file cannot be opened, OpenBulk gives the game that failure, as for any file it cannot open - the player's file is never replaced behind their back - logs each such call (20,000 lines at most, then only counted) and reports the first of a session; GetFileTime, GetFileSize and GetAttributes answer for the mods file. Without a mods folder nothing is hooked (DIAGNOSTIC_MODE still checks the patterns). A function another mod has hooked is hooked on top and chains through, said in the log - for the four found by a pattern inside them, GetFileTime and GetFileSize: another mod's hook on OpenBulk or GetAttributes changes the bytes their patterns match at the start, so the mods folder is not used and the start-up summary names the pattern;
  - OPEN archives: the five calls of the archive code (`R-E-E1..E5`) are redirected through call stubs together or not at all; both DecryptHeader2 calls must lead to the same function, and a call another mod has redirected is left alone. The encryption tag is kept per thread and used up by the parse it was found for, so archives opened at the same time never mix; only an OPEN archive's entry table is walked, and only a plausible one whose bytes can be read - an OPEN archive whose table is implausible, or points at memory that cannot be read (what a field moved by a game update would do), is left as it is, logged, and reported once per session;
  - The cache check: the function it calls (`R-E-K1`), which must be a function start, gets `C3 90`; a check another mod already skipped or hooked is left alone and is not a problem. The console patch (`R-E-C1`) only with `CONSOLE=1`, and not where another mod has NOPed the call already;
  - With `DIAGNOSTIC_MODE=1` every site and write is logged, then every file request, every file served from `mods\` and every archive header read - 20,000 lines of each kind at most, then only counted - and a summary 10 seconds in, then every minute while the numbers change; off, a hook costs one comparison. A game path in a line is read as UTF-8, as the game reads it, so that a name outside ASCII comes out right and `%USERPROFILE%` stands for the profile folder in it too.

- **DirectStorage:** `[DIRECTSTORAGE]` in `TweaksV.ini` (`ENABLED`, `UNLOCK_FILES`):
  - `UNLOCK_FILES=1` (on by default) keeps the game folder's files free while the game holds them open. With DirectStorage, the game asks it to open every file in its folder at start-up, subfolders included, and DirectStorage opens each for reading while letting others only read it, and keeps it open. TweaksV hooks `NtCreateFile` at start-up and gives every open of a file in the game folder that is not `.rpf` or `.cache`, asks for reading only and already lets others read, write and delete sharing too, before it goes on to Windows - whoever opens the file: the game, DirectStorage or a mods loader. The file opens and reads as before, and other programs can write, rename and delete it while it is open; archives, write opens, exclusive opens, folders and everything outside the game folder are left as they are, and nothing is refused. The limits, both Windows' rules for a file with an open handle: Windows checks every open against every handle open on the file, so a program that opens such a file for writing while sharing nothing still gets a sharing violation while the game holds it - one that lets others read while it writes, as editors and the C runtime's file functions do, and a rename are not affected; and Windows refuses the classic rename of a new file over an open one, whatever the sharing of the handles on it, with access denied (`MoveFileEx` with `MOVEFILE_REPLACE_EXISTING`, `std::filesystem::rename`) - the usual safe way to save a settings file, and how my LuminanceV's panel saved its INI, which got access denied while the game ran (found 2026-10-26) - while a rename with POSIX semantics, `ReplaceFile`, a delete followed by a new file and a write in place go through. Since 2.4.0 the second limit holds only for programs outside the game: inside it, such a rename gets POSIX semantics (below);
  - Until 2.1.1 this part refused, in the game folder, every file the game asked DirectStorage for that was not `.rpf` or `.cache`, on the premise that the game reads only archives there. A mods loader that serves loose files breaks it: NaturalVision Enhanced's `onigiri.asi` hands the game 91 loose files through DirectStorage, and the game died in its own fatal trap 22 ms after the first refusal (`onigiri\common\data\gameconfig.xml`) - why the part frees files now instead of refusing them. Files outside the game folder were never refused: the game reads its saves and `pc_settings.bin` (`Documents\Rockstar Games\GTAV Enhanced\Profiles`) and its cloud files in `%TEMP%` through DirectStorage too, and the first build of this part, which refused every path without `.rpf` or `.cache`, made the game find no save, start the prologue and rewrite `pc_settings.bin` with defaults (the saves themselves were untouched);
  - Whether an open lies in the game folder is decided on its own name, before the call, on the stack - no memory allocation and no lock per call: a full name is compared with the game folder; a name relative to a folder handle, which is what Windows makes of a relative path, counts when that handle is the game folder's, told by its identity (the volume's serial number and the folder's file ID, one query of Windows per such open, two on a file system without file IDs); a relative open of another folder is left as it is, and a game folder whose identity cannot be read is a problem in the start-up summary, since its relative opens then stay locked. TweaksV's own opens inside its hooks are left alone. The part needs no game patterns and no DirectStorage - the files are freed whoever opens them, `dstorage.dll` loaded or not - and a hook that cannot be made is a problem in the start-up summary;
  - The replace-renames, since 2.4.0: `UNLOCK_FILES=1` hooks `NtSetInformationFile` at start-up as well, and a rename made inside the game's process - by a mod, a script or the game - that replaces what lies at its target in the game folder goes to Windows with POSIX semantics: `FileRenameInformation` with ReplaceIfExists, which `MoveFileEx` with `MOVEFILE_REPLACE_EXISTING` makes, and `FileRenameInformationEx` with replace-if-exists but without POSIX semantics, which `ReplaceFile` makes, become `FileRenameInformationEx` with replace-if-exists and POSIX semantics, the caller's other flags kept, on a copy of its buffer on the stack. So the rename goes through while the game holds the file - the game reads the file it opened until it opens it again, and the name is the new file's - and a mod's safe save works without a change of its own, my LuminanceV's panel's included. ## Open Issues

Known bugs and open issues in TweaksV.

### T-HARDEN: MinHook's trampolines are writable and executable

- **What:** MinHook, the hook library, keeps the trampolines of TweaksV's hooks in memory that is writable and executable at once, and which Control Flow Guard treats as valid call targets - in a game that turned the guard on, the one gap TweaksV would leave in it. That only helps an attack that can already write to the game's memory. The rest of the code review's hardening is done: links, the user name and the size limit of `TweaksV.log`, problems after the start-up summary, the exploit mitigations.
- **Status:** accepted. It is MinHook's own design, and `vendor\MinHook` stays unchanged; TweaksV's own stubs are never writable and executable at once.
- **When it goes:** when MinHook keeps its trampolines read and execute only, or TweaksV moves to a hook library that does.

### T-DIAG: a diagnostic aid that cannot be set up is logged, not reported

- **What:** the console (`CONSOLE=1`), DirectStorage's call logging (`DIAGNOSTIC_MODE=1`) and the measurements - `DIAGNOSTIC_MODE`'s and the `UNLOCK_FILES` summary - are aids. When one cannot be set up - the console cannot be opened or kept, a DirectStorage function cannot be hooked for the log, the game never asks for the DirectStorage factory those hooks wait on, a measurement's thread cannot start - `TweaksV.log` says so, but it is no `PROBLEM` line and no item of the start-up summary, so nothing on screen tells of it.
- **Status:** accepted. An aid is switched on for a test, by someone who reads `TweaksV.log` for what it gives - or misses the console's window - and finds the reason there, and the `UNLOCK_FILES` summary only says what the part did; the game and every part's job go on as without the aid.
- **When it goes:** when a player is meant to rely on one of these switches: then an aid that cannot be set up is reported like a job not done while its switch is on.

### T-SUMMARY: no start-up summary when its thread cannot start

- **What:** the start-up summary is shown from a thread of its own, because a message box must not block `DllMain` or the game's thread that first asks for the time. When Windows cannot start that thread, the log says so (`The start-up summary thread could not be started (Windows error N).`) and no box comes for the rest of the session: the problems of the start-up and every later one stand only in `TweaksV.log`.
- **Status:** accepted as rare: Windows refuses a new thread only in an exceptional state, and the log says what happened.
- **When it goes:** with the next change to the start-up summary (`TweaksVSummary`): the thread is tried again with the next problem reported, as a new thread is started for the next problem after a box that could not be built.

### T-FREEZE: RageOpenV's start-up writes without freezing the other threads

- **What:** the writes in `DllMain` happen while the game is still single-threaded. RageOpenV's start-up runs later, on the game's thread at its first request for the time, and writes its few bytes there - the cache check's `C3 90`, the console's NOPs, the five `E8 rel32` of the OPEN archives - without freezing the game's other threads, as MinHook does for the hooks. A thread that ran one of those instructions while it was written could execute it half old, half new.
- **Status:** accepted: no other thread runs that code at that point of the start-up. The Blips part's write after `DllMain` is not of this kind: it goes into a script program on the game's resource placement thread before the game enters the program in its registry, where no script thread can run it (PATTERNS.md, "Script programs").
- **When it goes:** when `WriteCode` freezes the game's other threads around a write made after `DllMain`, as MinHook does - at the latest when a game build runs one of those sites on another thread that early.
