# Patterns

Every byte pattern TweaksV searches for in `GTA5_Enhanced.exe`, and the game build each one was last verified on. TweaksV searches only the game's code (its executable sections). Each pattern is defined once, in the table in `source\TweaksVPatterns.h`, under the label it has here (`H-E1`, `P-E-R31a`, ...), and is written here exactly as there; `?` matches any byte. The tests check that this file and the table list the same patterns, and `TweaksV.log` names each pattern by its label. RVA is where each pattern matched on 1.0.1158.16, counted from the start of `GTA5_Enhanced.exe` in memory. What each match holds - the reference, limit, call or function - is here; what each part does with it is in [SPECIFICATIONS.md](SPECIFICATIONS.md).

The DirectStorage part uses no patterns. The hooks that do its job are on `NtCreateFile` in `ntdll.dll`, which every file open of the game passes, and on `NtSetInformationFile`, which every rename passes; what the first relies on is how the game folder's files are locked: the game asks DirectStorage to open every file in its folder at start-up, subfolders included (`Redistributables\*.cab`, `BattlEye\*`, `update\`, `x64\` - on my 2.1.1 boot 463 files in the first 10 seconds, 184 of them `.rpf` and `.cache`, 279 others), and DirectStorage opens each with `CreateFileW` for reading while letting others only read it - `NtCreateFile` with access 0x80100080 (`GENERIC_READ`, `SYNCHRONIZE`, `FILE_READ_ATTRIBUTES`), share `R--`, options 0x48 - on the thread that called `OpenFile`, right before it returns, and keeps the handle. A relative path reaches `NtCreateFile` as a name relative to the current directory's handle, which the hook tells by the folder's identity. The diagnostic aids hook `DStorageGetFactory` in `dstorage.dll` and, on the factory the game gets for the interface `{6924EA0C-C3CD-4826-B10A-F64F4ED927C1}`, its function [4], `OpenFile` (`DStorageCore.dll+0x3F9D0` with DirectStorage 1.2.2311.1405 on 1.0.1158.16) - diagnostic facts now, nothing depends on them. ### When Game Updates

1. Start the game with `DIAGNOSTIC_MODE=1` and `DRY_RUN=1` - and `CONSOLE=1`, with every part on, so every pattern is looked for, the script programs' three by the Blips part and those of the parts measured first by their modules (SPECIFICATIONS.md, section 11.10). A dry run does not redirect their call, so the Blips part sees no script program then: whether it still finds `blip_controller`'s guard shows only on a boot without `DRY_RUN`, where its line, or its problem, says so. The game is not patched then. `TweaksV.log` lists every pattern not found, by its label.
2. Check whether the project the pattern came from has changed it (`CREDITS.md` names them).
3. Update the pattern in `source\TweaksVPatterns.h` and in this file - the tests check that both agree - and confirm that it matches exactly once. `GTA5_Enhanced.exe` is encrypted on disk, so look for the code in a copy of the running game: a test build with `TEST_DUMP_CODE=60` saves one (README, Test Builds) - the file on disk shows random bytes where the patterns match in memory, because the code is decrypted only there. The game is built with clang, not MSVC: its code writes `31 C9` and `45 31 C0` for xor where MSVC writes `33 C9`, and the image has a `.retplne` section, two `.text` sections and a `.pdata` function table - so a pattern from a GTA V Legacy mod never carries over and is found anew here. To analyse a dump, rebuild it as a PE (the headers and the saved sections at their offsets, `.data` as zeros) and let Ghidra's headless analyser take it; the `.pdata` table gives the functions. Re-find each site from its anchor pattern rather than trusting its old RVA, and treat a site that moved as new findings, never a guess.
4. DirectStorage: with `DIAGNOSTIC_MODE=1` the log names the factory's functions and says why `OpenFile` cannot be logged (another interface, an `OpenFile` outside DirectStorage's DLLs) - diagnostic facts only; the part's job depends on how the files are opened (item 5).

## Decals

## Script programs

A script program is one of the game's compiled scripts - `blip_controller` and the others its archives store, encrypted - as the game holds it in memory. The shared module `TweaksVScripts` hooks the place where the game makes one and reads its layout, for every part that works on a script program: the Blips part raises `blip_controller`'s threshold in one (SPECIFICATIONS.md, section 11.9), and `TEST_DUMP_SCRIPT` in test builds saves one (section 13.3). The facts, from the dump of 1.0.1158.16, verified against it on 2026-10-27:

- **The hook point:** in the program's resource constructor (RVA 0x91B9F0), the call of the natives' resolution, an `E8 rel32` at RVA 0x91BBAB to RVA 0x91BF20, with rcx = the program: `Y-E-H1` at RVA 0x91BBA8, the call at +3.
- **The function behind it** (RVA 0x91BF20) takes the program alone and returns a byte: 1 when every native resolved, 0 when one did not; the constructor ignores it. Before the call, the program's native table holds the natives' 64-bit hashes - the constructor has rotated them back already, in the loop `Y-E-N1` matches; after it, each entry holds its handler's address, and a hash the game does not know gets the handler at RVA 0x50CB60, `CC C3` (an `int3`, then a `ret`).
- **The thread and the timing:** the constructor runs on the game's resource placement thread whenever a script program is streamed in. The program enters the game's registry of programs only after the call, and every script thread looks its program up in the registry each time it runs (a thread whose program is not there faults rather than runs it), so no thread can run the program while the hook looks at it: the window of T-FREEZE (NOTES.md) does not arise.
- **The fields,** counted from the program's start: +0x10 the code page table (8-byte pointers, one per page), +0x1C the code length in bytes (dword), +0x2C the native count (dword), +0x40 the native table (count x 8 bytes), +0x58 the name's hash (dword), +0x60 the name (a pointer to a zero-terminated string), +0x68 the string page table, +0x70 the strings' length in bytes (dword); the object is at least 0x80 bytes. `Y-E-N1` pins +0x1C and +0x40, `Y-E-I1` +0x10, and `Y-E-H1` +0x70 with the page rounding: its last bytes begin the constructor's loop over the strings' pages (`mov r14d, 0x3FFF` at RVA 0x91BBB0, `mov eax, [r12+0x70]` at 0x91BBB6, `add eax, r14d; cmp eax, 0x4000` at 0x91BBBB; the loop at 0x91BD1B to 0x91BD37, `shr eax, 14` and the page table read at +0x68); the others are on the list of "When Game Updates", item 5.
- **The pages:** 0x4000 bytes each. A length gives (length + 0x3FFF) >> 14 pages, every one full but the last, which holds length & 0x3FFF bytes (0x4000 when that is 0); the strings are paged the same way.
- **The name's hash,** the game's own function (RVA 0x91B6A0): over the name's bytes - a leading double quote skipped, the name then ending at the next one; A to Z lowered and `\` taken as `/`; each byte sign-extended - h = (h + c) * 0x401 and h ^= h >> 6, all in 32 bits; then h *= 9, h ^= h >> 11, h *= 0x8001; a result below 2 gets 2 added. `blip_controller` gives 0x80CFE974.
- **The interpreter** (RVA 0x91DD30) fetches the byte at ip through the code page table - ip >> 14 the page, ip & 0x3FFF the offset in it - and dispatches through the table at .rdata 0x2610450 over 131 opcodes, 0x00 to 0x82; a byte above 0x82 is a fatal trap. Every instruction lies within one page, except SWITCH, whose entry table it reads from the page of ip + 2, so a page's end may lie between a SWITCH's count byte and its table. The lengths are the game's own table at .rdata 0x2610C50, the dispatch table + 0x800, one byte per opcode: 0x00..0x24 1; 0x25 2; 0x26 3; 0x27 4; 0x28..0x29 5; 0x2A..0x2B 1; 0x2C 4; 0x2D 0; 0x2E 3; 0x2F..0x33 1; 0x34..0x3E 2; 0x3F 1; 0x40..0x42 2; 0x43..0x5C 3; 0x5D..0x64 4; 0x65 0; 0x66..0x67 1; 0x68..0x6B 2; 0x6C..0x82 1 - 0 for the two of variable length, ENTER (0x2D: 5 bytes and its name's, whose length is the byte at +4) and SWITCH (0x65: 2 bytes and 6 for each entry, whose count is the byte at +1).
- **The opcodes a matcher needs,** every operand of more than one byte little-endian but NATIVE's index: NOP 0x00; NOT 0x06; the signed 32-bit compares IEQ 0x08, INE 0x09, IGT 0x0A, IGE 0x0B, ILT 0x0C and ILE 0x0D; PUSH_CONST_U8 0x25, PUSH_CONST_U8_U8 0x26, PUSH_CONST_U8_U8_U8 0x27, PUSH_CONST_U32 0x28 and PUSH_CONST_F 0x29; NATIVE 0x2C (+1 the argument count << 2 | the result count, +2 the native's index, big-endian); ENTER 0x2D and LEAVE 0x2E; PUSH_CONST_S16 0x43 (signed); J 0x55 and JZ 0x56 (a signed 16-bit offset from ip + 3), and the fused IEQ_JZ to ILE_JZ 0x57 to 0x5C, which jump when their comparison is false; CALL 0x5D (a 24-bit address in the code, unsigned); PUSH_CONST_U24 0x64; SWITCH 0x65 (n entries of a 32-bit value and an unsigned 16-bit offset from the entry's end); CATCH 0x6D, THROW 0x6E and CALLINDIRECT 0x6F, whose targets are computed while the script runs; PUSH_CONST_M1 0x70 and PUSH_CONST_0 to PUSH_CONST_7 0x71 to 0x78.

## Blips

The Blips part (`TweaksVBlips`, SPECIFICATIONS.md section 11.9) has the game's own `blip_controller` script make its blips while a mod's blips fill the blip pool; its patterns are the rows at the end of this section (`L` for the pool's). The facts it rests on, from the dump of 1.0.1158.16 and from the program the switch saved at my boot of 2026-10-27, verified against both:

- **The blip pool:** 2,000 slots of 8 bytes at RVA 0x3DEBD70, its high-water mark at RVA 0x3DEFBF0; a blip's handle is (serial << 16) | index, and the pool's code bounds an index with 0x7CF.
- **The count native** (on this build its hash is 0xC802478C8862BDAD and its handler is at RVA 0x1D51F40, which starts with a jump into the game's protected code) counts the slots below the mark that hold a blip, except three: the slot whose index the dword at RVA 0x288FEF0 holds, and the slots of the handles at RVA 0x3DEB7F8 and 0x3DEB7F4, those two only while the byte at RVA 0x3DEB7F0 is set. With all 2,000 slots taken it answers 1,997 while the three name live blips, and 1,998, 1,999 or 2,000 when one or more of them names none.
- **WAIT:** on this build its hash is 0x4EDE34FBADD967A6 and its handler is at RVA 0x920EA0.
- **The guard** in `blip_controller` (on 1.0.1158.16 its code is 11,394 bytes in one page, with 55 natives and 1,469 bytes of strings), 21 bytes at 0x3FE of its code - the count native is its index 10, WAIT its index 47:

  | Offset | Bytes | Instruction |
  |---|---|---|
  | 0x3FE | `2C 01 00 0A` | NATIVE, 0 arguments, 1 result, index 10: the count |
  | 0x402 | `25 96` | PUSH_CONST_U8 150: the threshold |
  | 0x404 | `0C` | ILT |
  | 0x405 | `06` | NOT |
  | 0x406 | `56 0A 00` | JZ +10, to 0x413: the exit |
  | 0x409 | `43 D0 07` | PUSH_CONST_S16 2000 |

  It holds the script back - WAIT with 2,000, then the count again - while count >= 150, and lets it on to make a blip as soon as count < 150. Told apart by their argument and result counts alone, the guard's NATIVE is the only one with 0 arguments and 1 result that a constant push and a comparison follow.
- **The threshold** is 150, the game's own. The program holds no 240, the value some setups show, which the part leaves as it is and logs; where that comes from is open.
- **The room:** the 4 bytes 0x402..0x405 between the count's NATIVE and the JZ. - **The highest limit that still holds with the pool full** is 1,997, the count's lowest answer then: above it, the script can pass the guard with the pool full, where making a blip fails.
- **Not settled:** which of the game's two copies of the script it runs - update2.rpf's, resource version 12, or x64b.rpf's, 10. A lead: the script store is built with 12 at its +0x2C (RVA 0x13FA29D and 0x30E40). The part reads the program as the game placed it, so it does not depend on it.

The research's other two sites of the pool, the count's three slots it leaves out, have no pattern: the measurement counts the slots in use, not the count's answer.

### Siren count

<!-- [siren count] -->

The sirens per vehicle (`TweaksVSirenCount`, SPECIFICATIONS.md section 11.10.4): the game lights 20 sirens of a vehicle at most, `siren1` to `siren20`, in four layers - a siren setting holds 20 lights, a vehicle's siren state 20, its renderer and six more loops run over 20, and the bones' hierarchy has IDs for 20 sirens and their glass - and no layer holds more. A vehicle made for more sirens loads, and its bones past `siren20` are never looked up: those lights stay dark, without an error. The measurement redirects the renderer's call and looks at each model's bones; the facts it rests on:

- **The renderer** (RVA 0xE9BCB0): the vehicle lights' function (RVA 0xE15B20) calls it at RVA 0xE16F9C, once per pass of a vehicle whose sirens are on (HINT, from the data flow, not verified: the call comes only while the vehicle's +0x96B has bit 1 set and its +0x985 & 0xC0 is 0x40), with nine arguments - the vehicle in rcx, three floats in xmm1 to xmm3, a flag byte (the 5th, [rsp+0x20]), the model info (the 6th, [rsp+0x28], the same rbp the siren settings getter at RVA 0x135D220 gets right after), the skeleton (the 7th, [rsp+0x30]), a dword and the coronas' list (the 9th). Its loop runs over 20 lights by its own constant, whatever a siren setting's count of lights says, and skips a light whose bone is missing or that the vehicle's +0x860 marks broken.
- **The bone structure:** the model info's +0xB0 leads through two pointers to it - a set of 128 bits, one per bone index, at +0x00, and at +0x10 one signed byte per hierarchy ID, 644 of them (0 to 0x283): the index of that ID's bone, below 0 for none. Siren n is ID 0x88 + n, its byte at +0x98 + n (`siren1` at +0x99); its glass, `siren_glass`n, is ID 0x9C + n, at +0xAC + n (`siren_glass1` at +0xAD); n runs from 1 to 20, and the next group of IDs begins at 0xB1 - there is no ID, and no name, past `siren20` and `siren_glass20`. A bone index is a signed byte: a model names at most 128 bones to the game, 0 to 127.
- **Find-bone-by-name** (RVA 0x1C4BFF0) takes the skeleton data - the skeleton's first field - in rcx and a name in rdx, tests the bone count, a uint16 at +0x5E of the skeleton data, first, and returns the bone, whose index is a uint16 at +0x42, or 0. The game names the sirens' bones `siren1` to `siren20` and `siren_glass1` to `siren_glass20`; whether the lookup ignores case is not settled.
- **The model info** holds the hash of its name at +0x18 - the game's code compares it with `police`'s, 0x79FBB0C5; not settled beyond that, the measurement's boot confirms it - and the index of its siren setting at +0x53B, 0 for none.
- **A raise,** which no build makes, would take about 100 more sites: the siren setting's 0x5E8 bytes (its 20 lights of 0x48 bytes at +0x3C, their count at +0x5DC, its name at +0x5E0) wherever the game sizes, builds, copies and reads it, the vehicle's siren state of 0x188 bytes at its +0x1380 with its four arrays of 20, the loops over 20 - and the bones' table, whose allocation and fill were not found, and the parser's member data in `.data`, which the dump leaves out. The 32-bit masks of the siren state, of the vehicle's broken sirens and of a damage object's hidden sirens make 32 the top.

### Streaming memory

<!-- [streaming memory] -->

The resource heap the game streams the map, the props and every other streamed resource into, and the streaming allocator's budgets beside it, verified in the dump's code:

- **The heaps of the start-up** (RVA 0x1020, the function `H-E1` lies in, which runs after TweaksV's `DllMain` - `H-E1`'s patch, made there, takes effect): the game heap of `H-E1`, 646 MB (RVA 0x29A8590); a 136 MB heap carved from it (RVA 0x29B1508); and the resource heap (RVA 0x29B15D8), made by its constructor (RVA 0x13F5C0) with a page size of 8 KB and a region size asked of 1024 MB. The multi-allocator (RVA 0x29B1580), the thread's current and master allocator, has 7 slots: 0 and 4 the game heap, 5 the 136 MB heap, 1, 2, 3 and 6 the resource heap. The game's general allocation takes slot 0, the streaming allocations slots 1 and 3, so `HEAP_SIZE` sizes the game heap, never the resource heap.
- **The resource heap:** up to 32 regions, each reserved and committed in full when it is made, read/write with its last page no access, of the size asked capped at 256 MB - halved while Windows refuses it, down to 16 MB - and a page less than that for its own use; the constructor makes the first, the heap's allocate the next whenever none of its regions can serve, and its queries of its free memory and its largest block add regions until 4 MB are free. None is given back, so the number of regions is its own high-water mark, and the heap holds at most 32 x (256 MB - 8 KB), 8 GB less 256 KB. A region is a buddy allocator over 8 KB pages with 32-bit page indices and 24 orders, so a region of 1 GB fits it; in the heap's code 0x10000000 stands only at the cap's two immediates (`Q-E-R1`). The object, 0x3FF0 bytes up to the next heap: +0x1D0 the page size, +0x1D8 the region size asked, +0x1E4 the regions made (a dword, 0 to 32), and per region i < 32 its allocator at +0x1E8 + i x 0x1E0, its bookkeeping at +0x3DE8 + i x 8 and its memory at +0x3EE8 + i x 8 (0 while it is not made); a region's allocator: +0x20 its pages, +0x28 its pages in use, +0x30 + b x 8 those of memory bucket b < 16, +0x1D0 its page size, +0x1D8 its size.
- **The streaming allocator** (RVA 0x42F9E10, its vtable at RVA 0x262E100), 0x38 bytes: +0x08 and +0x18 the virtual and the physical budget, +0x10 and +0x20 what is counted against them, +0x28 and +0x30 the external virtual and physical use - +0x30 the streaming engine's bytes in the resource heap; the crash report's "Streaming Memory Occupancy" is a copy of +0x08 to +0x30 at RVA 0x42F9D90. At the streaming engine's start (RVA 0xCE5E90) the budgets come from the game's configuration, two sizes in MB beside the archive count at +0x344 that `P-E-H1`'s object carries (`ArchiveCount`, 8512): +0x34C `VirtualStreamingBuffer`, 1000 in the game's `gameconfig.xml` for PC, and +0x348 `PhysicalStreamingBuffer`, 252, each kept within the resource heap's size; every streaming update (RVA 0xCEEC10, through the reset at RVA 0xCE60A0) sets both to the heap's size. Nothing but the start writes +0x10 and +0x20, to 0, so the budget checks - the placement check at RVA 0x4DBBA0 and the allocator's own allocations - pass unless one resource is larger than the whole heap: on this build the budgets do not bind, the heap does.
- **A streamed resource refused:** when the resource heap cannot hold its chunks, or when the placement check's other condition says no - the video memory budget for streamed resources ("Texture budget" above) - the game evicts what is not required, then scene objects by priority, then population models, and when nothing more frees memory sets the byte at RVA 0x435F57D; the loader's step (RVA 0xCF0E50) then stamps the dword at RVA 0x432ACA4 with `timeGetTime()` - its thunk at RVA 0x12C880 jumps through the import slot at RVA 0x5121F0C - unless one of two of the configuration object's virtual functions (+0x28, +0x30) answers otherwise, `Q-E-S1`'s `call [rax+0x30]` and `jnz`: when the last refusal happened, not how many there were. The crash report prints it as "Is Out of memory : Yes : <ms>".
- **The system's memory** (`GlobalMemoryStatusEx`) feeds the start-up's minimum-specification checks and the graphics presets' auto-detection, no streaming size.
