# Specifications

The design of TweaksV as it is built: every module of the source, what it does, what it checks, what it writes and what it logs, so that the source can be understood, forked or built on without opening it. Four files carry the whole truth about TweaksV, each with its own job:

| File | Carries |
|---|---|
| [README.md](README.md) | the player's view: what each part does, every key of `TweaksV.ini`, building, testing, other mods |
| SPECIFICATIONS.md, this file | the design: the files, the tables, the start-up, the formats, the shared code, the mechanism of every part, the rules, the tests, how to extend it |
| [PATTERNS.md](PATTERNS.md) | the game facts: every byte pattern, what the match holds, where it matched on the current build, how the sites are encoded |
| [NOTES.md](NOTES.md) | what each part does with the checks it makes, the measurements, the open issues, the bugs found in the projects the parts derive from |

Credits and derivations are in [CREDITS.md](CREDITS.md), the notices in [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md). [SECURITY.md](SECURITY.md) says how to report a security problem and what it covers; [ROADMAP.md](ROADMAP.md) holds what I plan next and [PLAN.md](PLAN.md) the phases of a change while one is under way, a placeholder while none is. "I" in these files is the author, dachdecker369. TweaksV is GPL-3.0-only.

## 1. What TweaksV is

One ASI plugin for GTA V Enhanced, `TweaksV.asi`, loaded by an ASI loader into `GTA5_Enhanced.exe`. It does nothing in any other program. Nine parts change the running game in memory, never a file on disk: the heap size (HeapAdjuster), the modkit array (ModkitLimit), the packfile array and the archive count of the game's configuration (PackfileLimit), the box streamer's traversal list (BoxStreamer), the decal definitions array (Decals), a mods folder with unencrypted archives and the cache check (RageOpenV), the three start-up screens (StraightToStoryMode), the files DirectStorage keeps locked (DirectStorage) and the threshold up to which the game's own script makes the vanilla blips (Blips). Every part but DirectStorage, which hooks two functions of Windows and needs no pattern, finds the game's code by byte patterns, checks every site before it writes, writes all of its sites in one go or none, leaves alone what another mod has already changed, and says in the log and in one start-up message box what it could not do. With `DIAGNOSTIC_MODE=1` it also measures the limits of four parts to come before any of them changes the game - the weapons.meta files and the weapon components (WeaponLimits), the siren setting IDs and the sirens per vehicle (SirenSettings), the props per anchor of a ped (PedProps), the video memory budget for streamed resources and the streaming memory (Resources) - and writes nothing for it but one redirected call of the siren count's measurement (section 11.10).

Everything is driven by three tables - the settings, the patterns, the parts - and by shared services: the log, the start-up summary, the scanner, the patch module, the relocation core. A new part is an entry in each table plus one file of its own.

## 3. The start-up

`DllMain` runs these steps on `DLL_PROCESS_ATTACH`, inside a `try` so that no exception leaves it, and returns `TRUE` whatever happens:

1. `IsGtaVEnhanced()`: the running program's file name is `GTA5_Enhanced.exe` (case-insensitive) or nothing more happens.
2. `CreateOrUpdateIni()`: `TweaksV.ini` exists from here on (section 5).
3. `LoadSettings()`: every setting is read once; the file is let go of afterwards (section 4.1).
4. `[TWEAKSV] ENABLED=0` stops here: the file is kept, nothing else is done. Otherwise the module pins itself (`GetModuleHandleExW` with `GET_MODULE_HANDLE_EX_FLAG_PIN`): `TweaksV.asi` stays loaded until the game exits, because the game's code calls into it once hooked, and an early `FreeLibrary` would crash the game at the next hooked call. A pin that fails is reported (`TweaksV.asi could not be pinned in memory (...): an ASI loader that unloads it later would crash the game.`).
5. `CheckForConflicts()` with `CONFLICT_CHECK=1` (section 7), before the log is started, so that the header's `Features:` line says `off` for every part the check switches off.
6. `ClearLogFile()` and `WriteLogHeader()`: the log is started and its header written (section 6.2). Lines logged before this point - the settings' problems, a pin that fails, the conflict check's lines - are kept and written after the header; the console, opened next, does not show them.
7. `OpenConsole()` with `CONSOLE=1`. A test build then runs `StartCodeDump()` (section 13.2), before anything is patched, and `StartScriptDump()`, which joins the script programs' hook when `TEST_DUMP_SCRIPT` is set (section 13.3) - before the Blips part joins it at step 8, so that its copy shows a program as the game placed it.
8. `StartFeatures()`: every part that is on, in table order (section 4.3). Each part runs its whole job here, except RageOpenV, which only hooks `GetSystemTimeAsFileTime` and does its job at the game's first time request, because the game's file system is not up in `DllMain`, and DirectStorage, which hooks `NtCreateFile` here, with `UNLOCK_FILES` `NtSetInformationFile` too - and with `DIAGNOSTIC_MODE` `DStorageGetFactory`, and `OpenFile` when the game creates its factory (section 11.8) - and Blips, which joins the script programs' hook here and does its job each time the game places `blip_controller` (section 11.9). With `DIAGNOSTIC_MODE=1` the parts measured first follow, after the parts (section 11.10).
9. `ShowStartupSummaryLater()` starts the thread that shows the start-up summary (section 6.4), unless `StartFeatures` returned true because a part shows it itself later (RageOpenV, at the first time request).
10. `DllMain` returns `TRUE`, also after an exception; one that reaches its own `try` is reported (`Unexpected exception during the start-up - the rest of TweaksV is skipped this session.`) and the summary thread started, so the box names it even when the log never started.

On `DLL_PROCESS_DETACH` the log is flushed and closed (`CloseLog`), without waiting for a lock another thread may have died holding.

The game's file version comes from the version resource of the running program (`ReadGameVersion`, four 16-bit numbers; `GameVersionNumber` packs them into one number, read once, 0 when unreadable). The PackfileLimit part chooses patterns by it; the log header prints it.

## 4. The three tables

### 4.1 Settings (`TweaksVSettings.h`)

A `SettingsSection` is a section of `TweaksV.ini` and the part it belongs to: `{ name, feature }`, the feature name being the log tag and the name in the `Features:` line and the start-up summary. The sections, in file order, which is also the order the parts start in: `kTweaksVSection` (`TWEAKSV`, `TweaksV`), `kHeapSection` (`HEAP_ADJUSTER`, `HeapAdjuster`), `kModkitSection` (`MODKIT_LIMIT`, `ModkitLimit`), `kPackfileSection` (`PACKFILE_LIMIT`, `PackfileLimit`), `kBoxStreamerSection` (`BOXSTREAMER`, `BoxStreamer`), `kDecalsSection` (`DECALS`, `Decals`), `kRageOpenVSection` (`RAGEOPENV`, `RageOpenV`), `kStoryModeSection` (`STRAIGHTTOSTORYMODE`, `StraightToStoryMode`), `kDirectStorageSection` (`DIRECTSTORAGE`, `DirectStorage`), `kBlipsSection` (`BLIPS`, `Blips`); `kSections` lists them in that order.

A `Setting` is `{ section, key, kind, defaultValue, minValue, maxValue, testBuildOnly, comment }` with `kind` one of `Switch` (0 or 1), `Number` (an `int` within `minValue..maxValue`) or `Text` (test builds only, never written to the file), and `comment` the short note the default file carries after the value, empty for none. The builders `Switch(section, key, on[, comment])`, `Number(section, key, value, min, max[, comment])` and `TestText(section, key)` make the entries of `kSettings`, the one table, in the order of the default file: the keys of `[TWEAKSV]` (`ENABLED`, `LOG`, `DIAGNOSTIC_MODE`, `DRY_RUN`, `CONSOLE`, `ERROR_POPUP`, `CONFLICT_CHECK`, `VERSION` with default 3 and range 2..1000000, then the test-only `TEST_BREAK_PATTERN`, `TEST_LOG_LIMIT_KB`, `TEST_DUMP_CODE`, `TEST_DUMP_SCRIPT`), then per part `ENABLED` and its own keys: `HEAP_SIZE` 2000 (1..2047), `MODKITARRAY_SIZE` 65536 (1..65536), `PACKFILEARRAY_SIZE` 13000 (1..65535), `TRAVERSAL_LIST_SIZE` 10000 (1000..100000), `DECALDEFS_SIZE` 2048 (260..16384), `MODS_FOLDER`, `OPEN_RPF`, `SKIP_RPF_CACHE_CHECK`, `SKIP_SPLASH_SCREEN`, `SKIP_LEGAL_SCREEN`, `SKIP_LANDING_PAGE`, `UNLOCK_FILES`, all on, and `ACTIVE_BLIP_LIMIT` 1900 (150..1997). `kIniLayoutVersion` is 3 and `kIniFirstLayout` 2, the first layout with `VERSION` - its minimum - and the oldest one carried forward (section 5.3). A `static_assert` on `IniKeyCount()` pins the layout at 30 keys in the file: a new key means a new layout number. `kIniCommentColumn`, 28, is the column at which every comment of the default file starts, and a second `static_assert`, on `CommentsFitTheColumn()`, refuses a key whose `KEY=default` would reach it.

`FindSetting(section, key)` is `consteval`: it returns the table entry, and a name that is not in the table does not compile. Every part reads its settings through a named reference made that way (`kHeapSize`, `kModkitArraySize`, `kPackfileArraySize`, `kTraversalListSize`, `kDecalDefsSize`, `kModsFolder`, `kOpenRpf`, `kSkipRpfCacheCheck`, `kSkipSplashScreen`, `kSkipLegalScreen`, `kSkipLandingPage`, `kUnlockFiles`, `kActiveBlipLimit`, `kEnabled`, `kLog`, `kDiagnosticMode`, `kDryRun`, `kConsole`, `kErrorPopup`, `kConflictCheck`, `kIniVersion`, the four test keys); the functions that work on the whole table (`IsFeatureOn`, `DescribeSettings`, `DefaultIniText`, the missing-key check of section 5.3) iterate `kSettings`.

`LoadSettings()` reads every entry once through `ReadIniValue` (a build that is not the test build skips the four test keys) and keeps the values in one array; afterwards nothing reads the file again. There is no in-game panel and no reload key, by my choice: the parts patch the game before it runs, so a setting changed live would change nothing. A value is parsed by its kind: a switch accepts `1`, `0`, `true`, `false`, `yes`, `no`, `on`, `off` in any case; a number is parsed with `wcstoll`, clamped to its limits with a reported problem when it lay outside, and a value that is no number is reported and the default used; a text is kept as it is. The report lines are `TweaksV.ini: [SECTION] KEY=value is not a valid on/off value - using 1.`, `... is not a number - using 2048.` and `... is outside 260..16384 - using 16384.`. A `VERSION` above 3 is reported as a file from a newer TweaksV. The readers: `IsOn(setting)`, `GetNumber(setting)`, `GetText(setting)`, `IsDryRun()`, `IsDiagnosticMode()`; `IsFeatureOn(section)` is the section's `ENABLED` unless `DisableFeatureForSession(section)` switched the part off (the conflict check does that), `IsEnabledInIni(section)` the `ENABLED` alone; `DefaultIniText()` builds the default file from the table (section 5.4); `DescribeSettings()` builds the header's `Features:` line and one line per part with its values (section 6.2).

### 4.2 Patterns (`TweaksVPatterns.h`)

A `GamePattern` is `{ label, text }`: the label is the one PATTERNS.md gives the pattern (`H-E1`, `P-E-R31a`, `D-E-L12`, ...), the text its bytes in hex with one space between them and `?` for any byte. `kPatterns` lists every pattern once, in the order of PATTERNS.md, grouped per part with a comment that says what the group's matches hold. Two `consteval` checks run when TweaksV is compiled: `PatternsAreValid()` (every text is well-formed hex and wildcards, every label is unique) and `Pattern(label)`, the only way the code names a pattern, which returns the table entry and refuses to compile for a label that is not there. `PatternByte(pattern, index)` gives the byte a pattern holds at an index (-1 for a wildcard), so that a constant can be checked, when TweaksV is compiled, against the byte its pattern pins it with (`TweaksVScripts`, section 13.3). The `patterns` test suite checks that PATTERNS.md lists exactly the table's patterns with the same bytes, and that the code uses each one exactly once (section 14.2). The table holds 143 patterns. 1.0.1158.16 uses 140 of them (the packfile part chooses one of three direct-size patterns and one of two references by build), and the check boot (`DIAGNOSTIC_MODE=1` and `CONSOLE=1`, every part on, with or without `DRY_RUN=1`) looks for every one: the Blips part the script programs' `Y-E-H1`, `Y-E-N1` and `Y-E-I1` on every boot it is on (section 13.3) and its own `L-E-P1` and `L-E-P2` with `DIAGNOSTIC_MODE`, and the parts measured first their 46 with `DIAGNOSTIC_MODE` (section 11.10); a normal boot looks for fewer (`R-E-C1` only with `CONSOLE=1`, `R-E-F1..F8` only with a mods folder in the game's current directory or with `DIAGNOSTIC_MODE=1`, `L-E-P1`, `L-E-P2` and the 46 of the parts measured first only with `DIAGNOSTIC_MODE=1`).

### 4.3 Features (`TweaksVFeatures.cpp`)

A `Feature` is `{ section, oldPlugins[3], peerPlugins[1], start }`: the part's section (its `ENABLED` switch and its name), up to three stand-alone `.asi` files that did its job before TweaksV and that TweaksV replaces, up to one stand-alone plugin that does its job too and stays installed because another mod needs it, and the function that starts it, which returns true if the part shows the start-up summary itself later. Such a plugin is a `PeerPlugin`, `{ file, description }` - its `.asi` file and what it is, for the start-up summary - defined once as a constant and named in the entry of every part whose job it does: `kNveLoader`, `onigiri.asi`, "NaturalVision Enhanced's loader", a mods loader that skips the splash and legal screens too and patches the sites of RageOpenV and StraightToStoryMode after TweaksV (NOTES.md, "Conflicts"). `kFeatures` lists the parts in the order of `kSections` (checked by a `static_assert`):

| Part | Old plugins | Plugins that stay | Start |
|---|---|---|---|
| HeapAdjuster | `HeapAdjuster.asi`, `ZHeapAdjuster.asi` | | `InitHeapAdjuster()` |
| ModkitLimit | `ModkitLimitAdjusterEnhanced.asi` | | `InitModkitLimit()` |
| PackfileLimit | `PackfileLimitAdjusterEnhanced.asi` | | `InitPackfileLimit()` |
| BoxStreamer | `DecalPatch.asi` | | `InitBoxStreamer()` |
| Decals | `DecalPatch.asi` | | `InitDecals()` |
| RageOpenV | `RageOpenV.asi`, `OpenRPF.asi`, `OpenIV.asi` | `onigiri.asi` (`kNveLoader`) | `InitRageOpenV()`, true when its hook is on and its start-up check runs: the start-up at the first time request shows the summary (false when the hook failed or the check's thread could not be started, and `DllMain` shows it) |
| StraightToStoryMode | `StraightToStoryMode.asi` | `onigiri.asi` (`kNveLoader`) | `InitStraightToStoryMode()` |
| DirectStorage | `DirectStorageFix.asi` | | `InitDirectStorage()` |
| Blips | `BlipLimitFix.asi` | | `InitBlips()` |

`StartFeatures()` calls each start function whose part is on, each inside its own `try`: an exception ends only that part, reported as `unexpected exception - this part is skipped for this session`. `Features()` hands the table to the conflict check.

`kMeasuredFirst`, beside it, lists the parts measured first (section 11.10), one entry per limit in the order of that section's subsections: `MeasuredFirst { feature, start }`, the part's log tag and its module's `Measure<Limit>()`. It is a `std::initializer_list`, so it may be empty: a limit leaves it when its part is built - the part then gets its section and its entry of `kFeatures` - and when it is not. With `DIAGNOSTIC_MODE=1`, `StartFeatures()` starts them after the parts, each inside its own `try`: an exception ends only that measurement and is logged, not reported, since a measurement is an aid (section 12) - `DIAGNOSTIC: unexpected exception - a measurement of this part is skipped for this session.`

## 5. TweaksV.ini

### 5.1 Where it is

`GetGameFolder()` is the folder of the running program, found once from its path. `GetFallbackFolder()` is `%LOCALAPPDATA%\TweaksV`, empty when `LOCALAPPDATA` is not set. The file in use (`GetIniPathW()`): the game folder's `TweaksV.ini` if it exists, else the one in the fallback folder if that exists, else a new file - in the game folder, or in the fallback folder when the game folder cannot take it. A file in the game folder always wins; the header says when an unused copy sits in the fallback folder.

### 5.2 The own-file checks (`TweaksVFiles`)

TweaksV writes only to its own files, `TweaksV.ini`, `TweaksV.log`, `TweaksV.old.ini` and the test-build dumps, and only where each is what its path says: a plain file directly in the folder it belongs in. A link in its place could otherwise make TweaksV write to another file, which matters when the game runs as administrator. `FileFolder` says which kind of folder the file is in: `Game`, which may itself be a link (an install moved to another drive), or `Own`, TweaksV's folder in `%LOCALAPPDATA%`, which may not. `Check` refuses a file that is a reparse point, a folder, a hard link (more than one name for the same file), a file whose folder is a reparse point where that is not allowed, a file whose final path (`GetFinalPathNameByHandleW`, every link followed) is not the folder's own final path plus the name (compared case-insensitively), and a file whose attributes, folder or final path cannot be read at all. An `OwnFile` result carries the handle, the Windows error if the open failed, and `unsafe`, the reason the file is not what its path says; `ReadOnly()` tells a read-only folder (`ERROR_ACCESS_DENIED`, `ERROR_WRITE_PROTECT`) from every other failure, because a read-only game folder is normal and only logged. `FinalPathOf(path)` gives the final path of any existing file or folder the same way, empty if it cannot be read; RageOpenV compares the current directory with the game folder by it (section 11.6). `FileExists(path)` says whether a file, not a folder, is there - for the places of `TweaksV.ini`, the conflict check and DirectStorage's note on `DirectStorageFix.asi`.

- `OpenOwnFile(folder, name, where, disposition, truncate)` opens for writing with `OPEN_ALWAYS` or `CREATE_NEW`, the link itself and never its target (`FILE_FLAG_OPEN_REPARSE_POINT`), checks, deletes a file it created itself when the check fails, and empties a file that passes when asked.
- `HoldOwnFile(folder, name, where)` opens an existing file for reading without delete sharing: while the handle is open, nobody can rename, delete or replace the file or rename a folder above it, so the Win32 INI functions that open it by its path reach this very file.
- `RenameOwnFile(folder, name, newName, where)` renames through a handle on the file after the same check; a file already at the new name is replaced only when it passes the check itself, otherwise nothing is renamed.

### 5.3 Creating, updating, replacing (`TweaksVIni`)

`CreateOrUpdateIni()`:

1. An existing file (game folder first, else fallback) is held (`HoldOwnFile`); one that fails the check is reported (`TweaksV.ini (<path>) is not used: <reason>. TweaksV uses its built-in defaults this session.`) and never read.
2. A held file without the key `VERSION` under `[TWEAKSV]` has the layout of TweaksV 1.x, whatever else it holds - a 1.6.0 file, an empty or damaged one, a layout-2 file whose `VERSION` line was deleted. Only the key names of that section are read to decide; no value of such a file is ever used. The hold is released, the file renamed to `TweaksV.old.ini` through `RenameOwnFile` (an older `TweaksV.old.ini` that passes the check is replaced), the default file written in its place with `CREATE_NEW`, held, and the problem reported once: `TweaksV.ini had the layout of TweaksV 1.x. It was renamed to TweaksV.old.ini and a fresh TweaksV.ini written with the default settings - set your values again.` A file that cannot be renamed is reported in its own words every boot (`... has the layout of TweaksV 1.x and could not be renamed to TweaksV.old.ini (<reason>). Delete or rename it yourself - TweaksV uses its built-in defaults until then.`) and not read; a renamed file whose replacement cannot be written is reported once (`TweaksV.ini had the layout of TweaksV 1.x and was renamed to TweaksV.old.ini, but a fresh TweaksV.ini could not be written in <folder> (<reason>). TweaksV uses its built-in defaults this session.`), and the next boot starts without a file (step 4).
3. Any other held file gets every key of the table it is missing, written with its default through `WritePrivateProfileStringW` - without a comment: TweaksV adds none to an existing file - and logged (`TweaksV.ini: added the missing key [SECTION] KEY=value.`); a key that cannot be added is logged when the file is read-only and reported otherwise. Existing values are never changed. A file of an older layout - its `VERSION`, read as `ReadIniValue` reads a value, a number from `kIniFirstLayout`, 2, to below `kIniLayoutVersion` - is then carried forward: this layout's number is written back in the old one's place, the rest of the line - a comment after the value - as it was (the value as `GetPrivateProfileStringW` gives it, 1023 characters at most; one cut short gets the number alone), and logged, `TweaksV.ini: carried from layout 2 to layout 3 (the keys it lacked are added).`; a `VERSION` that cannot be written back is logged when the file is read-only and reported otherwise (`TweaksV.ini: VERSION=3 could not be written back (<reason>), so the file keeps VERSION=2 and is carried forward again at the next start.`). A `VERSION` that is no number, or outside that range, is left as it is for `LoadSettings` (section 4.1): no number or below 2 it is reported, above 3 it is a newer TweaksV's file.
4. No file anywhere: the default file is written in the game folder; if that fails, in the fallback folder (the folder is created) - a read-only game folder is only logged (`The game folder is read-only (...), so TweaksV.ini was created with the default settings in <folder>.`), any other reason is reported; if both fail, the built-in defaults are used and reported.

The file stays held until `ReleaseIniFile()`, which `LoadSettings()` calls once every value is read. `ReadIniValue(section, key)` reads at most 255 characters of a value through `GetPrivateProfileStringW`, cuts it at a comment - `//`, as the default file writes one, or `;` - since Windows' INI functions take everything after the `=` for the value, and trims it of spaces and tabs; nothing is read when the file is not in use. `DescribeIniLocation()` gives the header its `TweaksV.ini:` line: the path, and in parentheses whether the 1.x file was renamed and this fresh file written, whether the game folder has no file, whether this file wins over an unused copy in the fallback folder, or why the file is not used.

`DefaultIniText()` builds the file from the table: the header comment, then every section with a blank line before it and its keys in table order, each as `KEY=default` with its comment from column 28 on where it has one (`DefaultLine`), CRLF line endings. ## 6. TweaksV.log and the start-up summary

### 6.1 The log file

`WriteLog(tag, text)` appends one line, `hh:mm:ss.mmm [Tag] text`, to `TweaksV.log` and to the console when one is open. It is thread-safe (one `SRWLOCK`, held through the guard of `TweaksVLock.h`, which an exception releases too, so no failure can leave the lock taken and the next line waiting forever), lines longer than 2 KB are cut and end in `...`, and every mention of the Windows user's profile folder is written as `%USERPROFILE%` - also in its short form (`C:\Users\NAME~1`), as `%TEMP%` often has it - because logs get posted in public and that folder is usually named after the user. Lines written before the log is started (up to 1024) are kept and written after the header. The file grows to 64 MB at most; the last line then says `TweaksV.log has reached its limit of 64 MB - nothing more is written to it this session.`, and the console still gets every line.

`ClearLogFile()` starts the file each session, truncated: in the game folder through `OpenOwnFile`, else - the folder read-only, a link in the file's place, the file in use by another program - in `%LOCALAPPDATA%\TweaksV`. A read-only game folder is logged; any other reason for the fallback, and no file at all, are problems. `LOG=0` writes no file. `GetLogPathW()` is the path in use, which the message boxes print - with `LOG=0`, `(off - LOG=0)` in its place.

### 6.4 Problems and the start-up summary (`TweaksVSummary`)

`ReportFailure(tag, what)` logs `PROBLEM: <what>` under the part's tag and keeps the item (`[Tag] what`) for the start-up summary, at most 40 items, the rest counted; the list is kept under a lock held through the same guard, with the item built before the lock is taken. `ShowStartupSummary()` runs once: with nothing to show it logs nothing; otherwise, with `ERROR_POPUP=0`, it logs `Start-up summary not shown (ERROR_POPUP=0): N problem(s), see above.`, and with `ERROR_POPUP=1` it logs `Showing the start-up summary (N problem(s)).` and shows one message box, `TweaksV could not apply everything:`, with one bullet (`•`) per item, `• ... and N more.` when items were dropped, the line `The game continues without the affected parts. Details are in TweaksV.log:` with the path on the next line (`(off - LOG=0)` with `LOG=0`), and `To stop this message, set ERROR_POPUP=0 in TweaksV.ini.` `ShowStartupSummaryLater()` does that from a thread of its own, which holds a reference to the module while it runs, because a message box must not block `DllMain` or the game's thread that first asks for the time. `StartModuleThread(thread, what)` starts such a thread - this one, the one for problems after the summary (below), RageOpenV's start-up check, DirectStorage's checks and its `OpenFile` summary, and the measurements' threads (section 6.6), which never end and keep it - with the extra reference to the module, which the thread drops when it ends; one that cannot start is logged, `The <what> thread could not be started (Windows error N).`; when that is the start-up summary's own thread, every problem of the session stays in the log alone (NOTES.md, T-SUMMARY). Both threads of this module run inside a `try`: a box that cannot be built is logged (`Unexpected exception while showing the start-up summary - the box is not shown; the problems are logged above.`) and skipped, and the next late problem starts a new thread.

A problem reported after the summary was shown - a part that stops working later, such as a file in the mods folder that RageOpenV cannot open - is shown by a thread of its own a second later, with the heading `TweaksV: a part stopped working after the start-up:`, at most three such boxes per session, a list of more than 40 ending in `• ... and N more.`; after that, and with `ERROR_POPUP=0`, such problems are only logged. Test builds show no box while the environment variable `TWEAKSV_TEST_NO_BOXES` is `1` and log `TEST BUILD: message box not shown (TWEAKSV_TEST_NO_BOXES=1): <heading>` instead, so the test suites never wait on one.

### 6.5 The console

`CONSOLE=1` opens a console window (`AllocConsole`) once the header is written, and it mirrors every log line from `Console opened (CONSOLE=1).` on; the RageOpenV part then NOPs the game's call that would hide it (section 11.6). The console is a testing aid: when it cannot be opened or kept, the log says so and nothing is reported.

### 6.6 The measurements (`TweaksVMeasure`)

`DIAGNOSTIC_MODE`'s five measurements of the parts - the box streamer's searches, the decal definitions registered, RageOpenV's file requests and archive headers, DirectStorage's opens in the game folder, the blip pool's slots in use - the seven of the parts measured first (section 11.10) and DirectStorage's `UNLOCK_FILES` summary share one loop. A part describes its measurement as a `Measurement { thread, firstMs, numbers, summary, start }` - the thread's name, when the first summary comes, a function whose number changes whenever the summary has something new to say, the function that writes the summary, given that number, and, if given, an event the part sets at the first thing it counts, which the thread waits for before `firstMs` begin, so that a hook never starts a thread itself (the `UNLOCK_FILES` summary, 10 seconds after the first open counted; an event that could not be made starts the clock at once) - and starts it with `StartMeasurement`, which starts its thread through `StartModuleThread` (section 6.4); the thread never ends, so it keeps its reference to the module. The thread writes the first summary `firstMs` in - `kFirstSummaryMs`, 10 seconds, or `kSummaryEveryMs`, a minute, for DirectStorage's open summary - always, and then one every minute while the number changes - in a test build every `TWEAKSV_TEST_SUMMARY_MS` milliseconds when that is set (section 13.1) - inside a `try`, so nothing leaves the thread. A measurement whose thread cannot start is logged (`The box streamer summary thread could not be started (Windows error 8).`, the names being `box streamer summary`, `decal definitions summary`, `RageOpenV summary`, `DirectStorage open summary`, `UNLOCK_FILES summary` and `blip pool summary`, and for the parts measured first `weapon infos summary`, `weapon components summary`, `siren settings summary`, `siren count summary`, `ped props summary`, `texture budget summary` and `streaming memory summary`), not reported: it is an aid that changes nothing in the game (section 12). `kMaxLinesPerKind`, 20,000, is the cap of every kind of line that comes per event (section 12).

## 7. The conflict check (`TweaksVConflicts`)

`CheckForConflicts()` looks in the game folder and its `scripts` and `plugins` subfolders - the three places an ASI loader loads from, `kLoaderFolders` in `TweaksVConflicts.h`, which DirectStorage's look for `DirectStorageFix.asi` uses too - for every old plugin and every plugin that stays of every feature (section 4.3). An old plugin found switches its part off for the session (`DisableFeatureForSession`) and is reported: `Old plugin found: <path>. TweaksV's <Feature> part is switched off for this session so nothing is patched twice. Delete the old file - TweaksV replaces it.` `DecalPatch.asi` is the old plugin of two parts and switches both off. A plugin that stays does the same while its part is on in `TweaksV.ini` - `IsEnabledInIni`, not `IsFeatureOn`, so that an old plugin found before it, which switched the part off already, does not keep it from being said - and is reported in words of its own, with the switch that stops the message: `<path> is installed and does this job too (<description>): TweaksV's <Feature> part is switched off while it is there, so nothing is patched twice. To stop this message, set ENABLED=0 under [<SECTION>] in TweaksV.ini.` `onigiri.asi` is the plugin that stays of two parts and reports both, `RageOpenV` under `[RAGEOPENV]` and `StraightToStoryMode` under `[STRAIGHTTOSTORYMODE]`; a part already off in `TweaksV.ini` gets no item, only a line in the log, not a problem: `Conflict check: <path> is installed; TweaksV's <Feature> part is off in TweaksV.ini already.` With no file of either kind found the log says `Conflict check: none of the plugins that do the job of one of TweaksV's parts were found.`; when a plugin that stays is found next to parts that are all off, its lines are written instead, so the log always shows what the check found. `IsInsideGameImage(p)` is the shared test for an address inside `GTA5_Enhanced.exe`'s image, from its PE headers read once.

## 8. The scanner (`TweaksVScanner`)

The scanner finds TweaksV's patterns in the running game's code. `GTA5_Enhanced.exe` is encrypted on disk, so the code is only readable in memory, and a game update changes it: what the scanner finds is the one thing that must be maintained after an update (PATTERNS.md, "When Game Updates").

- The image is read once: `GTA5_Enhanced.exe`'s base and size from the module information, its executable sections from the PE headers (read only where they lie inside the image; with no executable section the whole image is searched).
- Every search reads the readable parts of those sections afresh (`ReadableCode`: `VirtualQuery` over each section, committed and readable pages only, neighbouring regions joined), because TweaksV itself changes protections between two searches and a page the game protects must be skipped, not crash the game.
- A pattern's text is parsed into bytes and a mask (`ParsePattern`: tokens of exactly two hex digits, or `?`; any other token, or a text of wildcards only, refuses the pattern - nothing in the parser can throw - logged as `Pattern <label> is not valid (treated as not found): <text>`), and compiled with the positions of its two rarest fixed bytes, rarest by how often each byte occurs in the first 256 KB of the game's code (`ByteCounts`, read once). This only changes how fast the search is, never what it finds.
- `FindIn` compares those two bytes at 16 positions at a time with SSE2 and checks the whole pattern only where both match; a match must lie wholly inside one readable range.
- `Scanner::Find(pattern)` returns the one match or `nullptr`: it asks `FindAll(pattern, 2)`, and a pattern that matches twice is not used, because what would be written over cannot be known - logged as `Pattern <label> matches 2 or more times - not used (the site must be unique).`, and the part gives its `<label> was not found.` as for a miss (the heap, the three screens, RageOpenV's patterns); `Scanner::FindAll(pattern, limit)` returns every match in address order up to `limit` (a site the game must have exactly n times is asked for n + 1, so that an n + 1th match shows); both log a miss as `Pattern <label> not found: <bytes>` and, with `DIAGNOSTIC_MODE`, the line of section 6.3 with the RVA, the number of matches (exact up to 99, `100+` from 100 on) and the bytes of the match, 32 at most, plus one line for each of the first ten matches with 16 bytes before and 48 from its start, for a pattern that matches more than once, so that a longer pattern can be chosen that matches only the place it is meant for. The scanner's tag is `[Scanner]`.
- `Scanner::FindRipRelativeLeas(target, limit)` finds every `lea r64, [rip+disp32]` (a REX prefix with the W bit, opcode `8D`, ModRM mod 00 r/m 101: 7 bytes) in the readable code whose displacement leads to `target`, in address order up to `limit`, with the same 16-at-a-time comparison on the opcode and ModRM bytes. It is how the relocation core finds the loads of an array the game loads in places no pattern can tell apart. `Scanner::FindRipRelativeReferences(target, limit)` is the same search for every `lea r64, [rip+disp32]` and every `mov [rip+disp32], r64` (the same prefix and ModRM, opcode `8D` or `89`), one helper behind both: how the core checks that the references an array's patterns name are all the game has. Nothing is logged.
- `Scanner::FindCallsTo(target, limit)` finds every `call rel32` (`E8` and a rel32: 5 bytes) in the readable code that leads to `target`, in address order up to `limit`, with the same 16-at-a-time comparison on two bytes: the opcode, and the rel32's lowest byte, which a call at p must hold as the lowest byte of target - (p + 5), so that over 16 positions in a row those bytes count down by one; the whole rel32 is compared only where both match. It is how the ped props' measurement checks that the game calls a function exactly as often as the research found (section 11.10.5). Nothing is logged.
- Test builds: `TEST_BREAK_PATTERN=<label>` makes that pattern count as not found (`TEST BUILD: pattern <label> is treated as not found (TEST_BREAK_PATTERN).`), to watch its part be skipped cleanly.

The pattern parser is an altered version of ScriptHookVDotNet's memory scanner (THIRD_PARTY_NOTICES.md); the search is TweaksV's own.

## 9. The patch module (`TweaksVPatch`)

Every change to the game's code goes through this module, so that every part writes the same way and no part has to know about page protection, `DRY_RUN` or `DIAGNOSTIC_MODE`.

- **`WriteCode(writes, tag)`**: `writes` is a list of `CodeWrite { address, bytes, what }`. A write without address or bytes stops everything. With `DRY_RUN` nothing is written and each write is logged as `DRY_RUN: would patch the <what>: <old> -> <new>`. Otherwise every page any write touches is made writable first (`PAGE_EXECUTE_READWRITE` for a page that was executable, `PAGE_READWRITE` otherwise; a page that is already writable is left; a page that is not committed memory, a guard page, or one `VirtualProtect` refuses stops everything before a byte is written, with the protections changed so far put back, and the reason logged), then all bytes are written, then every page gets its own protection back, newest first - through a guard that runs on every exit, an exception included; nothing that can throw runs while a page is writable, so the old bytes for the log are read before and the lines written after - and `FlushInstructionCache` makes the processor see the new code; with `DIAGNOSTIC_MODE` each write is logged as `DIAGNOSTIC: <what> at <address>: <old> -> <new>`. False means nothing was written. `BytesOf(value)` gives the bytes of a value for a write.
- **`RedirectCalls(redirects, alsoWrite, tag)`**: `redirects` is a list of `CallRedirect { site, function, what, original }`, each a 5-byte relative call (`E8 rel32`) in the game to send to `function`; `original`, when given, receives the function the call led to, and is set before the call is rewritten, so a hook that calls it is ready the moment it can run. A site that is not a call stops everything. With `DRY_RUN` each is logged as `DRY_RUN: would redirect the <what> at RVA ...` and only `WriteCode(alsoWrite)` runs, which writes nothing either. Otherwise: a block of 16 bytes per call is allocated near the game (`AllocateNearGame`, read/write), each stub written as `FF 25 00 00 00 00` followed by the 8-byte address of `function` and two `CC`, the block made read+execute and never changed again (a call stub is never writable and executable at once), and then, in one `WriteCode`, every call's rel32 pointed at its stub together with `alsoWrite`. A call reaches only 2 GB, which is why the stubs sit near the game; a stub out of reach, no memory near the game, or a block that cannot be made read+execute stops everything with nothing changed.
- **`HookFunctions(hooks, tag)`** hooks functions at their start with MinHook: `FunctionHook { function, hook, original, what }`; every hook is created and queued, then all are switched on together (`MH_ApplyQueued`: the threads are frozen once per group, not once per hook); if any step fails, the hooks made so far are removed again and the reason logged: `<what> could not be hooked (MinHook: <status>)` when a hook cannot be created or queued, `The N hooks could not be switched on (MinHook: <status>)` when they cannot be applied, with ` - none of the N hooks is on.` for a group of more than one. `original` receives MinHook's trampoline. **`HookExport(module, function, hook, original, target, tag)`** hooks an exported function of a loaded DLL at once (`GetSystemTimeAsFileTime`, DirectStorage's exports, `NtCreateFile`, `NtSetInformationFile`) and hands back its address in `target`; **`DisableHook(function, tag)`** switches a hook off again, the function's own bytes back and the trampoline kept for a thread that is inside the hook right now. MinHook is initialised on first use; its trampolines are writable and executable, an accepted open issue (NOTES.md, T-HARDEN).
- **`AllocateNearGame(size)`**: `size` bytes, read/write, committed and zeroed, within 1 GB below the game's image, where a rel32 in the game's code reaches: the free regions below the image are walked by allocation granularity, as MinHook's own allocator does, and the first that gives `size` bytes is taken. For the moved arrays and the call stubs.
- The readers: `CallTarget(site)` (the target of an `E8 rel32`, or `nullptr`), `Rel32Target(address)` (where a rel32 or a rip-relative disp32 at that address leads), `StartsWithJump(address)` (`E9`, `EB` or `FF 25`: the usual sign of another mod's hook), `IsFunctionStart(address, detail)` (the game's unwind data, asked of Windows with `RtlLookupFunctionEntry`, says so - `a function start (unwind data)`; an address inside a function gives `inside the function at RVA ... (unwind data)`; for code without unwind data the byte before it, read only where it is readable (`no unwind data, the byte before it cannot be read`), must be `CC`, `90` or `C3` - `no unwind data, byte before it CC`), `IsReadable(address, size)` (committed, readable, no guard page, over the whole range; used before any byte outside a pattern's match is read), `CopyMemorySafely(target, source, size)` (a copy that catches an access violation and returns false - nothing else is caught - for memory that may change or be freed between a check and the read: the pointers the game's DirectStorage calls hand the DirectStorage part's hooks, the game's heap data a measurement walks while the game changes it, section 11.10), `DescribeAddress`, `HexBytes`.

## 10. The relocation core (`TweaksVRelocation`)

Four parts move one of the game's static arrays to a larger one and raise the limit the game's code carries for it: the modkit array, the packfile array, the box streamer's traversal list, the decal definitions array. They describe their array in tables; the core does the work once for all of them.

### 10.1 The tables

- `ReferenceSite { offset, opcode, opcodeSize }`: where a match holds the rel32 of a `lea r64, [rip+disp32]` or of a rip-relative `mov` that addresses the array, so that the array is the address after the rel32 plus its value; `opcode` are bytes the instruction must start with, right before the rel32, or none.
- `LimitSite { kind, offset, opcode, opcodeSize, valueOffset, mul, add }`: `Immediate`, an imm32 at `valueOffset` that holds `N x mul + add` with N the array's size, or `Variable`, the rel32 at `valueOffset` of a variable the game compares against, which holds `N + add`; `offset` is the instruction, `opcode` its first bytes, or none.
- `Anchor { pattern, matches, hasReference, reference, limitCount, limits[3] }`: a pattern of the part, how often it must match (1, or more for a site the game repeats), and what every match holds: a reference, up to three limits, both, or neither - a site the part reads itself through the plan. The builders: `Rel32(offset, opcode, opcodeSize)`, `Imm32(imm32, mul, add)`, `Imm32(instruction, opcode, opcodeSize, imm32, mul, add)`, `Variable(rel32, add)`, `Site(pattern)`, `Reference(pattern, site)`, `Limit(pattern, site)`, `Limits(pattern, matches, a, b[, c])`, `Repeated(pattern, matches, limit)`, `ReferenceAndLimit(pattern, ref, limit)`.
- `RelocationSpec { tag, name, sizeName, job, entrySize, maxEntries, setting, anchors, scannedReferences, leaPrefixes, leaPrefixCount, expectedReferences }`: the part's log tag, the array's name for the log (`modkit array`, `box streamer's traversal list`), the name of its size (`modkit list size`), the start of every failure line (`The modkit limit is not changed`), the bytes per entry, the new array's size (always allocated in full, and the setting's maximum), the setting that asks for the size, the anchors, for an array whose loads no pattern can tell apart exactly how many `lea` must load it, found by its address, with the REX bytes they may start with (`48` or `4C` for the decals; any with REX.W for the box streamer), and for an array moved by its anchors' references how many references the game's code has to it (`expectedReferences`: 6 for the modkit array, 33 for the packfile array; 0, not checked, for the other two).
- `RelocationPlan { array, gameSize, size, matches, references, limits }`: what was found: the game's own array, its size, the size to use, every anchor's matches (for the sites a part reads itself), the rel32 fields that are moved, the limits as `FoundLimit { value, mul, add }`.

### 10.2 `FindRelocation(spec, plan)`

Everything is found and checked before anything is written, and the first failure reports `<job> this session: <why>` and leaves the game as it is. A spec whose tables name no reference, or no limit, is refused as the part's own mistake. The anchors are worked through in table order - each one's matches, then for each match its reference and its limits - so a missing pattern late in the table is reported only after the sites before it passed:

1. The anchor must match exactly as often as it says (`FindAll` asks for one more): `<label> was not found.` or `the game code holds <label> N [or more] times, not the expected M.` (` or more` when more were found than expected).
2. Its reference: the instruction is readable and starts with the opcode when one is given (`is not the expected instruction (<bytes>)`); its target is logged with `DIAGNOSTIC_MODE` (`DIAGNOSTIC: reference at RVA ... -> RVA ... (<label>)`); the first reference's target must lie inside the game (`the <array> is not inside the game: <address> (another mod may have moved it already).`), every other must point at the same address (`the references to the <array> do not all point to the game's own array: <a> and <b> (<label>).`).
3. Its limits: readable, the expected instruction; a variable must lie inside the game; its value decodes to N through its encoding (`holds V, which is <encoding> for no size` when it does not divide), logged as `DIAGNOSTIC: limit[ variable] at RVA ... holds V (<encoding>, <label>) -> game size N`; the first size decoded in the whole job must be plausible (`the game's own <sizeName>, N, is not plausible.` beyond `maxEntries` or zero), every other must agree (`the limits of the <array> disagree about the game's own size: A and B (<label>).`).

Then:

4. The array is logged: `DIAGNOSTIC: the <array> is at RVA ... - N entries of E bytes`.
5. The references that are moved: the anchors' references, or - with `scannedReferences` - every `lea` that loads the array (`FindRipRelativeLeas`, each logged as `DIAGNOSTIC: reference at RVA ... -> RVA ... (lea scan)`), which must be exactly that many (`the game code loads the <array> in N [or more] places, not the expected M (another mod may have moved some of them, or the game has changed).`) and each start with an allowed prefix (`the load of the <array> at RVA ... is not a "lea r64, [rip+disp32]" with a 48 or 4C prefix: <7 bytes>.`).
6. With `expectedReferences`, the anchors' references must be every one the game has, because one no pattern names would keep the game's own, smaller array while the limits are raised: `FindRipRelativeReferences` (each site logged with `DIAGNOSTIC_MODE` as `DIAGNOSTIC: reference at RVA ... -> RVA ... (scan)`, the RVA of its rel32, as the anchors' lines have it) must find exactly that many (`the game code holds N [or more] references to the <array>, not the expected M (another mod may have moved some of them, or the game has changed).`), and every one must be an anchor's rel32 (`the reference to the <array> at RVA ... is not one its patterns name (another mod may have moved some of them, or the game has changed).`).
7. The size to use: the setting, clamped to the game's own size..`maxEntries`, reported when it lay outside (`TweaksV.ini: <KEY>=x is outside A..B - using C.`, `ReportFailure`), so that the start-up summary names the size really used - the settings' own report (section 4.1) names only the table's limits. Smaller than the game's own would shrink the array.

### 10.3 `ApplyRelocation(spec, plan, alsoWrite, redirects, also)`

With `DRY_RUN`: `DRY_RUN: would move the <array> (N references) and raise its limit from A to B (M sites)<also>.` and nothing else. Otherwise the game's own entries must be readable (`the game's own <array> cannot be read.`), the new array is allocated in full (`entrySize x maxEntries`, `AllocateNearGame`; `the new <array> could not be allocated near the game.` when that fails) and the game's own entries are copied into it, the rest staying zero - so an array the image initialises keeps its content - every reference's rel32 is recomputed for it with the int32 distance check (`the new <array> is out of reach of the game code at RVA ...`), every limit is re-encoded for the new size (`N x mul + add`), the part's own writes are added, and all of it is written in one `WriteCode` - or, when the part redirects calls too, one `RedirectCalls` - all or nothing (`the game code could not be changed (details in TweaksV.log).` when not). Then `The <array> moved and its limit raised from A to B entries.` The write lines carry `<array> reference` and `<array> limit` as their `what`.

What does not fit the core stays in the part's file and uses the plan: the packfile's hooked call, the box streamer's counted calls, the decals' count, loop and measurement (section 11).

## 11. The parts

Each part reads its switches once, at its start-up (RageOpenV's runs inside its one-shot time hook); the hooks that run per call never read them. ### 11.1 HeapAdjuster (`InitHeapAdjuster`)

The game sizes its memory heap with one immediate in its start-up code: the imm32 of a `mov edx, imm32` that `H-E1` matches, the size in bytes at +1. `HEAP_SIZE` in MB, 1..2047 - the most whole MB that imm32 holds as a positive int32. ### 11.8 DirectStorage (`InitDirectStorage`)

With DirectStorage, the game asks it to open every file in the game folder at start-up, subfolders included (`IDStorageFactory::OpenFile`), and DirectStorage opens each with `CreateFileW` for reading while letting others only read it (`NtCreateFile` with access 0x80100080, share `R--`, options 0x48) and keeps it open, so mods cannot write their own files there and scripts cannot be reloaded while the game runs. The part uses no game pattern, and its job needs no DirectStorage: it hooks `NtCreateFile` in `ntdll.dll` and decides every open by its own name, access and sharing, and with `UNLOCK_FILES` `NtSetInformationFile` as well, deciding every rename that replaces a file by its target, whoever makes them. With `UNLOCK_FILES=0` and `DIAGNOSTIC_MODE=0` it does nothing (`UNLOCK_FILES=0 and DIAGNOSTIC_MODE=0 - nothing to do.`). It logs the versions of `dstorage.dll` and `dstoragecore.dll` in the game folder and whether `dstorage.dll` is loaded (`dstorage.dll <version>, dstoragecore.dll <version>; dstorage.dll is loaded.`, a version being four numbers, `not found` or `unknown version`), as information. With `CONFLICT_CHECK=0`, an installed `DirectStorageFix.asi` is noted (`Note: <path> is installed as well - it changes DirectStorage's file opens, too.`). With `DRY_RUN` one "would" line per hook of a job that is on and nothing else: `DRY_RUN: would hook NtCreateFile so that the game folder's other files are opened with write and delete sharing (UNLOCK_FILES).` and `DRY_RUN: would hook NtSetInformationFile so that a rename inside the game that replaces a file in the game folder gets POSIX semantics (UNLOCK_FILES).`, and with `DIAGNOSTIC_MODE` `DRY_RUN: would hook dstorage.dll to log the game's DirectStorage calls.` and `DRY_RUN: would hook NtCreateFile to log the opens in the game folder.`

- `NtCreateFile` is hooked at the start-up (`HookExport`) whenever `UNLOCK_FILES` or `DIAGNOSTIC_MODE` is on, one hook for both jobs, `dstorage.dll` loaded or not: `UNLOCK_FILES: NtCreateFile is hooked - a read-only open of a file in the game folder other than .rpf and .cache that shares reading gets write and delete sharing too, so those files stay free for other programs.` A hook that cannot be made is a problem of the start-up summary with `UNLOCK_FILES` (`The files in the game folder are not unlocked this session: NtCreateFile could not be hooked (details in TweaksV.log).`), and `HookExport`'s line alone with `DIAGNOSTIC_MODE` alone.
- With `UNLOCK_FILES`, `CheckOpen` decides before the call, on the stack - no memory allocation, no lock of TweaksV's, nothing that can throw - every field of the call read within the length it gives, under a guard that catches a bad pointer; an open made on a thread that is inside one of TweaksV's hooks (`t_inside`) is not examined. Where the open lies: a name `\??\C:\...` (`\??\UNC\server\share\...` for a game folder on a network share) is compared with the game folder, letters in ASCII case - below it, the game folder itself, or outside, a sibling folder whose name starts with the game folder's and every other spelling (a device, `\Device\...`) among the outside; a name relative to a folder handle, which is what Windows makes of every relative path that lies in the current directory, lies below the game folder when that handle is the game folder's, told by its identity - `FileIdInformation`'s volume serial number and 128-bit file ID, on a file system without them `FileInternalInformation`'s 64-bit file number with `FileFsVolumeInformation`'s serial number, queries that need no access to the handle (the current directory's is opened for traversing only, which `GetFileInformationByHandle` is refused) and leave the caller's last error alone; the game folder's is read once before the hook is made, the handle's asked of Windows once per such open, twice on a file system without file IDs. An open relative to another folder, an open by file ID (`FILE_OPEN_BY_FILE_ID`) and a name that cannot be read cannot be examined. An open in the game folder is then, in this order: a directory (`FILE_DIRECTORY_FILE`, or the game folder itself; a folder opened without the flag cannot be told from a file before the call), an archive (the last name's extension - from its last `.` that is not its first letter, up to a `:` that starts a stream, so that `x.rpf::$DATA` is the archive - `.rpf` or `.cache` in any case), a write open (asking for `GENERIC_WRITE`, `GENERIC_ALL`, `MAXIMUM_ALLOWED`, `DELETE`, `FILE_WRITE_DATA`, `FILE_APPEND_DATA`, `FILE_WRITE_EA`, `FILE_WRITE_ATTRIBUTES`, `WRITE_DAC` or `WRITE_OWNER`), an exclusive open (its sharing leaves out `FILE_SHARE_READ`), and otherwise an open that gets `FILE_SHARE_WRITE` and `FILE_SHARE_DELETE` added before the call goes on to Windows. Every other open goes on untouched. Windows decides sharing per handle: a new open succeeds only if its access fits the sharing of every handle open on the file and its own sharing allows every such handle's access, so a program that opens a widened file for writing while sharing nothing still gets a sharing violation while the game holds it - the first limit README.md states. The second is Windows' rule for a rename: a file with an open handle, whatever that handle's sharing, cannot be replaced by a classic rename (`FileRenameInformation` with ReplaceIfExists, what `MoveFileEx` makes of `MOVEFILE_REPLACE_EXISTING`), which fails with access denied, while a rename with POSIX semantics (`FileRenameInformationEx` with `FILE_RENAME_POSIX_SEMANTICS`), `ReplaceFile`, a delete followed by a new file and a write in place go through - for a program outside the game's process; inside it, the `NtSetInformationFile` hook below gives a classic replace-rename POSIX semantics. A game folder whose identity cannot be read is a problem, since no relative open - nor a rename's name relative to a folder handle - can then be told to lie in it: `Files in the game folder opened by a relative path are not unlocked this session: the game folder's file ID could not be read (<error>).`
- Every examined open is counted after the call in exactly one of six counts, with atomics, whatever its result: widened, archives, write opens, exclusive opens, directories, not examinable; an open outside the game folder is not counted; every replace-rename into the game folder is counted in exactly one of three counts, whatever its result: given POSIX semantics, made again as the caller made it, passed on with a name too long. A widened open's file is told apart by a hash of its path below the game folder (FNV-1a over its letters, ASCII in lower case, up to a stream) in a fixed table of 16,384 slots that the threads fill without a lock or an allocation, 8,192 files at most; the type of each new file, its extension with the dot in lower case (`(none)` without one), is counted in a fixed table of 15 types in the order they come, a type past the 15th or one that does not fit 8 bytes counting as `others`. The summary is a measurement (section 6.6) whose thread starts with the hooks and waits for an event they set at the first open or rename they count, so that it comes 10 seconds after it, then every minute while the sum of the counts changes, each count read once: `UNLOCK_FILES: in its first 10 seconds, N opens of M files in the game folder other than .rpf and .cache were given write and delete sharing, so those files stay free for other programs; by type: .txt 4, .asi 1, (none) 1, others 1; left as they were: A opens of archives, B write opens, C exclusive opens, D directories, E whose path could not be examined; replace-renames into the game folder: R given POSIX semantics, F made again as the caller made them where the file system refused that, P passed on as made, their names longer than 1024 characters.` - `so far` in place of `in its first 10 seconds` later, `more than M files` once the table of files is full, no types while there are none. Without `DIAGNOSTIC_MODE` no line per open is written.
- With `UNLOCK_FILES`, `NtSetInformationFile` is hooked at the start-up too (`HookExport`), right after `NtCreateFile` and also when that hook could not be made: `UNLOCK_FILES: NtSetInformationFile is hooked - a rename inside the game that replaces a file in the game folder gets POSIX semantics, so it goes through while the game holds that file open.` A hook that cannot be made is a problem of the start-up summary: `The replace-renames into the game folder are not given POSIX semantics this session: NtSetInformationFile could not be hooked (details in TweaksV.log).` With `DIAGNOSTIC_MODE` alone it is not made. Windows refuses the classic rename of a new file over one that somebody holds open, whatever the sharing of the handles on it, with access denied; with POSIX semantics the rename goes through as long as every handle on that file shares deleting, which `CheckOpen` gives the game's opens - the holders go on reading the file they opened, and the name is the new file's. The hook passes every information class but the two renames, `FileRenameInformation` (10) and `FileRenameInformationEx` (65), on at once, the class compared and nothing read, and so it passes every call made on a thread inside one of TweaksV's hooks (`t_inside`). For a rename, `CheckRename` decides before the call, on the stack - no memory allocation, no lock of TweaksV's, nothing that can throw, the caller's last error kept: under the guard against a bad pointer, a buffer of at least 24 bytes, `FILE_RENAME_INFORMATION`'s size, gives its flags - `FileRenameInformation`'s ReplaceIfExists their first byte - the folder handle and the name's length, and a name that is not empty, of even length and within the buffer is copied into a `FILE_RENAME_INFORMATION` on the stack when it has 1024 characters at most; a buffer Windows refuses itself goes on as made. A replace-rename - ReplaceIfExists set, or `FILE_RENAME_REPLACE_IF_EXISTS` without `FILE_RENAME_POSIX_SEMANTICS` - is examined on the copy, so that what is examined is what goes to Windows; every other rename goes on as made. Its target lies in the game folder when its name is relative to a folder handle that is the game folder's - told by its identity as for an open, one query, two on a file system without file IDs - and does not start with `\`; when its full name lies below the game folder, compared as an open's; and when it is a bare name - no folder handle, no leading `\`, a rename inside the source's own folder for Windows - whose source lies below the game folder: the source's object name (`NtQueryObject`, `\Device\HarddiskVolume3\...`), one query into a stack buffer of 1024 characters, compared with the game folder's object name read the same way at the start-up, letters in ASCII case - not its final path (`GetFinalPathNameByHandleW`), which would allocate, take locks and ask the mount manager inside the hook, so a source opened by a short 8.3 path goes on as made. A bare name with a `\`, which Windows refuses, a name or a source with a `:` below the game folder - a stream, no file in it - and every target elsewhere go on as made. A replace-rename into the game folder goes to Windows as `FileRenameInformationEx` with `FILE_RENAME_REPLACE_IF_EXISTS`, `FILE_RENAME_POSIX_SEMANTICS` and the caller's other flags (`FILE_RENAME_IGNORE_READONLY_ATTRIBUTE`, say), from the copy, its length 20 bytes and the name's, 24 at least; one whose name has more than 1024 characters is passed on as made. Where Windows answers the rename turned with `STATUS_NOT_IMPLEMENTED`, `STATUS_INVALID_INFO_CLASS`, `STATUS_INVALID_PARAMETER`, `STATUS_INVALID_DEVICE_REQUEST` or `STATUS_NOT_SUPPORTED` - a file system that does not take the class or the flag, a FAT drive, a network share, a Windows older than 10 1607 - the call is made again as the caller made it and its result returned; every other answer, a failure too, is returned as Windows gave it. The test build stands in for such a file system with `TWEAKSV_TEST_NO_RENAME_EX=1` (section 13.1). The game folder's object name is read once before the hook is made, with `NtQueryObject` on the folder; one that cannot be read is a problem, since no rename by a bare name can then be told to lie in it: `Replace-renames in the game folder by a bare name are not given POSIX semantics this session: the game folder's path could not be read (<error>).` With `DIAGNOSTIC_MODE`, after the call (`AfterCall`), each rename turned is a line: `rename #N: <target below the game folder> | <result> | <asked>, <form> -> FileRenameInformationEx, flags 0x... | from <callers>` - the result `ok` or the status, or where the file system refused POSIX semantics `refused (<status>), made again as made: <result>`; asked `FileRenameInformation with ReplaceIfExists` or `FileRenameInformationEx, flags 0x...`; the form `a full name`, `a name relative to the game folder` or `a bare name`, whose target is the source's folder and the name; the callers as an open line's - 20,000 lines at most (`DIAGNOSTIC: 20000 lines of renames turned written - from now on they are only counted.`), the renames counted all the same. Programs outside the game are not touched: their classic replace over a file the game holds still gets access denied, the limit README.md states.
- With `DIAGNOSTIC_MODE`, `DStorageGetFactory`, `DStorageSetConfiguration` and `DStorageSetConfiguration1` are hooked in a loaded `dstorage.dll`, one hook for the two configuration functions (`DIAGNOSTIC: the game's DirectStorage calls are logged (N of 3 functions hooked).`; not loaded, `dstorage.dll is not loaded, so the game does not use DirectStorage here: there are no DirectStorage calls to log.`), and each call into DirectStorage is logged with its caller and its values: `the game asked for the DirectStorage factory (call #N, interface {...}) -> ok, from ...`, with the factory's first eight functions (`DIAGNOSTIC: the factory's first 8 functions: [0] dstorage.dll+0x... ... [7] ...`, or `DIAGNOSTIC: the factory's function table could not be read.`), and `the game set the DirectStorage configuration (DStorageSetConfiguration) -> ok, from ...` with `DIAGNOSTIC: DStorageSetConfiguration values: ...` (7 values, 8 for `DStorageSetConfiguration1`). When the game gets its factory for the interface `{6924EA0C-C3CD-4826-B10A-F64F4ED927C1}`, the hook reads the factory's function table (safely: a bad pointer is caught, never a crash) and hooks its function [4], `OpenFile`, which must lie in `dstorage.dll` or `dstoragecore.dll`, before the game gets the factory back, so that it sees the first `OpenFile` already (`DIAGNOSTIC: the game's OpenFile calls are logged (OpenFile at dstoragecore.dll+0x... hooked).`), tried once under a lock a second caller waits on; what keeps it from being made is a line, `DIAGNOSTIC: OpenFile is not logged: <why>.` - `the factory's function table could not be read`, `the factory's OpenFile is not in DirectStorage's DLLs (<address>)`, `OpenFile (<address>) could not be hooked (details in TweaksV.log)`, `OpenFile could not be hooked (unexpected exception)`, the last made before the attempt so that logging it needs no new text. - `HookOpenFile` passes every call on as it is and logs it, its own work done on the stack: the path is copied safely (at most 2047 characters), `/` made `\` in the copy only, and made full in a second buffer - a `\\?\UNC\server\share` path, the prefix in any case, as the network path `\\server\share`, any other `\\?\` path without the prefix and as it is, as Windows takes it, and every other path through `GetFullPathNameW`, which makes it absolute from the current directory, as DirectStorage does, and collapses `.` and `..` - and every call is counted in exactly one of four counts, with atomics: an archive in the game folder (decided as above), another file in the game folder, a path outside it, a path that cannot be read, is longer, or cannot be made full. ### 11.9 Blips (`InitBlips`)

The game's script `blip_controller` makes the vanilla blips behind a guard: a loop that calls the native that counts the active blips, compares the count with a threshold of its own, 150 on 1.0.1158.16, and while the count is at or above it waits 2000 ms and counts again (PATTERNS.md, "Blips"). The part raises that threshold to `ACTIVE_BLIP_LIMIT` - 150..1997, 1997 being the count's lowest answer with the pool full, so that a higher limit could let the script make a blip into a full pool - in the script's code each time the game places the script, at the start and again at every save load, a new program object each time, as a user of the script programs' hook (section 13.3). `InitBlips` reads the limit and `DIAGNOSTIC_MODE` once, then calls `Scripts::AddUser({ "Blips", before, after }, reason)`: a hook that cannot be made is the part's problem with the module's reason (`blip_controller's threshold is not raised this session: Y-E-H1 was not found.`); a hook made is said, `Each time the game places blip_controller, its guard's threshold is set to 1900 (ACTIVE_BLIP_LIMIT; the game's own: 150).`; in a dry run the call is not redirected and the part sees no program, `DRY_RUN: the natives' resolution call is not redirected, so blip_controller is not looked at - its guard is found and checked on a boot without DRY_RUN.`

`before`, at every placement, on the game's resource placement thread: a program object that cannot be read (`IsReadable`, 0x80 bytes) is logged once and left; one whose hash at +0x58 is not `blip_controller`'s (0x80CFE974, `Scripts::NameHash`) costs that read and nothing more; one with the hash and another name, read with `Scripts::ReadName` within 64 bytes, is logged once (`A script program has the hash of blip_controller, 0x80CFE974, but is named blip_imposter - left as it is (logged once).`). For `blip_controller` itself, its placements counted from 1: its code length 1 byte..16 MB and its native count 1..65536 (the module's bounds), its native table readable, its code's page table and every page readable (`PageLength`); then the whole code is decoded from 0 with the opcode lengths of the game's own table, constants in the part (`kLengthRanges`, checked when TweaksV is compiled to cover 0x00..0x82 once, in order), ENTER 5 bytes and its name's (the byte at +4), SWITCH 2 and 6 per entry (the byte at +1). A byte above 0x82, or an instruction that runs past the code or past its page - SWITCH's count within its page, its entries within the page of ip + 2 - refuses the program (`its code cannot be decoded: the byte 0xA0 at 0x200 is no instruction`), so the bytes inside operands, names and SWITCH tables are never taken for a match. The decode marks every instruction's start in a bitmap, a bit per byte of code, allocated per placement inside a `try` (`there was not enough memory to read its code`), and notes the first CATCH, THROW or CALLINDIRECT.

The guard is tried at every instruction start that is a NATIVE with no argument and one result, in a window of 256 bytes from it (fewer at the code's end), every instruction of the guard on an instruction start in the window and ending in it: the count's NATIVE; any NOPs; the threshold's push, PUSH_CONST_U8 or PUSH_CONST_S16, 1..1997; IGE or ILT, maybe NOT, then JZ - or the fused IGE_JZ or ILT_JZ in their place; the branch's target an instruction start in the window. JZ jumps when what it takes is 0 and a fused jump when its comparison is false, so the branch leaves the guard either while the count is below the threshold - the game's ILT NOT JZ, and IGE JZ or IGE_JZ - or while it is not - ILT JZ, IGE NOT JZ, ILT_JZ: the way out and the body are the branch's target and the instruction after it, in that order or the other. From each, NOPs and jumps (J) are followed within the window, a circle or a step off an instruction start failing the match: the body is a push of 2000 (PUSH_CONST_S16, PUSH_CONST_U24 or PUSH_CONST_U32) and a NATIVE with one argument and no result, WAIT, after which NOPs and jumps lead back to the count; the way out may not lead back into the guard. The two natives' indices (big-endian, at +2 of their NATIVE) lie below the native count and differ. A sequence with the guard's head but not the rest is a miss with its reason, the first of which the problem names when no guard is found (`its guard was not found in its code - the count and a comparison with a threshold are at 0x3FE, but its WAIT calls native 3, which is not below its native count, 3`). Refused, the program left as the game placed it: no guard (`its guard was not found in its code`); a second one (`its guard was found twice in its code, at 0x3FE and 0x800 - which one is meant cannot be told`); a CATCH, THROW or CALLINDIRECT anywhere in the code, whose target is computed while the script runs and could lead into the guard (`its code holds a CATCH, THROW or CALLINDIRECT at 0x..., whose target is computed while the script runs and could lead into its guard at 0x3FE of its code`); a jump (J, JZ and the fused jumps: ip + 3 + their signed 16-bit offset), a CALL (its unsigned 24-bit address) or a SWITCH case (its unsigned 16-bit offset from the entry's end), as the interpreter reads them from anywhere that leads into the bytes from the end of the count's NATIVE through the branch (`a jump at 0x100 leads into its guard at 0x3FE of its code, between 0x402 and 0x408`).

The threshold found: the configured limit already - left, `blip_controller's guard at 0x3FE of its code holds the threshold 1900 already (ACTIVE_BLIP_LIMIT=1900) - nothing to patch (placement 1).`; one other than the game's 150 - left as it is and logged, not a problem, as the heap adjuster leaves a heap another adjuster set (`blip_controller's threshold is not raised (placement 1): its guard at 0x3FE of its code holds 240, not the game's own 150 - left as it is.`); the game's 150 - the rewrite is prepared: the bytes from the end of the count's NATIVE to the branch become NOPs, the new threshold's push right-aligned against the branch - PUSH_CONST_U8 up to 255, PUSH_CONST_S16 above - and the comparison that keeps the polarity, IGE where the branch leaves the guard while the count is below the threshold and ILT where it leaves it otherwise; a fused branch's opcode becomes JZ, its offset and so its target unchanged; nothing after the branch moves - `43 6C 07 0B` for 1900, `00 25 C8 0B` for 200, in the place of the game's `25 96 0C 06`. Too little room - the push and the comparison longer than the bytes before the branch, or a push that would run past the end of a page - refuses it (`its guard at 0x3FE of its code has 3 bytes before its branch, and the threshold 1900 needs 4`). What `before` found goes to `after` in a record per thread, `thread_local`, without an allocation - the module calls a user's `before` and `after` in turn on one thread - with the two natives' hashes from the table before the resolution.

`after`, once the game has resolved the natives: for a rewrite, the program is read again - its code length, native count and page table, the pointers of the window's pages, and the window's bytes against those `before` read - and the window decoded again from the count and matched again, which must give the same guard, or nothing is written (`its guard at 0x3FE of its code changed between the game's placement and the write (another mod may be at work) - left as it is`); then one `WriteCode`, a piece per page the bytes lie in, `what` = `threshold in blip_controller's guard at 0x3FE of its code (placement 1)` (a write that fails: `its code could not be changed (details in TweaksV.log)`), and the line `blip_controller's guard at 0x3FE of its code: the threshold 150 -> 1900 (placement 1).` With `DIAGNOSTIC_MODE`, for every guard found, one line with both natives - index, hash and handler, the table's entry after the resolution: `DIAGNOSTIC: blip_controller's count native index 10, hash 0xC802478C8862BDAD, handler RVA 0x1D51F40; WAIT index 47, hash 0x4EDE34FBADD967A6, handler RVA 0x920EA0.` Every refusal is `blip_controller's threshold is not raised (placement N): <why>.`, a problem the first time a session for each kind of failure - after the start-up summary in a box of its own (section 6.4) - and afterwards a line with the count, `... - 2 times this session, reported once.`, since a save load places the same program again. Both functions run inside the module's `try`, and their own work that can throw inside one more.

The measurement, `DIAGNOSTIC_MODE` only: `L-E-P1` gives the blip pool, 2000 slots of 8 bytes (the rel32 of the allocator's `lea rbx, [rip+disp32]`, at +10), and `L-E-P2` its high-water mark, a dword (the disp32 of `cmp [rip+disp32], esi`, at +5) - the two instructions' opcode bytes checked against the patterns when TweaksV is compiled - both inside the game, the pool's last byte too. A pattern not found, an address outside the game or a thread that cannot start is logged (`DIAGNOSTIC: the blip pool is not measured: L-E-P1 was not found.`), not reported: an aid (NOTES.md, T-DIAG). Announced by `DIAGNOSTIC: the blip pool at RVA 0x3DEBD70 (L-E-P1), 2000 slots, and its high-water mark at RVA 0x3DEFBF0 (L-E-P2): the slots in use are logged after 10 seconds, then every minute while the numbers change.`, the measurement (section 6.6, thread `blip pool summary`) reads the mark and, after `IsReadable` over the pool, the slots below it in one pass, 8 bytes at a time, without a lock - nothing is written or called - and logs `DIAGNOSTIC: blips: 162 of the pool's 2000 slots in use, the high-water mark at 170; blip_controller makes blips up to 1900 (ACTIVE_BLIP_LIMIT).`, its end saying what the guard held after the last placement: another threshold left as it is, `blip_controller's threshold was not raised at its last placement (see above)`, `blip_controller has not been placed yet`, `blip_controller's threshold is not raised this session (see above)` when the hook could not be made, `DRY_RUN: blip_controller's threshold is not raised` in a dry run. The old plugin is rootBrz's `BlipLimitFix.asi` (section 4.3).

### 11.10 The parts measured first (`kMeasuredFirst`)

Four parts to come lift seven more limits of the game - WeaponLimits the weapons.meta files and the weapon components, SirenSettings the siren setting IDs and the sirens per vehicle, PedProps the props per anchor of a ped, Resources the video memory budget for streamed resources and the streaming memory (ROADMAP.md) - and each goes in only once a mod load reaches its limit. So the limits are measured first, each by a module of its part, `TweaksV<Limit>.cpp` and `.h`, with its header comment, its part's log tag (`kTag`: `WeaponLimits`, `SirenSettings`, `PedProps` or `Resources`, which the two modules of a part with two limits share) and one entry function, `Measure<Limit>()`, which `kMeasuredFirst` starts with `DIAGNOSTIC_MODE=1` (section 4.3); the subsections below are in that table's order. A module finds every pattern of its limit - its measurement's and those its part's writing half will use - as often as each must match, checks each site as the writing half will (its bytes, offsets and targets, the complete sets by a scan), logs every site in the wording of section 6.3 and starts its measurement through `StartMeasurement` (section 6.6). It writes nothing to the game - no `WriteCode`, no `RedirectCalls`, no hook - but the siren count's, which redirects one call (11.10.4). Every read of the game's memory is checked first and bounded (section 12): `IsReadable` for the game's own data, `CopyMemorySafely` (section 9) for heap data the game may change meanwhile. A pattern missing, a site not as expected, an address outside the game or a thread that cannot start is logged and not reported, a diagnostic aid (NOTES.md, T-DIAG), and that module measures nothing more. Without `DIAGNOSTIC_MODE` nothing is looked for, so a normal boot does what it did without them; `DRY_RUN` changes nothing in them but the siren count's, which then redirects nothing and counts nothing. They have no section in `TweaksV.ini`, no entry of `kFeatures` and no old plugin: those come with a part's writing half.

## 12. The rules every part follows

- **Nothing is written before everything is found and checked.** Every site is found by pattern, every instruction's bytes are the expected ones, every address inside the game, every value plausible and consistent; the first thing not as expected ends the part's job with nothing changed.
- **All or nothing.** A job's writes go in one `WriteCode` or `RedirectCalls`: every page made writable first, every page given its own protection back, on an exception too; a part either does its whole job or leaves the game as it was. Hooks of one group are created and switched on together or removed again. The writes in `DllMain` happen while the game is still single-threaded; RageOpenV's start-up writes its few bytes - the cache check's `C3 90`, the console's NOPs, the five `E8 rel32` - on the game's thread at the first time request without freezing the other threads, as MinHook does for the hooks: an accepted window, since no other thread runs that code then (NOTES.md, T-FREEZE). The Blips part writes into a script program on the game's resource placement thread, after `DllMain`, but before the game enters the program in its registry of programs, where no script thread can run it (section 13.3).
- **What another mod has already changed, TweaksV does not change again.** A heap another adjuster set, a cache check already skipped, a function already hooked (hooked on top, chained through) are left and logged; an array already moved, a call already redirected, a pattern that matches more often than it must are refused with the reason, because what TweaksV would write over cannot be known. The conflict check switches a part off entirely when its old plugin is installed, or a plugin that does its job too and stays (section 7).
- **Never silent.** Every job not done is a `PROBLEM` line in the log with the reason and an item of the start-up summary, which is a message box with `ERROR_POPUP=1`; a part that stops working after the start-up gets a box of its own. A switch that is off is logged in one line. DirectStorage's job is its `NtCreateFile` and `NtSetInformationFile` hooks: one that cannot be made is a problem of the start-up summary. An aid that cannot be set up - the console, DirectStorage's call logging (its factory and `OpenFile` hooks and the checks that the game asks for its factory), a measurement whose thread cannot start (section 6.6), the `UNLOCK_FILES` summary's among them - is logged, not reported (NOTES.md, T-DIAG). `DRY_RUN` and `DIAGNOSTIC_MODE` work the same for every part, with two exceptions: with `DIAGNOSTIC_MODE=1` the box streamer refuses its whole job when a tree-search call cannot be redirected, because the measurement is the reason the switch is on (section 11.4); and with `DRY_RUN=1` the Blips part checks its hook's sites but never sees `blip_controller`, which reaches it only through the hook a dry run does not make (section 11.9). The parts measured first are aids as a whole (section 11.10): without `DIAGNOSTIC_MODE=1` they look for nothing, a failure of one is logged and not reported, and `DRY_RUN` changes nothing in them but the siren count's measurement, which then redirects nothing.
- **Everything read is bounded and checked.** INI values are trimmed, limited to 255 characters, parsed and clamped; the mods list has limits on entries, depth and path length; paths from the game are read with a length limit, paths from DirectStorage copied with a length limit and a guard against unreadable memory, and the name of every `NtCreateFile` call read within its own length under the same guard, and every rename's buffer within the length its caller gives, its name copied only when it has 1024 characters at most; the entry table of an archive is walked only when its count is plausible; the scanner reads the PE header and the section table only where they lie inside the image, and unwind data is asked of Windows (`RtlLookupFunctionEntry`); the parts measured first read the game's data only after `IsReadable` or through `CopyMemorySafely`, within bounds of their own (section 11.10); the log cuts its lines and its file.
- **Nothing throws into the game.** Every hook puts what can throw - a log line, a table walk - inside a `try`, and so do the measurement threads and the two threads of `TweaksVSummary`; a lock is never left taken by an exception (`TweaksVLock.h`), nor a page of the game's code writable (the guard in `WriteCode`). The DirectStorage hooks, RageOpenV's ParseHeader hook and its OpenBulk hooks' lines, and the script programs' hook around its users' work (section 13.3), keep the game's last error; the other hooks call the game's function last, so the game's own error stands. `DllMain` catches everything on attach and returns `TRUE`.
- **Nothing per frame beyond the game's own work.** The hooks on hot paths (the file functions, the tree searches, DirectStorage's `NtCreateFile`, which every file open of the game passes) do one path spelling and one hash lookup, one count with atomics, or one bounded comparison of the open's name with the game folder and its counts with atomics - no allocation, no lock of TweaksV's, no file system call, but for one query of a folder's identity per open relative to a folder handle (section 11.8); DirectStorage's `NtSetInformationFile` hook compares the class of every call and reads nothing more of one that is not a rename, and a replace-rename costs a copy of its name on the stack and, for a name relative to a folder handle or a bare name, one query of Windows; the `DIAGNOSTIC_MODE` check costs one comparison, and with it on the log lines are capped (below); the measurements are read once a minute by threads of their own; the siren count's measurement, with `DIAGNOSTIC_MODE=1` only, adds to the game's call that draws a vehicle's sirens one lookup in a fixed table of the vehicle models seen, the model's bone lookups only on its first pass (section 11.10.4).
- **Memory TweaksV adds is never writable and executable at once.** The moved arrays are read/write data; the call stubs are written once and then read+execute; MinHook's trampolines are the one exception, accepted (NOTES.md, T-HARDEN). The build carries ASLR with high entropy, DEP, Control Flow Guard and CET compatibility, statically linked (section 15).
- **Per-event output is capped.** Every kind of line that can come without bound - file requests, files served, archive headers, OPEN archives left as they are, mods files that cannot be opened, folders of the mods folder that cannot be read, the opens inside the game folder, DirectStorage's `OpenFile` calls and the renames it turns - stops after 20,000 lines of its kind (`kMaxLinesPerKind`, section 6.6; the cap lines are in section 6.3); the events are then only counted, with a summary every minute where `DIAGNOSTIC_MODE` gives one, so no boot fills the 64 MB log. The tables behind a summary are bounded too: DirectStorage's open summary takes 100,000 entries per table, its `UNLOCK_FILES` summary 8,192 files and 15 types.
- **One wording** (section 6.3) and one log tag per part, the feature name.

## 13. Test builds

### 13.1 The switches

A test build (`-p:TweaksVTestBuild=true`, `TWEAKSV_TEST_BUILD` defined, built into `object\Test\Release\TweaksV.asi`) reads four more keys under `[TWEAKSV]`, never written to the file, and says `TEST BUILD - not for release` in the header: `TEST_BREAK_PATTERN=<label>` treats that pattern as not found; `TEST_LOG_LIMIT_KB=<KB>` (1..65536) lowers the log's limit; `TEST_DUMP_CODE=<seconds>` (1..3600) saves the game's code; `TEST_DUMP_SCRIPT=<name>` saves the script program of that name each time the game places it (section 13.3). The environment variable `TWEAKSV_TEST_NO_BOXES=1` keeps every message box off the screen, and `TWEAKSV_TEST_FILE_INDEX=1` makes DirectStorage read the game folder's identity as on a file system without file IDs (section 11.8; `TEST BUILD: the game folder's identity is read without FileIdInformation (TWEAKSV_TEST_FILE_INDEX=1).`), and `TWEAKSV_TEST_NO_RENAME_EX=1` makes it answer every rename it turns as a file system that refuses POSIX semantics would, `STATUS_INVALID_PARAMETER` without asking Windows, so that the fallback runs (section 11.8; `TEST BUILD: every rename turned is answered as on a file system that refuses POSIX semantics, without asking Windows (TWEAKSV_TEST_NO_RENAME_EX=1).`). `TWEAKSV_TEST_SUMMARY_MS=<ms>` (100..60000) makes every measurement's summaries after its first come every <ms> milliseconds instead of every minute, so that a suite sees a summary come again within the minute a fake game runs (section 6.6; said once per measurement, `TEST BUILD: the weapon infos summary comes every 2000 ms after its first (TWEAKSV_TEST_SUMMARY_MS=2000).`).

### 13.2 The code dump (`TweaksVDump`)

`StartCodeDump()` takes a copy of the game as it is before any part changes it, and a thread saves it as `GameCode-start.bin`, waits the seconds asked for, takes a second copy and saves it as `GameCode-later.bin`, both in `%LOCALAPPDATA%\TweaksV` through the own-file checks, never in the game folder. A copy holds the PE headers and every section that is not writable - the code, the constants, the function table - and a writable one only when it is also executable; the plain data sections, which can hold the player's data, are never saved; bytes that cannot be read are saved as zeros and counted. The file (format version 1, little-endian): a `DumpHeader` (`magic` "TWKVDUMP", `formatVersion` 1, `sectionCount`, `imageBase`, `imageSize`, `timeDateStamp`, `secondsAfterStart`, `reserved`; 40 bytes), one `DumpSection` per section (`name` as in the section table, "HEADERS" for the headers; `rva`, `size`, `characteristics`, `unreadable`, `fileOffset`; 32 bytes), then the bytes of each section at its `fileOffset`. The log says what was saved: `TEST BUILD: GameCode-start.bin saved, the game as it was 0 s after TweaksV started, before anything was patched: 50.3 MB in <folder> - sections HEADERS .text ...; none unreadable; not saved (the game writes to them): .data ...`. This is how patterns are found after a game update: a dump of the running game is rebuilt as a PE (the headers and the saved sections at their offsets, `.data` as zeros) and analysed with Ghidra's headless analyser, the `.pdata` table giving the functions (PATTERNS.md, "When Game Updates", item 3).

### 13.3 The script programs (`TweaksVScripts`) and their copy (`TEST_DUMP_SCRIPT`)

A script program is one of the game's compiled scripts - `blip_controller` and the others its archives store, encrypted - as the game holds it in memory: its code and its strings in pages of 16 KB, its table of natives (the game's functions it calls) and its name (PATTERNS.md, "Script programs"). The game makes one in the program's resource constructor whenever it streams the script in, on its resource placement thread; the constructor calls the game's function that resolves the natives (the call at +3 of `Y-E-H1`) and only afterwards enters the program in its registry of programs, where every script thread looks its program up each time it runs, so no script thread can run a program while that call is under way.

`TweaksVScripts` owns the one redirect of that call, for every part that works on a script program. A user is a `Scripts::User { tag, before, after }`: `before(program, placed)` runs for every program the game places, before its natives are resolved - the native table still holds their hashes - with how many programs the hook has seen so far, this one included, and what it returns comes back to `after(program, resolved, context)`, which runs once the game's function has returned, with its byte (1 when every native was found). `Scripts::AddUser(user, reason)`, from `DllMain` only, puts the user into a fixed table of four - no allocation and no lock on the game's thread, the count published after the entry - and the first user makes the hook: `Y-E-H1`, `Y-E-N1` and `Y-E-I1` are looked for, each one missing logged by the scanner and the first of them named in the reason (`Y-E-H1 was not found.`); the call at +3 must lead into the game (`the natives' resolution call at RVA ... is not a call into the game (another mod may have hooked it already).`); and `RedirectCalls` sends it through a call stub to the module's `ResolveHook` (with `DRY_RUN`, `DRY_RUN: would redirect the natives' resolution call at RVA ...` and nothing else; a write that fails gives `the game code could not be changed (details in TweaksV.log).`). `DIAGNOSTIC_MODE` logs the three sites under the user's tag: `DIAGNOSTIC: natives' resolution call at RVA ... -> RVA ..., strings' length offset at RVA ... holds 0x70 (Y-E-H1)`, `DIAGNOSTIC: code length offset at RVA ... holds 0x1C, native table offset at RVA ... holds 0x40 (Y-E-N1)` and `DIAGNOSTIC: code page table offset at RVA ... holds 0x10 (Y-E-I1)`. A hook made is logged, `The natives' resolution call at RVA ... is redirected: every script program the game places passes TweaksV, before and after the game resolves its natives.` The outcome is kept: a later user joins a hook that is made, and gets the first user's reason when it could not be made, which each user reports as its own problem. `ResolveHook` calls every user's `before`, then the game's function, then every user's `after`, each user inside a `try`, with the game's last error kept around their work, and returns the game's byte. The module gives its users the layout too: the fields as named constants (`kCodePagesOffset` 0x10, `kCodeLengthOffset` 0x1C, `kNativeCountOffset` 0x2C, `kNativesOffset` 0x40, `kNameHashOffset` 0x58, `kNameOffset` 0x60, `kStringPagesOffset` 0x68, `kStringLengthOffset` 0x70, `kProgramSize` 0x80), the four a pattern pins checked when TweaksV is compiled against the byte the pattern holds there (`PatternByte`, section 4.2) - `Y-E-H1` pins `kStringLengthOffset` at +18, in the constructor's loop over the strings' pages after the call; the page rule (`kPageSize`, `PageCount`, `PageLength`), its rounding, `kPageSize - 1`, pinned by `Y-E-H1` at +10 the same way; the bounds a program's fields are read within (`kMaxLength`, 16 MB for the code and for the strings - a call's target in the code is 24 bits - and `kMaxNatives`, 65536 - a native's index is 16 bits); `Field`, a field of a program or of a table it points to, read once `IsReadable` has said so; `ReadName`, the name read within `kNameRead`, 64 bytes, a memory page at a time and only where it can be read, and `Printable` for a log line; and the game's hash of a script's name (`NameHash`, checked against `blip_controller`'s 0x80CFE974 when TweaksV is compiled).

`TEST_DUMP_SCRIPT=<name>` (test builds) is its first user, started by `StartScriptDump()` at step 7 of the start-up, after `StartCodeDump()`, under the tag `TweaksV`; the Blips part is its second, joining at step 8 (section 11.9), so the switch's copy shows a program as the game placed it, before the part writes to it. The name is 1 to 63 letters, digits and `_`, compared without case; another value is reported (`TweaksV.ini: [TWEAKSV] TEST_DUMP_SCRIPT=../x is not a script's name of 1 to 63 letters, digits and _ - no script program is saved.`), and so are a `LOCALAPPDATA` that is not set (`TEST_DUMP_SCRIPT: LOCALAPPDATA is not set - no script program is saved.`) and a hook that cannot be made (`TEST_DUMP_SCRIPT: the script program blip_controller is not saved this session: Y-E-H1 was not found.`), and nothing is hooked. Otherwise the log says what the switch waits for, `TEST BUILD: TEST_DUMP_SCRIPT=blip_controller: the script program blip_controller (hash 0x80CFE974) is saved each time the game places it, at most 16 times, as Script-blip_controller-<n>.bin in <folder>.` - with `DRY_RUN`, `TEST BUILD: TEST_DUMP_SCRIPT=blip_controller: DRY_RUN - the call is not redirected, so no script program is saved.`

At each placement, on the game's thread, every read of the game's memory is checked with `IsReadable` first - the name a memory page at a time, within 64 bytes. The first program of all is logged, whatever its name - the line that proves the hook runs: `TEST BUILD: TEST_DUMP_SCRIPT: the first script program the game placed is <name> (hash 0x...), on thread N - the hook runs.` A program whose hash at +0x58 is the name's and whose name is that name is copied; one with only one of the two is logged once (`TEST BUILD: TEST_DUMP_SCRIPT: a script program has the hash of blip_controller, 0x80CFE974, but is named <name> - it is not saved (logged once).`) and not copied. The bounds, the module's: the code and the strings 16 MB each and 65536 natives; a program beyond them is a problem (`TEST_DUMP_SCRIPT: Script-blip_controller-3.bin was not saved: its code length, 16777217 bytes, is beyond 16 MB.`, `... its native count, 65537, is beyond 65536.`) and not copied. `before` allocates the file and copies the native table while it holds the hashes; `after` copies the program object, the code page after page, the table as the game left it and the strings, a page that cannot be read as zeros, counted, and writes the file right there, on the placement thread, through `OpenOwnFile` in `%LOCALAPPDATA%\TweaksV` (`FileFolder::Own`; the folder made if need be, a file of that name from an earlier session replaced), never in the game folder. At most 16 copies a session: the 17th placement logs `TEST BUILD: 16 copies of blip_controller saved - from now on its placements are only counted.` once. Memory that cannot be had and a file that cannot be written are problems (`TEST_DUMP_SCRIPT: Script-blip_controller-1.bin was not saved: it is a hard link: ...`), which after the start-up summary get a box of their own (section 6.4). Each copy saved is logged: `TEST BUILD: Script-blip_controller-1.bin saved in <folder>: blip_controller placed the 1st time, as the game's 312th script program, on thread N - code 16675 bytes in 2 pages, 245 natives, every one resolved, strings 496 bytes; none unreadable.`

The file, `Script-<name>-<n>.bin`, the name in lower case and n counting this program's placements from 1 (format version 1, little-endian; a research reader is written against it, so a change of its layout needs a new format version): a `ScriptDumpHeader` of 176 bytes (`TweaksVDump.h`, its size checked by a `static_assert`) - `magic` "TWKVSCRP", `formatVersion` 1, `headerSize` 176, `name` (64 bytes: the program's name as the game holds it, zero-padded), `nameHash`, `codeLength`, `nativeCount`, `stringLength` (the program's fields at +0x58, +0x1C, +0x2C and +0x70), `placement`, `threadId` (the thread that placed it), `programsPlaced` (every program the hook saw so far, this one included), `resolved` (the game's byte), 3 bytes reserved, `imageBase`, `imageSize`, `timeDateStamp` (where the game was, its SizeOfImage and its PE timestamp - the game build), `unreadable` (the bytes saved as zeros), a dword reserved, and the offsets of the five blocks that follow in this order: `programOffset` (the program object's first 0x80 bytes, as they are), `codeOffset` (`codeLength` bytes, page after page), `nativesBeforeOffset` (`nativeCount` x 8: the table before the game's resolution - the hashes), `nativesAfterOffset` (the same after it - the handlers' addresses, as they are) and `stringsOffset` (`stringLength` bytes, page after page). The reserved fields are 0.

## 14. The tests

### 14.1 The harness

`test\` holds everything, loose in one folder: `run_all.sh` builds and runs every suite from Git Bash and deletes its intermediates (its Release build replaces `x64\Release\TweaksV.asi`); `common.sh` has the helpers; `build_tweaksv.cmd` builds TweaksV's Release and test builds; `build.cmd` builds the fake programs into `object\TestRun`, with warnings as errors (`/WX`); `vsenv.cmd` finds Visual Studio with vswhere; `deps.cmd`, `headers.cmd` and `junction.cmd` are the integration suite's helpers (a module's imports, the PE headers for the mitigations, a junction made and removed - the rageopenv suite makes one too); the fake programs are `fake_game.cpp`, `fake_game_full.cpp`, `fake_game_rov.cpp`, `fake_game_version.rc`, `fake_dstorage.cpp` and `fake_renamer.cpp`; `base.ini` is the file the game suites start from (layout 3 with `HEAP_SIZE=1024` and `PACKFILEARRAY_SIZE=12000`, two values that are not the defaults, which the part suites and the integration suite assert - `heap: 1024 MB` - and which prove the file is read), `expected_default.ini` the default file of section 5.4, `layout1.ini` the 1.6.0 default for the 1.x-file scenarios. Each suite is one `run_<suite>.sh`; `run_all.sh` runs them in the order of its list, `SUITES`, one suite a line - `patterns ini_default story modkit packfile boxstreamer decals rageopenv directstorage blips`, then the suites of the parts measured first in the order of section 11.10, and `integration` last - reads each one's `N passed, M failed` line - a suite that prints none counts as one failure, with `no result line (the suite stopped early)` in its line of the RESULTS block - and prints the `all` line, whose count NOTES.md's "Tests:" bullet carries (901). The run fails when a check fails, when a suite stops early, when either build log holds a warning (`: warning `; the warnings are listed with the log's last lines), and when the number of checks run is not the one NOTES.md's "Tests:" bullet gives - that bullet's, not the first number before "checks" anywhere in the file - so that a check that silently stops running shows. It deletes `object\TestRun`, `object\TestTemp` and `object\Test` afterwards; `--keep` leaves them, and `--no-build` tests the TweaksV builds already there, which is why it works after a `--keep` run only. The suites are the arbiter: a change to a part passes the checks that pin its behaviour, or it is not done. The fake game's copies of game code live in its `.fakesit` section, since TweaksV searches executable sections only: a site that must be found goes there, and the fake game reaches a moved array only through a pointer, never with an instruction a scan would count. A pattern that must match more than once (`D-E-L12`, seven times, and `A-E-G1`, twice) goes through `Scanner::FindAll`, whose per-match DIAGNOSTIC lines name the pattern; the story and packfile suites count on those being the only per-match lines of a normal run. The check count in NOTES.md is the `all` line of `run_all.sh`, updated with every test change; the patterns suite checks that PATTERNS.md and `TweaksVPatterns.h` list the same patterns.

The fake programs pretend to be the game, not TweaksV: they run as `GTA5_Enhanced.exe` (copied to that name for each run), load the real `TweaksV.asi` the way an ASI loader does, ask for the time once (as the game does early on, which runs RageOpenV's start-up), wait for the summary thread, and report. `plain_game.exe` (`fake_game.cpp`) holds no game code: with it every part that uses a pattern reports it missing (DirectStorage only says that `dstorage.dll` is not loaded). `full_game.exe` (`fake_game_full.cpp` with `fake_game_rov.cpp`) holds copies of every site TweaksV patches, laid out so that the patterns match, in a section of its own, `.fakesit`, which is executable (TweaksV searches only executable sections); the arrays those sites reference lie in the fake's ordinary data, and the fake's own code reaches them only through a pointer, so that no `lea` of them in its code is counted by TweaksV's scan. RageOpenV's eight hooked file functions are real code in another section, `.fakefn`, so the hooks are called end to end; the five redirected call sites are only rewritten, and the report calls what they lead to - TweaksV's hooks, and through them the fake's own functions behind the calls. The script programs' three sites lie in `.fakesit` too, and with an option `script...` the fake places a script program laid out at the game's offsets - `blip_controller`, its code over two pages of 16 KB, the second partial, three natives and its strings, each page a memory allocation of its own, its code decodable from end to end with the game's opcode lengths - instructions of every length and kind, a SWITCH, an ENTER whose name holds the guard's bytes - with the guard at 0x3FE as the game has it, its count native 1 and WAIT native 2, or as an option `blip...` asks for it (the fused ILT_JZ with the polarity the other way round, NOPs, too little room, 240, a native the program lacks, a second guard, a jump, a call or a SWITCH case into its span, a CATCH, a byte that is no instruction, its threshold changed while the natives are resolved), laid again before each placement as the game makes a new program; `other_script` and `blip_imposter` (`blip_controller`'s hash under another name) beside it - once TweaksV has started, as the game does: on a thread of its own, through the call at the hook site, to TweaksV's stub when the call is redirected and to the fake's own resolution function when it is not, which turns the natives' hashes into the addresses of handlers of its own (a hash it does not know into its "unknown" handler, and it then returns 0) and leaves a last error of its own; for each placement of `blip_controller` it writes what it placed, before the call, to `script_placed_<n>.bin`, which a copy must hold byte for byte after its header. ## 15. Building and releasing

`source\TweaksV.vcxproj` is a plain Visual Studio project, no generated build system: C++20, `/W4` with warnings as errors in spirit (none is tolerated), the C runtime linked statically (`/MT`, `/MTd` in Debug: players need no redistributable), Control Flow Guard with its EH continuation metadata and CET compatibility set in the project (`ControlFlowGuard`, `GuardEHContMetadata`, `CETCompat`); ASLR with high entropy and DEP are the x64 linker's defaults, and the integration suite checks all four on the binary. Its `TweaksVVersionMajor`, `Minor` and `Patch` properties are the version (2.4.0); the `TweaksVBuildInfo` target writes `BuildInfo.h` into the intermediate folder before every build, with `TWEAKSV_VERSION`, its three numbers and `TWEAKSV_GIT_HASH` from `git rev-parse --short HEAD` when the folder is a repository, `-dirty` appended while the tree has uncommitted changes. Four builds matter: Release (`x64\Release\TweaksV.asi` and `TweaksV.pdb`, `object\Release`), Debug (`x64\Debug`, `object\Debug`), the test build (`-p:TweaksVTestBuild=true`, `object\Test\Release`) and the analysis build (`-p:TweaksVAnalyze=true`, `/analyze`, `object\Analyze\Release`); all four must build from scratch (`-t:Rebuild`: an incremental build shows no warnings for files it does not recompile) without a warning before a build reaches me, and `bash test/run_all.sh` must be green; `object\Analyze` is deleted afterwards, as `run_all.sh` deletes `object\Test`, `object\TestRun` and `object\TestTemp` itself. New source files get CRLF line endings; git normalizes every text file to LF, and `.sh` files and `test\*.ini` stay LF (`.gitattributes`). MinHook builds at `/W3`, unchanged, from `vendor\MinHook`. `version.rc` fills the file's version resource from `BuildInfo.h`, with the copyright string `Copyright (C) dachdecker369. Licensed under GPL-3.0-only - see LICENSE.`

A release is a tag `major.minor.patch` on the commit I booted, and a zip with exactly five files, for this version and every later one: `TweaksV.asi`, `LICENSE`, `THIRD_PARTY_NOTICES.md`, `CREDITS.md` and `README.md` - nothing else; the `.pdb` stays with the build. The release notes name the tag and link the repository, and `THIRD_PARTY_NOTICES.md` and `README.md`, which ship in the zip, name the repository too, so the Corresponding Source is one step from the binary wherever the zip goes (GPL-3.0, section 6d). The order: version in the project file, a local commit in the style of the earlier `TweaksV 1.x.y` commits, Release rebuilt from it so the header carries that commit, my boots (with `DIAGNOSTIC_MODE=1` when patterns changed, with my map mods for anything that streams), then, with a clean log, push and tag: an annotated tag named and messaged with the plain version, `main` and the tag pushed together.

## 16. Extending TweaksV

- **A new setting:** one entry in `kSettings` (section 4.1) in its section's place, with its comment for the default file - its `KEY=default` short of the comment column - a named reference, a row in README's table, and `expected_default.ini` with the new default file. `IniKeyCount()`'s `static_assert` names the count (30) and fails until it is updated: a new key in the file means a new layout number (`kIniLayoutVersion`), and the suites pin that number in `run_ini_default.sh` (the header line, the `VERSION`-alone file and its 29 keys added back, the carried layout-2 file, the newer-layout line), in `base.ini` and `expected_default.ini`, and the keys of one section in `run_directstorage.sh`. An existing file of an older layout, from `kIniFirstLayout` on, is carried forward at its next start - its missing keys added, then this layout's `VERSION` written back (section 5.3) - so a new layout needs nothing more in the code. The 1.x rule stays as it is (a file without `VERSION`).
- **A new pattern:** one entry in `kPatterns` with a new label in its part's group, and the row in PATTERNS.md with the same bytes, the offset and what the match holds; the code names it as `Pattern("label")` once. The `patterns` suite fails until both agree. After a game update the same: the table and PATTERNS.md change together, and `DIAGNOSTIC_MODE=1` with `DRY_RUN=1`, `CONSOLE=1` and every part on shows that every pattern matches as often as it must (`D-E-L12` seven times).
- **A plugin that does a part's job:** an old one TweaksV replaces is its file name in `oldPlugins` of each part whose job it does; one that stays installed is a `PeerPlugin` constant in `TweaksVFeatures.cpp`, its file and what it is, named in `peerPlugins` of each such part (the array grows when a part gets a second one), with a comment that says why it stays and what clashes. Either kind gets its scenarios in the integration suite, its row in section 4.3 and its name in README's "Testing" step 2.
- **A new part:** a section in `kSections` and `kSettings` (the layout rule above applies), a feature in `kFeatures` in the order of `kSections` (a `static_assert` checks it) with its old plugins, its plugins that stay and `Init<Part>()`, one file `TweaksV<Part>.cpp` with its header comment, its tag and its credits, listed with its header in `TweaksV.vcxproj` and `TweaksV.vcxproj.filters` (the project lists every file by name), patterns in the table, a suite `test\run_<part>.sh` with the sites added to the fake game and its name in `run_all.sh`'s list of suites, a section and the key rows in README, a bullet in NOTES and the new check count there, a section 11.x here, and the project the part derives from or takes its idea from in CREDITS.md (and in THIRD_PARTY_NOTICES.md where the part carries its code). The part finds and checks everything first, writes through `WriteCode` or `RedirectCalls`, hooks through `HookFunctions`, reports through `ReportFailure` with its job's wording, logs in the wording of section 6.3, and runs a measurement, if it has one, through `StartMeasurement` (section 6.6).
- **A limit measured first,** before its part is built (section 11.10): a module `TweaksV<Limit>.cpp` and `.h` with its header comment, its part's tag and `Measure<Limit>()`, an entry in `kMeasuredFirst` in the order of 11.10, its two files in `TweaksV.vcxproj` and `.vcxproj.filters`, its patterns in its part's group of the table, a suite `test\run_<limit>.sh` with its sites in the fake game and its name in `run_all.sh`'s list, its subsection of 11.10 and its rows here in 2 and 14.2, its section in PATTERNS.md, its paragraph in README's "Measured first" and its line in NOTES. It finds and checks everything its writing half will, logs in the wording of section 6.3, measures through `StartMeasurement` and writes nothing, all with `DIAGNOSTIC_MODE=1` only. Once its part is built, the limit leaves `kMeasuredFirst` and its module becomes the part's.
- **A new array part:** a `RelocationSpec` with its anchors (section 10.1), `FindRelocation` then `ApplyRelocation`; what the core cannot express stays in the part and reads `RelocationPlan::matches`.
- **A part that works on a script program**, as the Blips part does (section 11.9): it registers with `TweaksVScripts` - `Scripts::AddUser` from its `Init<Part>()`, in `DllMain` - reports the reason it gets back as its own problem when the hook is not there, and does its work in its `before` or `after` on the game's placement thread, reading the program by the module's offsets and page rule, every read through `IsReadable`, nothing thrown, no allocation it can do without (section 13.3); a pattern of its own goes in a group of its own in the table (the Blips part's `L`), and the module's table of users has room for four.
- **A fork or a pull request** keeps the license (GPL-3.0-only), CREDITS.md and THIRD_PARTY_NOTICES.md, which must accompany every copy, and the notices' three pieces of code (the console opener, the pattern parser, the free-memory search adapted from MinHook's `buffer.c`) credited as they are; keeps the parts their own code, as 2.0.0 made them, and carries no code of the projects that are idea only (CREDITS.md names them); keeps the suites green with the count updated in NOTES.md; and keeps the documents true: PATTERNS.md for every game fact, NOTES.md for what a part does, this file for how it does it, README.md for the player.
