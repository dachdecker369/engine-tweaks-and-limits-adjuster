# Specifications

The design of TweaksV as it is built: every module of the source, what it does, what it checks, what it writes and what it logs, so that the source can be understood, forked or built on without opening it. Four files carry the whole truth about TweaksV, each with its own job:

| File | Carries |
|---|---|
| [README.md](README.md) | the player's view: what each part does, every key of `TweaksV.ini`, building, testing, other mods |
| SPECIFICATIONS.md, this file | the design: the files, the tables, the start-up, the formats, the shared code, the mechanism of every part, the rules, the tests, how to extend it |
| [PATTERNS.md](PATTERNS.md) | the game facts: every byte pattern, what the match holds, where it matched on the current build, how the sites are encoded |
| [NOTES.md](NOTES.md) | what each part does with the checks it makes, the measurements, the open issues, the bugs found in the projects the parts derive from |

Credits and derivations are in [CREDITS.md](CREDITS.md), the notices in [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md). [SECURITY.md](SECURITY.md) says how to report a security problem and what it covers; [ROADMAP.md](ROADMAP.md) holds what I plan next and [PLAN.md](PLAN.md) the phases of a change while one is under way, both empty while nothing is planned. "I" in these files is the author, dachdecker369. TweaksV is GPL-3.0-only.

## 1. What TweaksV is

One ASI plugin for GTA V Enhanced, `TweaksV.asi`, loaded by an ASI loader into `GTA5_Enhanced.exe`. It does nothing in any other program. Eight parts change the running game in memory, never a file on disk: the heap size (HeapAdjuster), the modkit array (ModkitLimit), the packfile array and the archive count of the game's configuration (PackfileLimit), the box streamer's traversal list (BoxStreamer), the decal definitions array (Decals), a mods folder with unencrypted archives and the cache check (RageOpenV), the three start-up screens (StraightToStoryMode) and the files DirectStorage keeps locked (DirectStorage). Every part finds the game's code by byte patterns, checks every site before it writes, writes all of its sites in one go or none, leaves alone what another mod has already changed, and says in the log and in one start-up message box what it could not do.

Everything is driven by three tables - the settings, the patterns, the parts - and by shared services: the log, the start-up summary, the scanner, the patch module, the relocation core. A new part is an entry in each table plus one file of its own.

## 3. The start-up

`DllMain` runs these steps on `DLL_PROCESS_ATTACH`, inside a `try` so that no exception leaves it, and returns `TRUE` whatever happens:

1. `IsGtaVEnhanced()`: the running program's file name is `GTA5_Enhanced.exe` (case-insensitive) or nothing more happens.
2. `CreateOrUpdateIni()`: `TweaksV.ini` exists from here on (section 5).
3. `LoadSettings()`: every setting is read once; the file is let go of afterwards (section 4.1).
4. `[TWEAKSV] ENABLED=0` stops here: the file is kept, nothing else is done. Otherwise the module pins itself (`GetModuleHandleExW` with `GET_MODULE_HANDLE_EX_FLAG_PIN`): `TweaksV.asi` stays loaded until the game exits, because the game's code calls into it once hooked, and an early `FreeLibrary` would crash the game at the next hooked call. A pin that fails is reported (`TweaksV.asi could not be pinned in memory (...): an ASI loader that unloads it later would crash the game.`).
5. `ClearLogFile()` and `WriteLogHeader()`: the log is started and its header written (section 6.2). Lines logged before this point are kept and written after the header.
6. `OpenConsole()` with `CONSOLE=1`.
7. `CheckForConflicts()` with `CONFLICT_CHECK=1` (section 7). A test build then runs `StartCodeDump()` (section 13.2), before anything is patched.
8. `StartFeatures()`: every part that is on, in table order (section 4.3). Each part runs its whole job here, except RageOpenV, which only hooks `GetSystemTimeAsFileTime` and does its job at the game's first time request, because the game's file system is not up in `DllMain`, and DirectStorage, which hooks `DStorageGetFactory` here and `OpenFile` when the game creates its factory (section 11.8).
9. `ShowStartupSummaryLater()` starts the thread that shows the start-up summary (section 6.4), unless `StartFeatures` returned true because a part shows it itself later (RageOpenV, at the first time request).
10. `DllMain` returns `TRUE`, also after an exception; one that reaches its own `try` is reported (`Unexpected exception during the start-up - the rest of TweaksV is skipped this session.`) and the summary thread started, so the box names it even when the log never started.

On `DLL_PROCESS_DETACH` the log is flushed and closed (`CloseLog`), without waiting for a lock another thread may have died holding.

The game's file version comes from the version resource of the running program (`ReadGameVersion`, four 16-bit numbers; `GameVersionNumber` packs them into one number, read once, 0 when unreadable). The PackfileLimit part chooses patterns by it; the log header prints it.

## 4. The three tables

### 4.1 Settings (`TweaksVSettings.h`)

A `SettingsSection` is a section of `TweaksV.ini` and the part it belongs to: `{ name, feature }`, the feature name being the log tag and the name in the `Features:` line and the start-up summary. The sections, in file order, which is also the order the parts start in: `kTweaksVSection` (`TWEAKSV`, `TweaksV`), `kHeapSection` (`HEAP_ADJUSTER`, `HeapAdjuster`), `kModkitSection` (`MODKIT_LIMIT`, `ModkitLimit`), `kPackfileSection` (`PACKFILE_LIMIT`, `PackfileLimit`), `kBoxStreamerSection` (`BOXSTREAMER`, `BoxStreamer`), `kDecalsSection` (`DECALS`, `Decals`), `kRageOpenVSection` (`RAGEOPENV`, `RageOpenV`), `kStoryModeSection` (`STRAIGHTTOSTORYMODE`, `StraightToStoryMode`), `kDirectStorageSection` (`DIRECTSTORAGE`, `DirectStorage`); `kSections` lists them in that order.

A `Setting` is `{ section, key, kind, defaultValue, minValue, maxValue, testBuildOnly }` with `kind` one of `Switch` (0 or 1), `Number` (an `int` within `minValue..maxValue`) or `Text` (test builds only, never written to the file). The builders `Switch(section, key, on)`, `Number(section, key, value, min, max)` and `TestText(section, key)` make the entries of `kSettings`, the one table, in the order of the default file: the keys of `[TWEAKSV]` (`ENABLED`, `LOG`, `DIAGNOSTIC_MODE`, `DRY_RUN`, `CONSOLE`, `ERROR_POPUP`, `CONFLICT_CHECK`, `VERSION` with default 2 and range 2..1000000, then the test-only `TEST_BREAK_PATTERN`, `TEST_LOG_LIMIT_KB`, `TEST_DUMP_CODE`), then per part `ENABLED` and its own keys: `HEAP_SIZE` 2000 (1..2047), `MODKITARRAY_SIZE` 65536 (1..65536), `PACKFILEARRAY_SIZE` 13000 (1..65535), `TRAVERSAL_LIST_SIZE` 10000 (1000..100000), `DECALDEFS_SIZE` 2048 (260..16384), `MODS_FOLDER`, `OPEN_RPF`, `SKIP_RPF_CACHE_CHECK`, `SKIP_SPLASH_SCREEN`, `SKIP_LEGAL_SCREEN`, `SKIP_LANDING_PAGE`, `UNLOCK_FILES`, all on. `kIniLayoutVersion` is 2. A `static_assert` on `IniKeyCount()` pins the layout at 28 keys in the file: a new key means a new layout number.

`FindSetting(section, key)` is `consteval`: it returns the table entry, and a name that is not in the table does not compile. Every part reads its settings through a named reference made that way (`kHeapSize`, `kModkitArraySize`, `kPackfileArraySize`, `kTraversalListSize`, `kDecalDefsSize`, `kModsFolder`, `kOpenRpf`, `kSkipRpfCacheCheck`, `kSkipSplashScreen`, `kSkipLegalScreen`, `kSkipLandingPage`, `kUnlockFiles`, `kEnabled`, `kLog`, `kDiagnosticMode`, `kDryRun`, `kConsole`, `kErrorPopup`, `kConflictCheck`, `kIniVersion`, the three test keys); the functions that work on the whole table (`IsFeatureOn`, `DescribeSettings`, `DefaultIniText`, the missing-key check of section 5.3) iterate `kSettings`.

`LoadSettings()` reads every entry once through `ReadIniValue` (a build that is not the test build skips the three test keys) and keeps the values in one array; afterwards nothing reads the file again. There is no in-game panel and no reload key, by my choice: the parts patch the game before it runs, so a setting changed live would change nothing. A value is parsed by its kind: a switch accepts `1`, `0`, `true`, `false`, `yes`, `no`, `on`, `off` in any case; a number is parsed with `wcstoll`, clamped to its limits with a reported problem when it lay outside, and a value that is no number is reported and the default used; a text is kept as it is. The report lines are `TweaksV.ini: [SECTION] KEY=value is not a valid on/off value - using 1.`, `... is not a number - using 2048.` and `... is outside 260..16384 - using 16384.`. A `VERSION` above 2 is reported as a file from a newer TweaksV. The readers: `IsOn(setting)`, `GetNumber(setting)`, `GetText(setting)`, `IsDryRun()`, `IsDiagnosticMode()`; `IsFeatureOn(section)` is the section's `ENABLED` unless `DisableFeatureForSession(section)` switched the part off (the conflict check does that); `DefaultIniText()` builds the default file from the table (section 5.4); `DescribeSettings()` builds the header's `Features:` line and one line per part with its values (section 6.2).

### 4.2 Patterns (`TweaksVPatterns.h`)

A `GamePattern` is `{ label, text }`: the label is the one PATTERNS.md gives the pattern (`H-E1`, `P-E-R31a`, `D-E-L12`, ...), the text its bytes in hex with one space between them and `?` for any byte. `kPatterns` lists every pattern once, in the order of PATTERNS.md, grouped per part with a comment that says what the group's matches hold. Two `consteval` checks run when TweaksV is compiled: `PatternsAreValid()` (every text is well-formed hex and wildcards, every label is unique) and `Pattern(label)`, the only way the code names a pattern, which returns the table entry and refuses to compile for a label that is not there. The `patterns` test suite checks that PATTERNS.md lists exactly the table's patterns with the same bytes, and that the code uses each one exactly once (section 14.2). The table holds 92 patterns. 1.0.1158.16 uses 89 of them (the packfile part chooses one of three direct-size patterns and one of two references by build), and the check boot (`DIAGNOSTIC_MODE=1` and `CONSOLE=1`, every part on, with or without `DRY_RUN=1`) finds all 89; a normal boot looks for fewer (`R-E-C1` only with `CONSOLE=1`, `R-E-F1..F8` only with a mods folder in the game's current directory or with `DIAGNOSTIC_MODE=1`).

### 4.3 Features (`TweaksVFeatures.cpp`)

A `Feature` is `{ section, oldPlugins[3], start }`: the part's section (its `ENABLED` switch and its name), up to three stand-alone `.asi` files that did its job before TweaksV, and the function that starts it, which returns true if the part shows the start-up summary itself later. `kFeatures` lists the parts in the order of `kSections` (checked by a `static_assert`):

| Part | Old plugins | Start |
|---|---|---|
| HeapAdjuster | `HeapAdjuster.asi`, `ZHeapAdjuster.asi` | `InitHeapAdjuster()` |
| ModkitLimit | `ModkitLimitAdjusterEnhanced.asi` | `InitModkitLimit()` |
| PackfileLimit | `PackfileLimitAdjusterEnhanced.asi` | `InitPackfileLimit()` |
| BoxStreamer | `DecalPatch.asi` | `InitBoxStreamer()` |
| Decals | `DecalPatch.asi` | `InitDecals()` |
| RageOpenV | `RageOpenV.asi`, `OpenRPF.asi`, `OpenIV.asi` | `InitRageOpenV()`, true when its hook is on: the start-up at the first time request shows the summary (false when the hook failed, and `DllMain` shows it) |
| StraightToStoryMode | `StraightToStoryMode.asi` | `InitStraightToStoryMode()` |
| DirectStorage | `DirectStorageFix.asi` | `InitDirectStorage()` |

`StartFeatures()` calls each start function whose part is on, each inside its own `try`: an exception ends only that part, reported as `unexpected exception - this part is skipped for this session`. `Features()` hands the table to the conflict check.

## 5. TweaksV.ini

### 5.1 Where it is

`GetGameFolder()` is the folder of the running program, found once from its path. `GetFallbackFolder()` is `%LOCALAPPDATA%\TweaksV`, empty when `LOCALAPPDATA` is not set. The file in use (`GetIniPathW()`): the game folder's `TweaksV.ini` if it exists, else the one in the fallback folder if that exists, else a new file - in the game folder, or in the fallback folder when the game folder cannot take it. A file in the game folder always wins; the header says when an unused copy sits in the fallback folder.

### 5.2 The own-file checks (`TweaksVFiles`)

TweaksV writes only to its own files, `TweaksV.ini`, `TweaksV.log`, `TweaksV.old.ini` and the test-build dumps, and only where each is what its path says: a plain file directly in the folder it belongs in. A link in its place could otherwise make TweaksV write to another file, which matters when the game runs as administrator. `FileFolder` says which kind of folder the file is in: `Game`, which may itself be a link (an install moved to another drive), or `Own`, TweaksV's folder in `%LOCALAPPDATA%`, which may not. `Check` refuses a file that is a reparse point, a folder, a hard link (more than one name for the same file), a file whose folder is a reparse point where that is not allowed, a file whose final path (`GetFinalPathNameByHandleW`, every link followed) is not the folder's own final path plus the name (compared case-insensitively), and a file whose attributes, folder or final path cannot be read at all. An `OwnFile` result carries the handle, the Windows error if the open failed, and `unsafe`, the reason the file is not what its path says; `ReadOnly()` tells a read-only folder (`ERROR_ACCESS_DENIED`, `ERROR_WRITE_PROTECT`) from every other failure, because a read-only game folder is normal and only logged. `FinalPathOf(path)` gives the final path of any existing file or folder the same way, empty if it cannot be read; RageOpenV compares the current directory with the game folder by it (section 11.6). `FileExists(path)` says whether a file, not a folder, is there - for the places of `TweaksV.ini`, the conflict check and DirectStorage's note on `DirectStorageFix.asi`.

- `OpenOwnFile(folder, name, where, disposition, truncate)` opens for writing with `OPEN_ALWAYS` or `CREATE_NEW`, the link itself and never its target (`FILE_FLAG_OPEN_REPARSE_POINT`), checks, deletes a file it created itself when the check fails, and empties a file that passes when asked.
- `HoldOwnFile(folder, name, where)` opens an existing file for reading without delete sharing: while the handle is open, nobody can rename, delete or replace the file or rename a folder above it, so the Win32 INI functions that open it by its path reach this very file.
- `RenameOwnFile(folder, name, newName, where)` renames through a handle on the file after the same check; a file already at the new name is replaced only when it passes the check itself, otherwise nothing is renamed.

### 5.3 Creating, updating, replacing (`TweaksVIni`)

`CreateOrUpdateIni()`:

1. An existing file (game folder first, else fallback) is held (`HoldOwnFile`); one that fails the check is reported (`TweaksV.ini (<path>) is not used: <reason>. TweaksV uses its built-in defaults this session.`) and never read.
2. A held file without the key `VERSION` under `[TWEAKSV]` has the layout of TweaksV 1.x, whatever else it holds - a 1.6.0 file, an empty or damaged one, a layout-2 file whose `VERSION` line was deleted. Only the key names of that section are read to decide; no value of such a file is ever used. The hold is released, the file renamed to `TweaksV.old.ini` through `RenameOwnFile` (an older `TweaksV.old.ini` that passes the check is replaced), the default file written in its place with `CREATE_NEW`, held, and the problem reported once: `TweaksV.ini had the layout of TweaksV 1.x. It was renamed to TweaksV.old.ini and a fresh TweaksV.ini written with the default settings - set your values again.` A file that cannot be renamed is reported in its own words every boot (`... has the layout of TweaksV 1.x and could not be renamed to TweaksV.old.ini (<reason>). Delete or rename it yourself - TweaksV uses its built-in defaults until then.`) and not read; a renamed file whose replacement cannot be written is reported once (`TweaksV.ini had the layout of TweaksV 1.x and was renamed to TweaksV.old.ini, but a fresh TweaksV.ini could not be written in <folder> (<reason>). TweaksV uses its built-in defaults this session.`), and the next boot starts without a file (step 4).
3. A held layout-2 file gets every key of the table it is missing, written with its default through `WritePrivateProfileStringW` and logged (`TweaksV.ini: added the missing key [SECTION] KEY=value.`); a key that cannot be added is logged when the file is read-only and reported otherwise. Existing values are never changed.
4. No file anywhere: the default file is written in the game folder; if that fails, in the fallback folder (the folder is created) - a read-only game folder is only logged (`The game folder is read-only (...), so TweaksV.ini was created with the default settings in <folder>.`), any other reason is reported; if both fail, the built-in defaults are used and reported.

The file stays held until `ReleaseIniFile()`, which `LoadSettings()` calls once every value is read. `ReadIniValue(section, key)` reads at most 255 characters of a value, trimmed of spaces and tabs, through `GetPrivateProfileStringW`, and nothing when the file is not in use. `DescribeIniLocation()` gives the header its `TweaksV.ini:` line: the path, and in parentheses whether the 1.x file was renamed and this fresh file written, whether the game folder has no file, whether this file wins over an unused copy in the fallback folder, or why the file is not used.

### 5.4 The default file

`DefaultIniText()` builds the file from the table: the header comment, then every section with a blank line before it and its keys in table order, CRLF line endings. It is exactly this, and the `ini_default` suite compares byte for byte with `test\expected_default.ini`, which is kept with LF endings and given CRLF by the suite before the comparison:

What each key does is README's table. The two testing switches: `DRY_RUN=1` makes every part find and check everything, logging what it would change, and nothing in the game is written or hooked (only RageOpenV's one-shot hook on `GetSystemTimeAsFileTime`, which runs its checks and switches itself off); `DIAGNOSTIC_MODE=1` makes every part that is on log every site it finds, the value it holds and every write, run its measurement where it has one, and makes the scanner log a line per pattern. A part with `ENABLED=0` does nothing at all, so a diagnostic check of every pattern needs every part on. `DIAGNOSTIC_MODE=1` with `DRY_RUN=1` is the quiet check after a game update; `DIAGNOSTIC_MODE=1` alone is the full measurement of the running game, which hooks a little more than a normal boot (the box streamer's four search calls, DirectStorage's configuration calls - and its factory and `OpenFile` with `UNLOCK_FILES=0` - and the file opens).

## 6. TweaksV.log and the start-up summary

### 6.1 The log file

`WriteLog(tag, text)` appends one line, `hh:mm:ss.mmm [Tag] text`, to `TweaksV.log` and to the console when one is open. It is thread-safe (one `SRWLOCK`, held through the guard of `TweaksVLock.h`, which an exception releases too, so no failure can leave the lock taken and the next line waiting forever), lines longer than 2 KB are cut and end in `...`, and every mention of the Windows user's profile folder is written as `%USERPROFILE%` - also in its short form (`C:\Users\NAME~1`), as `%TEMP%` often has it - because logs get posted in public and that folder is usually named after the user. Lines written before the log is started (up to 1024) are kept and written after the header. The file grows to 64 MB at most; the last line then says `TweaksV.log has reached its limit of 64 MB - nothing more is written to it this session.`, and the console still gets every line.

`ClearLogFile()` starts the file each session, truncated: in the game folder through `OpenOwnFile`, else - the folder read-only, a link in the file's place, the file in use by another program - in `%LOCALAPPDATA%\TweaksV`. A read-only game folder is logged; any other reason for the fallback, and no file at all, are problems. `LOG=0` writes no file. `GetLogPathW()` is the path in use, which the message boxes print - with `LOG=0`, `(off - LOG=0)` in its place.

### 6.2 The header

`WriteLogHeader()` writes, all tagged `[TweaksV]`:

```

TweaksV.asi: <path>
Game: <path>, file version 1.0.1158.16, PE timestamp 0x6AA45F10 (<UTC date>)
TweaksV.ini: <path> (<notes, section 5.3>)
TweaksV.log: <path>
mods folder: <game folder>\mods (present | not present)
Features: HeapAdjuster on, ModkitLimit on, PackfileLimit on, BoxStreamer on, Decals on, RageOpenV on, StraightToStoryMode on, DirectStorage on
TweaksV: LOG=1 DIAGNOSTIC_MODE=0 DRY_RUN=0 CONSOLE=0 ERROR_POPUP=1 CONFLICT_CHECK=1 VERSION=2
HeapAdjuster: HEAP_SIZE=2000
ModkitLimit: MODKITARRAY_SIZE=65536
PackfileLimit: PACKFILEARRAY_SIZE=13000
BoxStreamer: TRAVERSAL_LIST_SIZE=10000
Decals: DECALDEFS_SIZE=2048
RageOpenV: MODS_FOLDER=1 OPEN_RPF=1 SKIP_RPF_CACHE_CHECK=1
StraightToStoryMode: SKIP_SPLASH_SCREEN=1 SKIP_LEGAL_SCREEN=1 SKIP_LANDING_PAGE=1
DirectStorage: UNLOCK_FILES=1
```

The version and the git hash come from `BuildInfo.h` (section 15): a build from a tree with uncommitted changes carries `-dirty` after the hash, a build from a folder that is not a git repository says `unknown`. A test build adds `TEST BUILD - not for release. TEST_BREAK_PATTERN=... TEST_LOG_LIMIT_KB=... TEST_DUMP_CODE=...`. A part that is off says `off` in the `Features:` line; its values line still follows, and the part itself logs nothing.

### 6.4 Problems and the start-up summary (`TweaksVSummary`)

`ReportFailure(tag, what)` logs `PROBLEM: <what>` under the part's tag and keeps the item (`[Tag] what`) for the start-up summary, at most 40 items, the rest counted; the list is kept under a lock held through the same guard, with the item built before the lock is taken. `ShowStartupSummary()` runs once: with nothing to show it logs nothing; otherwise, with `ERROR_POPUP=0`, it logs `Start-up summary not shown (ERROR_POPUP=0): N problem(s), see above.`, and with `ERROR_POPUP=1` it logs `Showing the start-up summary (N problem(s)).` and shows one message box, `TweaksV could not apply everything:`, with one bullet (`•`) per item, `• ... and N more.` when items were dropped, the line `The game continues without the affected parts. Details are in TweaksV.log:` with the path on the next line (`(off - LOG=0)` with `LOG=0`), and `To stop this message, set ERROR_POPUP=0 in TweaksV.ini.` `ShowStartupSummaryLater()` does that from a thread of its own, which holds a reference to the module while it runs, because a message box must not block `DllMain` or the game's thread that first asks for the time. `StartModuleThread(thread, what)` starts such a thread - this one, the one for problems after the summary (below), RageOpenV's start-up check, DirectStorage's checks and its `OpenFile` summary, and the measurements' threads (section 6.6), which never end and keep it - with the extra reference to the module, which the thread drops when it ends; one that cannot start is logged, `The <what> thread could not be started (Windows error N).`; when that is the start-up summary's own thread, every problem of the session stays in the log alone (NOTES.md, T-SUMMARY). Both threads of this module run inside a `try`: a box that cannot be built is logged (`Unexpected exception while showing the start-up summary - the box is not shown; the problems are logged above.`) and skipped, and the next late problem starts a new thread.

A problem reported after the summary was shown - a part that stops working later, such as DirectStorage's `OpenFile` hook a few seconds in - is shown by a thread of its own a second later, with the heading `TweaksV: a part stopped working after the start-up:`, at most three such boxes per session, a list of more than 40 ending in `• ... and N more.`; after that, and with `ERROR_POPUP=0`, such problems are only logged. Test builds show no box while the environment variable `TWEAKSV_TEST_NO_BOXES` is `1` and log `TEST BUILD: message box not shown (TWEAKSV_TEST_NO_BOXES=1): <heading>` instead, so the test suites never wait on one.

### 6.5 The console

`CONSOLE=1` opens a console window (`AllocConsole`) once the header is written, and it mirrors every log line from `Console opened (CONSOLE=1).` on; the RageOpenV part then NOPs the game's call that would hide it (section 11.6). The console is a testing aid: when it cannot be opened or kept, the log says so and nothing is reported.

### 6.6 The measurements (`TweaksVMeasure`)

`DIAGNOSTIC_MODE`'s four measurements - the box streamer's searches, the decal definitions registered, RageOpenV's file requests and archive headers, DirectStorage's opens in the game folder - share one loop. A part describes its measurement as a `Measurement { thread, firstMs, numbers, summary }` - the thread's name, when the first summary comes, a function whose number changes whenever the summary has something new to say, and the function that writes the summary, given that number - and starts it with `StartMeasurement`, which starts its thread through `StartModuleThread` (section 6.4); the thread never ends, so it keeps its reference to the module. The thread writes the first summary `firstMs` in - `kFirstSummaryMs`, 10 seconds, or `kSummaryEveryMs`, a minute, for DirectStorage's open summary - always, and then one every minute while the number changes, inside a `try`, so nothing leaves the thread. A measurement whose thread cannot start is logged (`The box streamer summary thread could not be started (Windows error 8).`, the names being `box streamer summary`, `decal definitions summary`, `RageOpenV summary` and `DirectStorage open summary`), not reported: it is a diagnostic aid (section 12). `kMaxLinesPerKind`, 20,000, is the cap of every kind of line that comes per event (section 12).

## 7. The conflict check (`TweaksVConflicts`)

`CheckForConflicts()` looks in the game folder and its `scripts` and `plugins` subfolders - the three places an ASI loader loads from, `kLoaderFolders` in `TweaksVConflicts.h`, which DirectStorage's look for `DirectStorageFix.asi` uses too - for every old plugin of every feature (section 4.3). Each one found switches its part off for the session (`DisableFeatureForSession`) and is reported: `Old plugin found: <path>. TweaksV's <Feature> part is switched off for this session so nothing is patched twice. Delete the old file - TweaksV replaces it.` `DecalPatch.asi` is the old plugin of two parts and switches both off. With none found the log says `Conflict check: none of the old plugins TweaksV replaces were found.` `IsInsideGameImage(p)` is the shared test for an address inside `GTA5_Enhanced.exe`'s image, from its PE headers read once.

## 8. The scanner (`TweaksVScanner`)

The scanner finds TweaksV's patterns in the running game's code. `GTA5_Enhanced.exe` is encrypted on disk, so the code is only readable in memory, and a game update changes it: what the scanner finds is the one thing that must be maintained after an update (PATTERNS.md, "When Game Updates").

- The image is read once: `GTA5_Enhanced.exe`'s base and size from the module information, its executable sections from the PE headers (read only where they lie inside the image; with no executable section the whole image is searched).
- Every search reads the readable parts of those sections afresh (`ReadableCode`: `VirtualQuery` over each section, committed and readable pages only, neighbouring regions joined), because TweaksV itself changes protections between two searches and a page the game protects must be skipped, not crash the game.
- A pattern's text is parsed into bytes and a mask (`ParsePattern`: tokens of exactly two hex digits, or `?`; any other token, or a text of wildcards only, refuses the pattern - nothing in the parser can throw - logged as `Pattern <label> is not valid (treated as not found): <text>`), and compiled with the positions of its two rarest fixed bytes, rarest by how often each byte occurs in the first 256 KB of the game's code (`ByteCounts`, read once). This only changes how fast the search is, never what it finds.
- `FindIn` compares those two bytes at 16 positions at a time with SSE2 and checks the whole pattern only where both match; a match must lie wholly inside one readable range.
- `Scanner::Find(pattern)` returns the one match or `nullptr`: it asks `FindAll(pattern, 2)`, and a pattern that matches twice is not used, because what would be written over cannot be known - logged as `Pattern <label> matches 2 or more times - not used (the site must be unique).`, and the part gives its `<label> was not found.` as for a miss (the heap, the three screens, RageOpenV's patterns); `Scanner::FindAll(pattern, limit)` returns every match in address order up to `limit` (a site the game must have exactly n times is asked for n + 1, so that an n + 1th match shows); both log a miss as `Pattern <label> not found: <bytes>` and, with `DIAGNOSTIC_MODE`, the line of section 6.3 with the RVA, the number of matches (exact up to 99, `100+` from 100 on) and the bytes of the match, 32 at most, plus one line for each of the first ten matches with 16 bytes before and 48 from its start, for a pattern that matches more than once, so that a longer pattern can be chosen that matches only the place it is meant for. The scanner's tag is `[Scanner]`.
- `Scanner::FindRipRelativeLeas(target, limit)` finds every `lea r64, [rip+disp32]` (a REX prefix with the W bit, opcode `8D`, ModRM mod 00 r/m 101: 7 bytes) in the readable code whose displacement leads to `target`, in address order up to `limit`, with the same 16-at-a-time comparison on the opcode and ModRM bytes. It is how the relocation core finds the loads of an array the game loads in places no pattern can tell apart. `Scanner::FindRipRelativeReferences(target, limit)` is the same search for every `lea r64, [rip+disp32]` and every `mov [rip+disp32], r64` (the same prefix and ModRM, opcode `8D` or `89`), one helper behind both: how the core checks that the references an array's patterns name are all the game has. Nothing is logged.
- Test builds: `TEST_BREAK_PATTERN=<label>` makes that pattern count as not found (`TEST BUILD: pattern <label> is treated as not found (TEST_BREAK_PATTERN).`), to watch its part be skipped cleanly.

The pattern parser is an altered version of ScriptHookVDotNet's memory scanner (THIRD_PARTY_NOTICES.md); the search is TweaksV's own.

## 9. The patch module (`TweaksVPatch`)

Every change to the game's code goes through this module, so that every part writes the same way and no part has to know about page protection, `DRY_RUN` or `DIAGNOSTIC_MODE`.

- **`WriteCode(writes, tag)`**: `writes` is a list of `CodeWrite { address, bytes, what }`. A write without address or bytes stops everything. With `DRY_RUN` nothing is written and each write is logged as `DRY_RUN: would patch the <what>: <old> -> <new>`. Otherwise every page any write touches is made writable first (`PAGE_EXECUTE_READWRITE` for a page that was executable, `PAGE_READWRITE` otherwise; a page that is already writable is left; a page that is not committed memory, a guard page, or one `VirtualProtect` refuses stops everything before a byte is written, with the protections changed so far put back, and the reason logged), then all bytes are written, then every page gets its own protection back, newest first - through a guard that runs on every exit, an exception included; nothing that can throw runs while a page is writable, so the old bytes for the log are read before and the lines written after - and `FlushInstructionCache` makes the processor see the new code; with `DIAGNOSTIC_MODE` each write is logged as `DIAGNOSTIC: <what> at <address>: <old> -> <new>`. False means nothing was written. `BytesOf(value)` gives the bytes of a value for a write.
- **`RedirectCalls(redirects, alsoWrite, tag)`**: `redirects` is a list of `CallRedirect { site, function, what, original }`, each a 5-byte relative call (`E8 rel32`) in the game to send to `function`; `original`, when given, receives the function the call led to, and is set before the call is rewritten, so a hook that calls it is ready the moment it can run. A site that is not a call stops everything. With `DRY_RUN` each is logged as `DRY_RUN: would redirect the <what> at RVA ...` and only `WriteCode(alsoWrite)` runs, which writes nothing either. Otherwise: a block of 16 bytes per call is allocated near the game (`AllocateNearGame`, read/write), each stub written as `FF 25 00 00 00 00` followed by the 8-byte address of `function` and two `CC`, the block made read+execute and never changed again (a call stub is never writable and executable at once), and then, in one `WriteCode`, every call's rel32 pointed at its stub together with `alsoWrite`. A call reaches only 2 GB, which is why the stubs sit near the game; a stub out of reach, no memory near the game, or a block that cannot be made read+execute stops everything with nothing changed.
- **`HookFunctions(hooks, tag)`** hooks functions at their start with MinHook: `FunctionHook { function, hook, original, what }`; every hook is created and queued, then all are switched on together (`MH_ApplyQueued`: the threads are frozen once per group, not once per hook); if any step fails, the hooks made so far are removed again and the reason logged: `<what> could not be hooked (MinHook: <status>)` when a hook cannot be created or queued, `The N hooks could not be switched on (MinHook: <status>)` when they cannot be applied, with ` - none of the N hooks is on.` for a group of more than one. `original` receives MinHook's trampoline. **`HookExport(module, function, hook, original, target, tag)`** hooks an exported function of a loaded DLL at once (`GetSystemTimeAsFileTime`, DirectStorage's exports, `NtCreateFile`) and hands back its address in `target`; **`DisableHook(function, tag)`** switches a hook off again, the function's own bytes back and the trampoline kept for a thread that is inside the hook right now. MinHook is initialised on first use; its trampolines are writable and executable, an accepted open issue (NOTES.md, T-HARDEN).
- **`AllocateNearGame(size)`**: `size` bytes, read/write, committed and zeroed, within 1 GB below the game's image, where a rel32 in the game's code reaches: the free regions below the image are walked by allocation granularity, as MinHook's own allocator does, and the first that gives `size` bytes is taken. For the moved arrays and the call stubs.
- The readers: `CallTarget(site)` (the target of an `E8 rel32`, or `nullptr`), `Rel32Target(address)` (where a rel32 or a rip-relative disp32 at that address leads), `StartsWithJump(address)` (`E9`, `EB` or `FF 25`: the usual sign of another mod's hook), `IsFunctionStart(address, detail)` (the game's unwind data, asked of Windows with `RtlLookupFunctionEntry`, says so - `a function start (unwind data)`; an address inside a function gives `inside the function at RVA ... (unwind data)`; for code without unwind data the byte before it, read only where it is readable (`no unwind data, the byte before it cannot be read`), must be `CC`, `90` or `C3` - `no unwind data, byte before it CC`), `IsReadable(address, size)` (committed, readable, no guard page, over the whole range; used before any byte outside a pattern's match is read), `DescribeAddress`, `HexBytes`.

## 10. The relocation core (`TweaksVRelocation`)

Four parts move one of the game's static arrays to a larger one and raise the limit the game's code carries for it: the modkit array, the packfile array, the box streamer's traversal list, the decal definitions array. They describe their array in tables; the core does the work once for all of them.

### 10.1 The tables

- `ReferenceSite { offset, opcode, opcodeSize }`: where a match holds the rel32 of a `lea r64, [rip+disp32]` or of a rip-relative `mov` that addresses the array, so that the array is the address after the rel32 plus its value; `opcode` are bytes the instruction must start with, right before the rel32, or none.
- `LimitSite { kind, offset, opcode, opcodeSize, valueOffset, mul, add }`: `Immediate`, an imm32 at `valueOffset` that holds `N x mul + add` with N the array's size, or `Variable`, the rel32 at `valueOffset` of a variable the game compares against, which holds `N + add`; `offset` is the instruction, `opcode` its first bytes, or none.
- `Anchor { pattern, matches, hasReference, reference, limitCount, limits[3] }`: a pattern of the part, how often it must match (1, or more for a site the game repeats), and what every match holds: a reference, up to three limits, both, or neither - a site the part reads itself through the plan. The builders: `Rel32(offset, opcode, opcodeSize)`, `Imm32(imm32, mul, add)`, `Imm32(instruction, opcode, opcodeSize, imm32, mul, add)`, `Variable(rel32, add)`, `Site(pattern)`, `Reference(pattern, site)`, `Limit(pattern, site)`, `Limits(pattern, matches, a, b[, c])`, `Repeated(pattern, matches, limit)`, `ReferenceAndLimit(pattern, ref, limit)`.
- `RelocationSpec { tag, name, sizeName, job, entrySize, maxEntries, setting, anchors, scannedReferences, leaPrefixes, leaPrefixCount, expectedReferences }`: the part's log tag, the array's name for the log (`modkit array`, `box streamer's traversal list`), the name of its size (`modkit list size`), the start of every failure line (`The modkit limit is not changed`), the bytes per entry, the new array's size (always allocated in full, and the setting's maximum), the setting that asks for the size, the anchors, for an array whose loads no pattern can tell apart exactly how many `lea` must load it, found by its address, with the REX bytes they may start with (`48` or `4C` for the decals; any with REX.W for the box streamer), and for an array moved by its anchors' references how many references the game's code has to it (`expectedReferences`: 6 for the modkit array, 33 for the packfile array; 0, not checked, for the other two).
- `RelocationPlan { array, gameSize, size, matches, references, limits }`: what was found: the game's own array, its size, the size to use, every anchor's matches (for the sites a part reads itself), the rel32 fields that are moved, the limits as `FoundLimit { value, mul, add }`.

### 10.2 `FindRelocation(spec, plan)`

Everything is found and checked before anything is written, and the first failure reports `<job> this session: <why>` and leaves the game as it is. A spec whose tables name no reference, or no limit, is refused as the part's own mistake. The anchors are worked through in table order - each one's matches, then for each match its reference and its limits - so a missing pattern late in the table is reported only after the sites before it passed:

1. The anchor must match exactly as often as it says (`FindAll` asks for one more): `<label> was not found.` or `the game code holds <label> N [or more] times, not the expected M.` (` or more` when more were found than expected).
2. Its reference: the instruction is readable and starts with the opcode when one is given (`is not the expected instruction (<bytes>)`); its target is logged with `DIAGNOSTIC_MODE` (`DIAGNOSTIC: reference at RVA ... -> RVA ... (<label>)`); the first reference's target must lie inside the game (`the <array> is not inside the game: <address> (another mod may have moved it already).`), every other must point at the same address (`the references to the <array> do not all point to the game's own array: <a> and <b> (<label>).`).
3. Its limits: readable, the expected instruction; a variable must lie inside the game; its value decodes to N through its encoding (`holds V, which is <encoding> for no size` when it does not divide), logged as `DIAGNOSTIC: limit[ variable] at RVA ... holds V (<encoding>, <label>) -> game size N`; the first size decoded in the whole job must be plausible (`the game's own <sizeName>, N, is not plausible.` beyond `maxEntries` or zero), every other must agree (`the limits of the <array> disagree about the game's own size: A and B (<label>).`).

Then:

4. The array is logged: `DIAGNOSTIC: the <array> is at RVA ... - N entries of E bytes`.
5. The references that are moved: the anchors' references, or - with `scannedReferences` - every `lea` that loads the array (`FindRipRelativeLeas`, each logged as `DIAGNOSTIC: reference at RVA ... -> RVA ... (lea scan)`), which must be exactly that many (`the game code loads the <array> in N [or more] places, not the expected M (another mod may have moved some of them, or the game has changed).`) and each start with an allowed prefix (`the load of the <array> at RVA ... is not a "lea r64, [rip+disp32]" with a 48 or 4C prefix: <7 bytes>.`).
6. With `expectedReferences`, the anchors' references must be every one the game has, because one no pattern names would keep the game's own, smaller array while the limits are raised: `FindRipRelativeReferences` (each site logged with `DIAGNOSTIC_MODE` as `DIAGNOSTIC: reference at RVA ... -> RVA ... (scan)`, the RVA of its rel32, as the anchors' lines have it) must find exactly that many (`the game code holds N [or more] references to the <array>, not the expected M (another mod may have moved some of them, or the game has changed).`), and every one must be an anchor's rel32 (`the reference to the <array> at RVA ... is not one its patterns name (another mod may have moved some of them, or the game has changed).`).
7. The size to use: the setting, clamped to the game's own size..`maxEntries`, reported when it lay outside (`TweaksV.ini: <KEY>=x is outside A..B - using C.`, `ReportFailure`), so that the start-up summary names the size really used - the settings' own report (section 4.1) names only the table's limits. Smaller than the game's own would shrink the array.

### 10.3 `ApplyRelocation(spec, plan, alsoWrite, redirects, also)`

With `DRY_RUN`: `DRY_RUN: would move the <array> (N references) and raise its limit from A to B (M sites)<also>.` and nothing else. Otherwise the game's own entries must be readable (`the game's own <array> cannot be read.`), the new array is allocated in full (`entrySize x maxEntries`, `AllocateNearGame`; `the new <array> could not be allocated near the game.` when that fails) and the game's own entries are copied into it, the rest staying zero - so an array the image initialises keeps its content - every reference's rel32 is recomputed for it with the int32 distance check (`the new <array> is out of reach of the game code at RVA ...`), every limit is re-encoded for the new size (`N x mul + add`), the part's own writes are added, and all of it is written in one `WriteCode` - or, when the part redirects calls too, one `RedirectCalls` - all or nothing (`the game code could not be changed (details in TweaksV.log).` when not). Then `The <array> moved and its limit raised from A to B entries.` The write lines carry `<array> reference` and `<array> limit` as their `what`.

What does not fit the core stays in the part's file and uses the plan: the packfile's hooked call, the box streamer's counted calls, the decals' count, loop and measurement (section 11).

## 11. The parts

Each part reads its switches once, at its start-up (RageOpenV's runs inside its one-shot time hook); the hooks that run per call never read them. The game facts - the patterns, what each match holds, the offsets - are PATTERNS.md's; NOTES.md lists each part's behaviour and measurements. Here is the mechanism.

### 11.1 HeapAdjuster (`InitHeapAdjuster`)

The game sizes its memory heap with one immediate in its start-up code: the imm32 of a `mov edx, imm32` that `H-E1` matches, the size in bytes at +1. `HEAP_SIZE` in MB, 1..2047 - the most whole MB that imm32 holds as a positive int32. Steps: the match must start with `BA`; the value must be a whole number of MB other than 0 (`the game code found holds an unexpected value (0x...)`), logged with `DIAGNOSTIC_MODE` as `DIAGNOSTIC: heap size at RVA ... holds 646 MB`; a value of 1024 MB or more - up to 4095 MB, since the `mov` zero-extends its imm32, past what `HEAP_SIZE` allows too - is not the game's own (646 MB on the current build): another heap adjuster set it, and the part leaves it, logs `The heap size is not changed this session: another heap adjuster already set it to N MB - left as it is.` and reports nothing; the size to use is the setting clamped to the size found..2047, reported when it lay outside (`TweaksV.ini: HEAP_SIZE=100 is outside 646..2047 - using 646.`), so that the start-up summary names the size really used; a heap that already has the size asked for is logged and left (`Heap size is 646 MB already (HEAP_SIZE=100) - nothing to patch.`); otherwise one `WriteCode` of the new imm32, computed in 64-bit arithmetic, `what` = `heap size (A MB -> B MB)`, then `Heap size patched: A MB -> B MB.` Failures: `The heap size is not changed this session: H-E1 was not found.`, `... the game code found is not the expected instruction (<bytes>).`, `... the game code could not be made writable (details in TweaksV.log).`

### 11.2 ModkitLimit (`InitModkitLimit`)

The game's array of vehicle modkit IDs: 1024 entries of 2 bytes on the current build, loaded by six `lea` (`M-E-R1..R6`, the rel32 at the offset PATTERNS.md gives) and sized by eight immediates (`M-E-L1..L8`: N-1, N+3, N+3, N+3, N+3, 2N, N-1, N-1; `M-E-L2`'s, which lies past its pattern, checked as the imm32 of `cmp rdi, imm32`, `48 81 FF`). Entirely on the core: spec `{ "ModkitLimit", "modkit array", "modkit list size", "The modkit limit is not changed", 2 bytes, 65536 entries, MODKITARRAY_SIZE, the 14 anchors, no scanned references, 6 expected references }` - the six leas must be every reference the game's code has to the array; `FindRelocation`, then `ApplyRelocation` with nothing of its own. Modkit IDs are 16-bit, which caps the array at 65536.

### 11.3 PackfileLimit (`InitPackfileLimit`)

Another interface, whose functions TweaksV does not know, asked for once the hook was tried is a line, once a session: `The game also asked for another DirectStorage interface, {...}, whose functions TweaksV does not know - left as it is.` Asked for before, it starts (once) a check, a thread of its own (`StartModuleThread`; one that cannot start is logged and, with `UNLOCK_FILES`, reported: `The check of the other DirectStorage interface the game asked for, {...}, is not done this session: its thread could not be started (details in TweaksV.log).`), which 10 seconds later writes that line if the hook has been tried by then - the known interface asked for in the meantime - and otherwise reports `The files in the game folder are not unlocked this session: the game asked only for another DirectStorage interface, {...}, whose functions TweaksV does not know.` (a log line without `UNLOCK_FILES`). With `UNLOCK_FILES`, a thread started with the hook (`StartModuleThread`; one that cannot start is logged) waits 30 seconds and, if the game has not called `DStorageGetFactory` by then, reports `The files in the game folder are not unlocked this session: the game has not asked for its DirectStorage factory since TweaksV started - TweaksV may have been loaded too late.`, a problem after the start-up summary, which gets a box of its own (section 6.4).
- `HookOpenFile` decides before the game's call, on the stack - no memory allocation, no lock of TweaksV's, nothing that can throw: the path is copied safely (at most 2047 characters), `/` made `\` in the copy only, and made full in a second buffer - a `\\?\UNC\server\share` path, the prefix in any case, as the network path `\\server\share`, any other `\\?\` path without the prefix and as it is, as Windows takes it, and every other path through `GetFullPathNameW`, which makes it absolute from the current directory, as DirectStorage does, and collapses `.` and `..`; whether it lies in the game folder and ends in `.rpf` or `.cache` is decided on that full path. A path that cannot be read, is longer, or cannot be made full is passed on unchecked. A path inside the game folder that does not end in `.rpf` or `.cache` is refused with `UNLOCK_FILES` as `HRESULT_FROM_WIN32(ERROR_FILE_NOT_FOUND)` and a null interface, as for a file that is not there; every other path - the archives, and everything outside the game folder: the game reads its saves, `pc_settings.bin` and its cloud files through `OpenFile` - goes to DirectStorage's own function. Every call is counted in exactly one of five counts, with atomics: an archive in the game folder, a file refused, another file in the game folder opened (`UNLOCK_FILES=0`), a path outside the game folder, a path passed on unchecked; a refused file's type, its extension with the dot in lower case (`(none)` without one), is counted in a fixed table of 15 types that the game's threads fill with atomics, in the order the types come, a type past the 15th or one that does not fit 8 bytes counting as `others`. Ten seconds after the first call a summary line, from a thread of its own (`StartModuleThread`; one that cannot start is logged and, with `UNLOCK_FILES`, reported - `The UNLOCK_FILES summary is not written this session: its thread could not be started (details in TweaksV.log).` - and every later refusal then gets a line), gives the five counts, each read once and the total their sum: `UNLOCK_FILES: in its first 10 seconds the game asked DirectStorage for N files: A .rpf and .cache files were opened, R other files in the game folder refused, so they stay free for other programs[, O outside the game folder opened as usual][, U with an unreadable path passed on][; refused by type: .txt 4, .asi 1, (none) 1, others 2].` With `DIAGNOSTIC_MODE` alone, `OpenFile` is hooked for the log (`DIAGNOSTIC: the game's OpenFile calls are logged (OpenFile at ... hooked); UNLOCK_FILES=0, so every file is opened.`) and the summary reads `OpenFile: in its first 10 seconds the game asked DirectStorage for N files: A .rpf and .cache files, B other files in the game folder and C outside it[, U with an unreadable path passed on] (UNLOCK_FILES=0 - all of them opened).` A refusal after that summary gets a line of its own (`UNLOCK_FILES: refused locktest.txt (in the game folder, not .rpf or .cache).`); with `DIAGNOSTIC_MODE` every call does (`OpenFile #N: <name> -> ok | refused (in the game folder, not .rpf or .cache) | 0x...`, the first with its callers). Each of the two kinds stops after 20,000 lines, then the calls are only counted (`UNLOCK_FILES: 20000 lines of files refused after the summary written - from now on they are only counted.`, `DIAGNOSTIC: 20000 lines of OpenFile calls written - from now on they are only counted.`). A line names a path inside the game folder below it (`update\update.rpf`) and any other by a category and its file name only - `(outside the game folder) SGTA50000`, `(temp) cloud_tweaksv.dat` for one in `%TEMP%` (`GetTempPathW` and its long form, read at the start), `(network) cloud.dat` for a `\\server\share` path - so that no other folder, such as a profile's, reaches the log; an unreadable path is `(unreadable path)`. The name is made only for a line that is written.
- With `DIAGNOSTIC_MODE`, `DStorageSetConfiguration` and `DStorageSetConfiguration1` are hooked too, one hook for both (`DIAGNOSTIC: the game's DirectStorage calls are logged (N of 3 functions hooked).`), and each call into DirectStorage is logged with its caller and its values: `the game asked for the DirectStorage factory (call #N, interface {...}) -> ok, from ...`, with the factory's first eight functions (`DIAGNOSTIC: the factory's first 8 functions: [0] dstorage.dll+0x... ... [7] ...`, or `DIAGNOSTIC: the factory's function table could not be read.`), and `the game set the DirectStorage configuration (DStorageSetConfiguration) -> ok, from ...` with `DIAGNOSTIC: DStorageSetConfiguration values: ...` (7 values, 8 for `DStorageSetConfiguration1`).
- `NtCreateFile` in `ntdll.dll` is hooked with `DIAGNOSTIC_MODE` (`DIAGNOSTIC: every open of a file or folder in <game folder> is logged, 2 lines per file, caller and sharing; a summary follows every minute.`): every open inside the game folder is logged (`open #N: <relative path> | <status> | access 0x..., share RWD, open, options 0x... | from <callers>`, the callers being the first three frames outside TweaksV and the system DLLs), at most 2 lines per file, caller and sharing, 20,000 lines in all (`DIAGNOSTIC: 20000 open lines written - from now on the opens are only counted (see the summaries).`), and counted in four tables - the ways of opening (file, caller and sharing), the files, the callers and the types - of 100,000 entries each at most: an open a full table cannot take is only counted, said once (`DIAGNOSTIC: a table of the open summary is full (100000 entries) - the opens it cannot take are only counted (see the summaries).`). The measurement (section 6.6; its thread, if it cannot start, is logged as `The DirectStorage open summary thread could not be started (...).`) writes a minute in and then every minute while the count changes `summary: N opens of P files and folders in the game folder (S not shown above[, T not tracked: 100000 entries per table at most]); W file opens kept others from writing the file | by caller: ... | by type: ...` (at most 15 types, then `others N`).
- Every hook does its own work after the game's call through one helper, `AfterCall`: not on a thread that is inside a hook already (`t_inside`, so that nothing TweaksV opens there itself is logged), with the game's `GetLastError` kept and every exception caught.

## 12. The rules every part follows

- **Nothing is written before everything is found and checked.** Every site is found by pattern, every instruction's bytes are the expected ones, every address inside the game, every value plausible and consistent; the first thing not as expected ends the part's job with nothing changed.
- **All or nothing.** A job's writes go in one `WriteCode` or `RedirectCalls`: every page made writable first, every page given its own protection back, on an exception too; a part either does its whole job or leaves the game as it was. Hooks of one group are created and switched on together or removed again. The writes in `DllMain` happen while the game is still single-threaded; RageOpenV's start-up writes its few bytes - the cache check's `C3 90`, the console's NOPs, the five `E8 rel32` - on the game's thread at the first time request without freezing the other threads, as MinHook does for the hooks: an accepted window, since no other thread runs that code then (NOTES.md, T-FREEZE).
- **What another mod has already changed, TweaksV does not change again.** A heap another adjuster set, a cache check already skipped, a function already hooked (hooked on top, chained through) are left and logged; an array already moved, a call already redirected, a pattern that matches more often than it must are refused with the reason, because what TweaksV would write over cannot be known. The conflict check switches a part off entirely when its old plugin is installed.
- **Never silent.** Every job not done is a `PROBLEM` line in the log with the reason and an item of the start-up summary, which is a message box with `ERROR_POPUP=1`; a part that stops working after the start-up gets a box of its own. A switch that is off is logged in one line. A diagnostic aid that cannot be set up - the console, DirectStorage's call logging, a measurement whose thread cannot start (section 6.6) - is logged, not reported (NOTES.md, T-DIAG). `DRY_RUN` and `DIAGNOSTIC_MODE` work the same for every part, with one exception: with `DIAGNOSTIC_MODE=1` the box streamer refuses its whole job when a tree-search call cannot be redirected, because the measurement is the reason the switch is on (section 11.4).
- **Everything read is bounded and checked.** INI values are trimmed, limited to 255 characters, parsed and clamped; the mods list has limits on entries, depth and path length; paths from the game are read with a length limit, paths from DirectStorage copied with a length limit and a guard against unreadable memory; the entry table of an archive is walked only when its count is plausible; the scanner reads the PE header and the section table only where they lie inside the image, and unwind data is asked of Windows (`RtlLookupFunctionEntry`); the log cuts its lines and its file.
- **Nothing throws into the game.** Every hook puts what can throw - a log line, a table walk - inside a `try`, and so do the measurement threads and the two threads of `TweaksVSummary`; a lock is never left taken by an exception (`TweaksVLock.h`), nor a page of the game's code writable (the guard in `WriteCode`). The DirectStorage hooks, RageOpenV's ParseHeader hook and its OpenBulk hooks' lines keep the game's last error; the other hooks call the game's function last, so the game's own error stands. `DllMain` catches everything on attach and returns `TRUE`.
- **Nothing per frame beyond the game's own work.** The hooks on hot paths (the file functions, the tree searches, DirectStorage's `OpenFile`) do one path spelling and one hash lookup, one count with atomics, or one path made full on the stack (`GetFullPathNameW`) and its counts with atomics - no allocation, no lock of TweaksV's, no file system call; the `DIAGNOSTIC_MODE` check costs one comparison, and with it on the log lines are capped (below); the measurements are read once a minute by threads of their own.
- **Memory TweaksV adds is never writable and executable at once.** The moved arrays are read/write data; the call stubs are written once and then read+execute; MinHook's trampolines are the one exception, accepted (NOTES.md, T-HARDEN). The build carries ASLR with high entropy, DEP, Control Flow Guard and CET compatibility, statically linked (section 15).
- **Per-event output is capped.** Every kind of line that can come without bound - file requests, files served, archive headers, OPEN archives left as they are, mods files that cannot be opened, folders of the mods folder that cannot be read, the opens inside the game folder, DirectStorage's `OpenFile` calls and its refusals after the summary - stops after 20,000 lines of its kind (`kMaxLinesPerKind`, section 6.6; the cap lines are in section 6.3); the events are then only counted, with a summary every minute where `DIAGNOSTIC_MODE` gives one, so no boot fills the 64 MB log. The tables behind a summary are bounded too: DirectStorage's open summary takes 100,000 entries per table, its refused types 15.
- **One wording** (section 6.3) and one log tag per part, the feature name.

## 13. Test builds

### 13.1 The switches

A test build (`-p:TweaksVTestBuild=true`, `TWEAKSV_TEST_BUILD` defined, built into `object\Test\Release\TweaksV.asi`) reads three more keys under `[TWEAKSV]`, never written to the file, and says `TEST BUILD - not for release` in the header: `TEST_BREAK_PATTERN=<label>` treats that pattern as not found; `TEST_LOG_LIMIT_KB=<KB>` (1..65536) lowers the log's limit; `TEST_DUMP_CODE=<seconds>` (1..3600) saves the game's code. The environment variable `TWEAKSV_TEST_NO_BOXES=1` keeps every message box off the screen.

### 13.2 The code dump (`TweaksVDump`)

`StartCodeDump()` takes a copy of the game as it is before any part changes it, and a thread saves it as `GameCode-start.bin`, waits the seconds asked for, takes a second copy and saves it as `GameCode-later.bin`, both in `%LOCALAPPDATA%\TweaksV` through the own-file checks, never in the game folder. A copy holds the PE headers and every section that is not writable - the code, the constants, the function table - and a writable one only when it is also executable; the plain data sections, which can hold the player's data, are never saved; bytes that cannot be read are saved as zeros and counted. The file (format version 1, little-endian): a `DumpHeader` (`magic` "TWKVDUMP", `formatVersion` 1, `sectionCount`, `imageBase`, `imageSize`, `timeDateStamp`, `secondsAfterStart`, `reserved`; 40 bytes), one `DumpSection` per section (`name` as in the section table, "HEADERS" for the headers; `rva`, `size`, `characteristics`, `unreadable`, `fileOffset`; 32 bytes), then the bytes of each section at its `fileOffset`. The log says what was saved: `TEST BUILD: GameCode-start.bin saved, the game as it was 0 s after TweaksV started, before anything was patched: 50.3 MB in <folder> - sections HEADERS .text ...; none unreadable; not saved (the game writes to them): .data ...`. This is how patterns are found after a game update: a dump of the running game is rebuilt as a PE (the headers and the saved sections at their offsets, `.data` as zeros) and analysed with Ghidra's headless analyser, the `.pdata` table giving the functions (PATTERNS.md, "When Game Updates", item 3).

## 14. The tests

### 14.1 The harness

`test\` holds everything, loose in one folder: `run_all.sh` builds and runs every suite from Git Bash and deletes its intermediates (its Release build replaces `x64\Release\TweaksV.asi`); `common.sh` has the helpers; `build_tweaksv.cmd` builds TweaksV's Release and test builds; `build.cmd` builds the fake programs into `object\TestRun`, with warnings as errors (`/WX`); `vsenv.cmd` finds Visual Studio with vswhere; `deps.cmd`, `headers.cmd` and `junction.cmd` are the integration suite's helpers (a module's imports, the PE headers for the mitigations, a junction made and removed - the rageopenv suite makes one too); the fake programs are `fake_game.cpp`, `fake_game_full.cpp`, `fake_game_rov.cpp`, `fake_game_version.rc` and `fake_dstorage.cpp`; `base.ini` is the file the game suites start from (layout 2 with `HEAP_SIZE=1024` and `PACKFILEARRAY_SIZE=12000`, two values that are not the defaults, which the part suites and the integration suite assert - `heap: 1024 MB` - and which prove the file is read), `expected_default.ini` the default file of section 5.4, `layout1.ini` the 1.6.0 default for the 1.x-file scenarios. Each suite is one `run_<suite>.sh`; `run_all.sh` runs them in the order `patterns ini_default story modkit packfile boxstreamer decals rageopenv directstorage integration`, reads each one's `N passed, M failed` line - a suite that prints none counts as one failure, with `no result line (the suite stopped early)` in its line of the RESULTS block - and prints the `all` line, whose count NOTES.md carries (486). The run fails when a check fails, when a suite stops early, when either build log holds a warning (`: warning `; the warnings are listed with the log's last lines), and when the number of checks run is not the one NOTES.md gives, so that a check that silently stops running shows. It deletes `object\TestRun`, `object\TestTemp` and `object\Test` afterwards; `--keep` leaves them, and `--no-build` tests the TweaksV builds already there, which is why it works after a `--keep` run only. The suites are the arbiter: a change to a part passes the checks that pin its behaviour, or it is not done. The fake game's copies of game code live in its `.fakesit` section, since TweaksV searches executable sections only: a site that must be found goes there, and the fake game reaches a moved array only through a pointer, never with an instruction a scan would count. A pattern that must match more than once (`D-E-L12`, seven times) goes through `Scanner::FindAll`, whose per-match DIAGNOSTIC lines name the pattern; the story and packfile suites count on those being the only per-match lines of a normal run. The check count in NOTES.md is the `all` line of `run_all.sh`, updated with every test change; the patterns suite checks that PATTERNS.md and `TweaksVPatterns.h` list the same patterns.

The fake programs pretend to be the game, not TweaksV: they run as `GTA5_Enhanced.exe` (copied to that name for each run), load the real `TweaksV.asi` the way an ASI loader does, ask for the time once (as the game does early on, which runs RageOpenV's start-up), wait for the summary thread, and report. `plain_game.exe` (`fake_game.cpp`) holds no game code: with it every part that uses a pattern reports it missing (DirectStorage only says that `dstorage.dll` is not loaded). `full_game.exe` (`fake_game_full.cpp` with `fake_game_rov.cpp`) holds copies of every site TweaksV patches, laid out so that the patterns match, in a section of its own, `.fakesit`, which is executable (TweaksV searches only executable sections); the arrays those sites reference lie in the fake's ordinary data, and the fake's own code reaches them only through a pointer, so that no `lea` of them in its code is counted by TweaksV's scan. RageOpenV's eight hooked file functions are real code in another section, `.fakefn`, so the hooks are called end to end; the five redirected call sites are only rewritten, and the report calls what they lead to - TweaksV's hooks, and through them the fake's own functions behind the calls. It is built three more times with other version resources (`full_game_1158_13.exe`, `full_game_1013.exe`, `full_game_889.exe`) and once without one (`full_game_nover.exe`) for the packfile part's choice by build. `dstorage.dll` (`fake_dstorage.cpp`) stands in for DirectStorage with its four exports, one of its own that tells the fake game how many calls reached it, and an 8-entry factory whose function [4] is `OpenFile`. After TweaksV has started, the full game prints one report line that the suites read, field by field (`has`): the heap in MB, the three screens' bytes, the modkit references and limits, the packfile references, sizes and hook, the box streamer's references, capacities and calls (each search called with the capacity its site holds, and stopping 16 entries short of it, as the game's do), the decals' references, limits and count, RageOpenV's time hook, console bytes, cache check bytes, file hooks (called with a path the mods folder has and one it has not, the other spellings, a folder, `..` and an over-long path) and encryption calls (called with OPEN and encrypted tags and a fake packfile), the stand-in DirectStorage's results (the configuration calls, the factory, the nineteen `OpenFile` results and how many calls reached the DLL, and with `dsflood` how many of 20,001 more were refused) and the file opens, the call stubs (`stubs: N, all RX`) and whether every page got its own protection back (`protect: all restored (RX)`). Options on its command line set up the scenarios: a pattern missing, a reference pointing elsewhere, an array already moved, a limit that disagrees, a call another mod hooked, a flood of requests, the game's dynamic code policy, and so on; each is listed at the top of `fake_game_full.cpp` and `fake_game_rov.cpp`.

`common.sh`: `fresh_ini` copies `base.ini` with CRLF endings and `ERROR_POPUP=0`; `setkey KEY VALUE [SECTION [FILE]]` and `addkey` edit it (`setkey` also another file); `run_fake [-C DIR] EXE [ARG...]` runs a fake program, in DIR if given, with a fake `LOCALAPPDATA` inside the run folder and `TEMP` and `TMP` in `object\TestTemp` next to it - outside the game folder, as the real `%TEMP%` is; the real ones are never touched - for 60 seconds at most, and notes in `harness.state` how the run ended: stopped at the time limit, without its report (the full game's last field is `protect: ...`, the plain game's `harness: ...`), or with it; `game EXE [OPTION...]` runs one as `GTA5_Enhanced.exe` through `run_fake` and prints its report; `check DESCRIPTION CONDITION` counts a pass or a fail - after a run that was stopped or printed no report every check fails, printed as `TIMEOUT` or `NO REPORT`, until the next run - and `skip DESCRIPTION` counts a check the machine cannot make as passed, printed as `SKIP`, so that the count is the same everywhere (the short form of a profile folder on a volume without 8.3 names, a profile folder's name the ANSI code page cannot hold); `has`, `log_has`, `log_lacks` (which fails when the log is missing, so a negated check cannot pass on a log never written), `log_line` and `count` read the report and `TweaksV.log`; `deny_writes DIR` makes a folder read-only for the user, as a game folder the game cannot write to is, `deny_listing DIR` makes what is in it unlistable, as in a folder copied from another user's account, and `allow_writes DIR` takes back either. Scenarios that must raise a problem with `ERROR_POPUP=1`, the 1.x-file scenarios and the `TEST_` keys use the test build (`TweaksV_test.asi`, chosen with `ASI=`), the only build that reads those keys and keeps the box off the screen.

## 15. Building and releasing

`source\TweaksV.vcxproj` is a plain Visual Studio project, no generated build system: C++20, `/W4` with warnings as errors in spirit (none is tolerated), the C runtime linked statically (`/MT`, `/MTd` in Debug: players need no redistributable), Control Flow Guard with its EH continuation metadata and CET compatibility set in the project (`ControlFlowGuard`, `GuardEHContMetadata`, `CETCompat`); ASLR with high entropy and DEP are the x64 linker's defaults, and the integration suite checks all four on the binary. Its `TweaksVVersionMajor`, `Minor` and `Patch` properties are the version (2.1.0); the `TweaksVBuildInfo` target writes `BuildInfo.h` into the intermediate folder before every build, with `TWEAKSV_VERSION`, its three numbers and `TWEAKSV_GIT_HASH` from `git rev-parse --short HEAD` when the folder is a repository, `-dirty` appended while the tree has uncommitted changes. Four builds matter: Release (`x64\Release\TweaksV.asi` and `TweaksV.pdb`, `object\Release`), Debug (`x64\Debug`, `object\Debug`), the test build (`-p:TweaksVTestBuild=true`, `object\Test\Release`) and the analysis build (`-p:TweaksVAnalyze=true`, `/analyze`, `object\Analyze\Release`); all four must build from scratch (`-t:Rebuild`: an incremental build shows no warnings for files it does not recompile) without a warning before a build reaches me, and `bash test/run_all.sh` must be green; `object\Analyze` is deleted afterwards, as `run_all.sh` deletes `object\Test`, `object\TestRun` and `object\TestTemp` itself. New source files get CRLF line endings; git normalizes every text file to LF, and `.sh` files and `test*.ini` stay LF (`.gitattributes`). MinHook builds at `/W3`, unchanged, from `vendor\MinHook`. `version.rc` fills the file's version resource from `BuildInfo.h`, with the copyright string `Copyright (C) dachdecker369. Licensed under GPL-3.0-only - see LICENSE.`

A release is a tag `major.minor.patch` on the commit I booted, and a zip with exactly five files, for this version and every later one: `TweaksV.asi`, `LICENSE`, `THIRD_PARTY_NOTICES.md`, `CREDITS.md` and `README.md` - nothing else; the `.pdb` stays with the build. The release notes name the tag and link the repository, and `THIRD_PARTY_NOTICES.md` and `README.md`, which ship in the zip, name the repository too, so the Corresponding Source is one step from the binary wherever the zip goes (GPL-3.0, section 6d). The order: version in the project file, a local commit in the style of the earlier `TweaksV 1.x.y` commits, Release rebuilt from it so the header carries that commit, my boots (with `DIAGNOSTIC_MODE=1` when patterns changed, with my map mods for anything that streams), then, with a clean log, push and tag: an annotated tag named and messaged with the plain version, `main` and the tag pushed together.

## 16. Extending TweaksV

- **A new setting:** one entry in `kSettings` (section 4.1) in its section's place, a named reference, a row in README's table, and `expected_default.ini` with the new default file. `IniKeyCount()`'s `static_assert` names the count (28) and fails until it is updated: as the code stands, a new key in the file means a new layout number (`kIniLayoutVersion`), and the suites pin that number in `run_ini_default.sh` (the header line, the `VERSION`-alone file and its 27 keys added back, the newer-layout line) and the key count per section in `run_directstorage.sh`. An existing file gets a missing key added back with its default at the next start whatever its `VERSION` (section 5.3), but nothing carries it to a new layout number: `VERSION` is never written back and its lower limit is the current layout, so after a bump every existing file would report `VERSION=2 is outside 3..1000000` at every start until that step exists - the open issue T-LAYOUT in NOTES.md, which goes with the first layout bump. The 1.x rule stays as it is (a file without `VERSION`).
- **A new pattern:** one entry in `kPatterns` with a new label in its part's group, and the row in PATTERNS.md with the same bytes, the offset and what the match holds; the code names it as `Pattern("label")` once. The `patterns` suite fails until both agree. After a game update the same: the table and PATTERNS.md change together, and `DIAGNOSTIC_MODE=1` with `DRY_RUN=1`, `CONSOLE=1` and every part on shows that every pattern matches as often as it must (`D-E-L12` seven times).
- **A new part:** a section in `kSections` and `kSettings` (the layout rule above applies), a feature in `kFeatures` in the order of `kSections` (a `static_assert` checks it) with its old plugins and `Init<Part>()`, one file `TweaksV<Part>.cpp` with its header comment, its tag and its credits, listed with its header in `TweaksV.vcxproj` and `TweaksV.vcxproj.filters` (the project lists every file by name), patterns in the table, a suite `test\run_<part>.sh` with the sites added to the fake game and its name in `run_all.sh`'s list of suites, a section and the key rows in README, a bullet in NOTES and the new check count there, a section 11.x here, and the project the part derives from or takes its idea from in CREDITS.md (and in THIRD_PARTY_NOTICES.md where the part carries its code). The part finds and checks everything first, writes through `WriteCode` or `RedirectCalls`, hooks through `HookFunctions`, reports through `ReportFailure` with its job's wording, logs in the wording of section 6.3, and runs a measurement, if it has one, through `StartMeasurement` (section 6.6).
- **A new array part:** a `RelocationSpec` with its anchors (section 10.1), `FindRelocation` then `ApplyRelocation`; what the core cannot express stays in the part and reads `RelocationPlan::matches`.
- **A fork or a pull request** keeps the license (GPL-3.0-only), CREDITS.md and THIRD_PARTY_NOTICES.md, which must accompany every copy, and the notices' three pieces of code (the console opener, the pattern parser, the free-memory search adapted from MinHook's `buffer.c`) credited as they are; keeps the parts their own code, as 2.0.0 made them, and carries no code of the projects that are idea only (CREDITS.md names them); keeps the suites green with the count updated in NOTES.md; and keeps the documents true: PATTERNS.md for every game fact, NOTES.md for what a part does, this file for how it does it, README.md for the player.
